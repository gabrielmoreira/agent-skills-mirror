# 改进已有 Skill

当用户给出失败案例、反馈或模糊的改进目标，需要找出问题并提出修改方案时读取本文件。用户已经说清改哪里、改成什么的小改，不需要本文件。

Skill 文件本身不会持续学习。每次改进都由当前 Agent 读取运行证据、修改文件并保存结果；没有写入文件或记录时，下一次调用不会继承本次经验。

## 复现失败

先拿到一次实际失败，再判断原因：

- 用户给了失败输出或运行记录：读完整记录，找到失败发生在哪一步；
- 用户只有印象，例如“它总是太啰嗦”：用一个贴近真实使用的请求运行当前版本，取得实际输出；
- 无法运行，也没有记录：在方案中把这条问题标为“未复现”，修改项写成待验证假设。

只看最终答案容易误判因果。能取得过程记录时，对照每一步的指令检查偏差从哪里开始。

## 把目标改写成可观察行为

“更聪明”“更像我”“更好用”需要改写成能核对的行为。例如“知识尚未核实时不要提前写结论”可以拆成：识别未经核实的主张、标记核实状态、提出取证动作、不写确定性结论。

只写本轮改动涉及的行为，不需要为整个 Skill 重写完整契约。需要完整契约时，格式见 [problem-and-goal.md](problem-and-goal.md) 的「行为契约」。

## 失败归因

每个失败先确定一个主要来源：

| 来源 | 识别信号 | 处理 |
| --- | --- | --- |
| Skill 指令缺陷 | 相似任务在同一步稳定出错 | 修改决策条件、步骤、reference 或 script |
| 触发描述缺陷 | 该用时没用，或相邻任务误触发 | 调整 `description` 的用途和使用条件 |
| 输入缺口 | 缺少会改变结论的材料 | 增加必要输入或最少追问条件 |
| 样本缺陷 | 预期互相冲突、脱离真实使用或泄露答案 | 修订测试，不修改 Skill |
| 评分缺陷 | 断言只检查格式，或与用户真实目标无关 | 重写验收标准，必要时加入人工评审 |
| 工具环境故障 | 权限、网络、依赖或文件缺失 | 修复环境或资源打包 |
| 执行波动 | 相同条件下偶发失败，没有稳定模式 | 重跑观察，降低结论强度 |
| 理论缺口 | 出错的步骤没有可靠的判断方法，只能靠模型临场发挥；或用错了理论 | 按 [theory-grounding.md](theory-grounding.md) 补上或替换理论锚点 |

只有指向 Skill 指令、触发描述或理论缺口的失败，才进入修改清单。其他来源在方案中单独说明处理方式。

## 判断错在哪一层

同一步出错，根源可能在三个层：

| 层 | 表现 | 修法 |
| --- | --- | --- |
| 规则层 | 判断条件没写清，或规则互相冲突 | 补条件、删冲突 |
| 方法层 | 这一步没有可靠的判断方法，或理论用错了 | 补上或替换理论锚点 |
| 骨架层 | 整个 Skill 解决问题的路线不对 | 建议用户升级为新建或大改，重新寻找标准答案 |

在能解释所有同类失败的那一层修改。同一位置已经打过补丁仍然出错，通常说明问题在方法层或骨架层，不再继续加规则。

## 最小修改

对每项准备修改的问题写一行：

```text
观察到的失败 → 推测原因 → 修改位置 → 预期改善 → 可能影响
```

优先顺序：

1. 补清决策条件和停止条件，或为出错步骤补上理论锚点；
2. 调整步骤顺序或输入输出的传递；
3. 增加一个能拦截错误的检查点；
4. 把重复、确定的工作沉淀为脚本；
5. 删除无效或互相冲突的指令；
6. 最后才增加更长的规则清单。

新增规则时说明它覆盖的一类失败。不把测试题答案、专有名词或单个案例细节直接写进通用规则。

## 常见的虚假改善

出现以下情况时，候选不能视为变好：

- 追着单条反馈修改，把一次偏好写成通用规则；
- 只增加规则，不清理重复和冲突，指令越来越长；
- 执行者提前看到预期答案；
- 用平均表现掩盖安全、事实或权限边界上的严重失败；
- 只看触发率提高，没有检查误触发和任务完成质量；
- 连续在同一组样本上迭代，逐渐迎合样本。

## 迭代记录

用户打算持续迭代同一个 Skill，或本轮使用了完整评测时，把记录保存在目标 Skill 的 `evals/` 或用户指定目录，至少包含：本轮目标、样本、改动前后的标识、失败归因、实际修改、对比结果和未解决问题。记录要能让下一次 Agent 恢复上下文。

一次性的小修改不需要记录文件，交付报告即可。
