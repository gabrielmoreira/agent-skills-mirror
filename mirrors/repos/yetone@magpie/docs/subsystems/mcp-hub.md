# MCP hub

With the Library's switch "MCP hub" on (#2679, @minggang123 on X), each agent is given one MCP server, `magpie`, in place of the Library's MCP servers ticked for it. magpie serves it at `/mcp/magpie/hub/<agent>` (Streamable HTTP) and hands each call on to the Library server behind it. Any other app (Cursor, VS Code, Windsurf, an app on another computer) connects at `/mcp/magpie/hub`, which serves every server in the Library. A server written once is then set up once, for every agent and app, and a command server runs once, not once in each. The servers themselves are the [Library](library.md)'s; the endpoint is the gateway's, guarded as [Plugin tools](plugin-tools.md)' `/mcp/magpie/tools` is. The switch is off by default.

The CLI's `magpie library mcp hub on|off` calls `SetMCPHub`, and `magpie library` lists the agents given magpie's entry and those that keep their own, with why (`libraryStatus` in [`library_cli.go`](../../internal/cli/library_cli.go)).

The gateway can't import the library (the library imports the gateway), so the gateway declares `Hub` and `MCPHub`, and the library sets `MCPHub` in its `init`.

## Runtime path

1. The user turns the switch on. `SetMCPHub(true)` saves `mcpHub` and syncs: each agent that can take it gets the one `magpie` entry, and the servers behind it are taken out of that agent's file. Nothing is started yet.
2. The agent starts and posts `initialize`, then `tools/list`, to `/mcp/magpie/hub/<agent>`. `hubMCP` passes the guard. `Tools` reads library.json for the servers ticked for that agent, and lists each in parallel, by `hubListWait` (40s): a server not reached by then is left out of that list, not an error.
   Another app does the same at `/mcp/magpie/hub`, under the same guard: from another computer it needs a gateway key, as every LAN request does.
3. `tools/call` finds the tool by its hub name in the same list, holds it to the key's limit, and calls `Call` under `hubCallWait` (50s, under the 60s an MCP client gives a call). The server's result goes back as it gave it.
4. An error comes back as `isError` text naming the server: `The MCP server S couldn't run T: <why>`, where why is how it exited and its last line on stderr, a sign-in it needs, its command not found, or `it didn't answer in 50s`.

## Constraints and failure behavior

- Off means off: no tool is listed, a call says the hub is off, and no server is started (`TestHubMCPOff`, `TestHubToolsAndCalls`).
- magpie takes out only the `magpie` entry it wrote (`Applied.MCP`). An entry called magpie of the agent's own, or a Library server called magpie, keeps every server's own entry for that agent, said on the page.
- A tool turned off in the Library is neither listed nor run, for every agent, including those that have no setting of their own for it.
- A call that times out leaves the server running for the next; a server that died is started again. A server that can't be started is an error on each call, not a retry loop.
- Every process the hub starts is in a `proc` tree magpie ends when the switch goes off, the server is edited, it has been idle, or the gateway stops. A test ends them in cleanup (`hubSandbox`).
- A gateway key holder on the LAN reaches the Library's command servers through the hub while it is on, as they reach plugin tools. They run with the user's rights on this computer.
- The tools a server listed are cached until it says they changed, it is edited, or the switch is turned off. A server that changes its tools without saying so shows them after one of those.
