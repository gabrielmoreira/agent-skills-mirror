# Gateway routing and fallback

The gateway is magpie's local LLM endpoint (`127.0.0.1:3425` by default). It
serves Chat Completions, Responses, Anthropic Messages and Gemini. It finds
the provider, key or account and model for each request. When the upstream
doesn't speak the agent's API, the gateway translates. When an upstream
fails before any of the reply is sent, the gateway moves to the next
candidate.

This page covers how a request is routed. Plugins that change requests and
replies are in [Gateway middleware](gateway-middleware.md). Subscriptions
served by a plugin are in [Provider and plugin ownership](provider-plugins.md).

## Codex titles, descriptions and predictions

Codex's title and description requests are independent hidden turns. The
settings `CodexTitles` and `CodexDescriptions` select their models separately;
an empty setting preserves the requested model. On a Magpie model, both
paths wrap plain model text in the object Codex requested. Titles use
`{"title": ...}`; descriptions use `{"description": ...}` with nonempty text
and no invented maximum length. Title Off mode does not disable descriptions.

`codexTitlesTo`, `codexDescriptionsTo`, `codexTitle` and `codexDescription` in
[`codex_titles.go`](../../internal/gateway/codex_titles.go) own this selection
and response wrapping. Both the Responses API and Codex backend entrypoints
use it. Usage and Routing retain the original purpose; unusable description
answers are recorded as description failures. These helpers do not decrypt
foreign sealed history or repair ChatGPT's response protection.

Codex's composer predictions (#1970), its guess at the user's next message,
are another hidden turn on a fork of the thread, sent only through the
ChatGPT sign-in, with `thread_source` `composer_predictions`. Each one reads
the whole conversation again. `CodexPredictions` selects where they go: empty
sends them as Codex asked, `off` answers `{"suggestion":null}` from magpie
and sends nothing (`sentNowhere`, as title Off mode), and a model id sends
them to that model. `codexPredictionsTo` and `codexPrediction` own this, at
the same two entrypoints. A model's answer reaches Codex only as the
`{"suggestion": string|null}` object it asked for (`predictionJSON`): plain
text is never taken as a suggestion, as Codex would put it in the user's
composer as their next message, so it gives no prediction and the call is
recorded as a prediction failure (`noPrediction`).

## Runtime path

1. `handle(proto)` reads the body and the model (`requestBody`, `requestModel`), then calls `serveAgent`. Every route that reads an agent's body (each API, count_tokens, Gemini's, embeddings, images, videos, System One, the Codex backend path) reads it through `readBoundedRequestBody` in [`request_bounds.go`](../../internal/gateway/request_bounds.go). It decodes a `Content-Encoding` of `gzip` or `zstd` (`decodedBody`; Codex sends zstd to a custom provider's `/v1/responses` too, #1223) and drops the header, so the provider is sent plain JSON, with one exception: a ChatGPT account's turn (POST `CodexBase`/responses, from the accounts loop in `forwardOnce` or relayed by `codexUpstreamOn`) is compressed again with zstd, as Codex's own client sends it (`provider.CodexCompressed`; openai/codex `responses_request_compression`). It is compressed once the body is final, and again on each try. `/responses/compact`, an API key's requests and every other provider stay plain. Sent plain, a 1.1 MB text-only turn was answered 503 (ylorn on X). The plain body is what magpie keeps and shows, and `codexDropped` judges a reset by the bytes that went on the wire. `codexDropped` also reads Envoy's 507 "exceeded request buffer limit while retrying upstream" (the backend failed and the front couldn't retry a body that large) as that reset, at any size, told as a 503 so magpie, Codex and pi ask again and nobody rests (#2034). The size limit (`defaultBodyLimit`, 512 MB) holds for the decoded bytes (413), and any other encoding is refused 415. It was 128 MB until a long Codex session that had read many images went past it decoded, its inline screenshots resent each turn, and got the 413 on all five of Codex's retries (#1422, `TestImageHeavyCodexTurnIsRead`). magpie's own 413 says it is magpie's gateway limit, with the size, and that the provider was not asked (`overLimit`); `writeError` adds to any 413 it isn't holding that this is a byte limit, not the model's context, and to `/compact` or start a new conversation (`TestOverLimitSaysWhoseAndWhatToDo`). `keyLimited` reads a limited key's compressed body the same way, so its reservation is the decoded size. `serveAgent` runs the [middleware](gateway-middleware.md) chain, then `serve`.
2. `serve` redacts secrets in the request (`redacted`; `redact.MaskJSON` leaves ids alone; the request's tool definitions and output schemas, found by their place in each protocol (top-level `tools`, `tool_choice`, `response_format`, `text`, `generationConfig` and the like, and the tools of a Responses `additional_tools` or `tool_search_output` item), go as written save their descriptions, so a word the user masks can't break a grammar or an enum (#1911); and what the vendor sealed with a signature, a thinking block, Gemini's thoughts or Responses' encrypted reasoning, goes back as the vendor wrote it: only the values masked elsewhere in the request, and secrets masked before, are put back as their placeholders; a value masked once, at least 8 characters long, is masked again wherever a request has it, as an exact match whatever words are around it, so what the vendor wrote about a placeholder doesn't go back with the value in it, `redact/known.go`), resolves the model to a provider or a group, and refuses what can't be served. The reply has the values put back on its way to the agent (`redact.Writer`, a stream event by event, a whole body at its end): a placeholder the model wrote as it was given, or as models rewrite one (spaces inside the braces, a brace or both dropped, another case), is the value again when what is left names one magpie made, and one split across events is held until it is whole (`redact.Restore`, `partialTail`, [`internal/redact/redact.go`](../../internal/redact/redact.go)). Then `affine` moves the conversation's last answerer first, unless it is resting or nearly used up. An `X-Magpie-Account` header (`AccountHeader`) pins the request to one account: only that account is tried, and when it can't answer the caller is told why.
4. The candidate loop calls `attempt` on each candidate in turn, through a `holdWriter`. The writer holds the reply until it is clearly passing. A candidate that fails before anything is sent rests (`failure`): out of credit for 30 minutes, out of quota until reset, rate limited until retry-after, otherwise a minute and longer on repeats: doubled each time, up to `longestRetry` (10 minutes) for a failure and `longestRateRest` (30 minutes) for a rate limit back as soon as its rest is over, or up to the provider's own `restCap` in minutes (`Provider.RestCapOr`, at most `MaxQuotaRest`; `magpie provider rest-cap <id> 4h`, #2008: a free key down for hours was asked every 10 minutes). A time the vendor names stands over it as before (`TestOwnRestCap`). A 400, 403, 404 or 422 that says the model isn't served (`unservedWords`) and says nothing of quota, credit or a rate limit rests only that key's or account's model (`modelRefused`, keyed by `restID`, its backoff counted apart): its other models are still served first in order (#1235, SenseNova's 403 "model is not available in the current token plan"). A 400, 404, 410 or 422 that says the model is retired (`retiredWords`: OpenCode Zen's 410 `ModelDeprecated` "Model exo-free has been deprecated.", whose own model list still names it; MOMO on Discord) rests only that model the same way, is retryable so a group's next member or another provider of it is asked, and is remembered (`provider.Retire`, `retired.json` beside `providers.json`): the model leaves that provider's entries in the catalog (`buildEntries`), so /v1/models, every agent's model list and the found groups go without it, until a request on it is answered again (`Unretire` in `servedCandidate`) or a week has passed. A refresh of the vendor's list doesn't bring it back early, since that list is where it still is. A `provider/model` request for it is still sent. A 400 or 422 that says this upstream's API can't take the request's shape (`shapeWords`: xAI's 422 "unknown item type" (#350), OpenAI's "Unknown parameter", and a limit of a model's own on tool schemas, OpenCode Go's 400 "JSON schema exceeds the maximum nesting depth of 10 levels" on muse-spark-1.3-contributor, #1870) rests nobody: the next candidate is asked once (`shapeRefused`, `failShape`), and the last one's error reaches the agent. A request missing what every API requires ("field required") isn't one, nor is a 200 that mentions it. A subscription account that fails any other way with a window full, by magpie's latest reading of its windows, rests until that window renews. Both quota rests and window rests are held to `longestQuota` (8 days), so a reset time read wrong (a year off) doesn't bench the account for that long. The next candidate is then tried. A failed provider waits `fallbackCooldown` (1 minute) at the back. A WorkBuddy account the vendor restricted (#1849: 403 `{"code":11140,"msg":"request illegal","displayMsg":{"en":"Your account has been restricted due to unusual activity",…}}`) rests `restrictedRest` (2 hours) as `restricted` (`failRestricted`), not the minutes of an unknown failure: only WorkBuddy lifting the restriction, after the user's appeal, brings it back. Both shapes are known: the built-in's `wbExplain` and the plugin's `explained()` (0.1.17, the mover's `min`) end the error with `provider.WBRestrictedHint` (`restrictedSaid`), and the vendor's own body, its code 11140 or its words (`provider.WBRestricted`), counts only from a WorkBuddy candidate (`restrictedRefused`, `isWorkBuddy`), as another vendor's 11140 is its own. Bare "request illegal" isn't matched. WorkBuddy's 11128 channel refusal stays `promptRefused` and rests nobody. The Routing page names it "account restricted by the vendor", says the appeal is the way back, and gives the account's row a button that lifts the rest (`/api/gateway/unrest`) once the vendor has. Every other rest a key or account takes (quota, rate limit, retry-after, a failure's backoff) can be lifted by hand the same way (#1869): "Try now" on its row on the Routing page and beside its rest note in the provider's key list. It ends the rest only: the backoff count stays, and a refusal after it rests the key again the usual way. The vendor's safety filter refusing a reply rests nobody, whether it refuses the turn before any of the reply is said or once some of it has been said (`refused`, `refusedAfter`). Its note on the try (and in the error the agent gets when nobody is left) is the vendor's reason, with Anthropic's `stop_details` category and explanation when it gave them (`refusedDetail`, #1768: "safety filter: refusal (category cyber)"); none is made up when it gave none. `stop_details` is carried through the IR (`Event.StopDetails`), so a Claude subscription run through the claude CLI and a translated Anthropic route keep it for an Anthropic client too. How many more candidates a refusal before any of the reply is asked of is Settings' `RefusalRetries` (`refusalAsksAgain`, counted per request in the candidate loop; a group's other members count too): unset, every one left (#248); 0, none (#1925, DD on Discord). When nobody is left, an agent on Anthropic's Messages API gets the held refusal itself, the vendor's 200 with `stop_reason` `refusal` and its `stop_details`, streamed or whole (`holdWriter.handBack`), since that is what Claude Code switches to its fallback model on; a 400 is only an API error to it. Codex and Chat clients still get `failTo`'s 400 (`refusedStatus`), which they don't ask again for. `TestRefusalRetries*` in [`refusal_retries_test.go`](../../internal/gateway/refusal_retries_test.go) cover keys, a group and the Claude subscription. The ChatGPT backend's 502 "response protection is unavailable" is about the request's content, not the account: the same history fails the same on each of its accounts and models. It rests nobody, isn't tried again after a moment, and isn't asked of the provider's other accounts or models; another provider left in a group is asked once (`protectionRefused`, `elsewhere`). One cause is known (#1270): a history that replays the backend's own `web_search_call` in a request that doesn't declare the `web_search` tool is refused so, whatever the account, model or turn (a plain turn, a thread's description, a compaction, Codex's own text compaction for a custom provider with `tools: []`). Every request to the ChatGPT backend with such a history therefore declares cached-only search (`{"type":"web_search","external_web_access":false}`, `provider.DeclareSearch`): an account's in `codexBody`, Codex's own sign-in relayed in `codexUpstreamOn`. It goes in the tools, or for Responses Lite (its header, `reasoning.context` `all_turns`, or an `additional_tools` item already there), which refuses a top-level `web_search`, in the `additional_tools` item. A request that offered no tools gets `tool_choice` `none` so the model can't search; one with a forced choice keeps it. A history without a search, or a request that declares search already, is relayed unchanged. siwc, API-key requests to openai.com and the legacy `/responses/compact` are left as they were.
5. The last candidate's error reaches the agent, with one exception for a group (#1418, `patience.go`). When every member has failed in a way that passes (`busy`: 408, 500, 502, 503, 504 or 529 that isn't a proxy, a quota or response protection, or a 429 that is a short rate limit, not a plan or credit), and nothing of the reply has been sent, the members that failed so are asked again in turn after a pause (`replan`). The pause is `retryPause` doubled each round up to `replanLongest()` (30 times `retryPause`, 30s), and never shorter than the soonest Retry-After; a member whose Retry-After ends past the pause is asked after the others. This goes on while the group's `Patience` lasts. `replanRounds` (12) is only a backstop that never comes first: the pauses alone add up to `PatienceLongest` in 11 rounds (with 6, a group set to 240s gave up after 90s of pauses, real-jacket on #1418; `TestPatienceIsUsedUp`). The budget is the group's `Patience`, counted from the first time every member had failed, when the agent would have had the error (`waitFrom`; `Group.Waits`: 0 is `PatienceDefault`, 60s; -1, `PatienceOff`, turns it off; at most `PatienceLongest`, 240s). A pause that would end past the budget isn't taken, and the agent gets the error. While another member is busy too, the last one isn't first tried again alone (`passing`): the members take turns, and once the budget has begun, the same-one retries aren't taken either. While the budget lasts, the last candidate's failure is held (`newHoldWriter`), and a streaming agent is kept alive through the pause with SSE comments (`pauseAlive`). The try is traced with `Again` (the pause), `Replan` (how many are asked again) and `Patience` (the budget in seconds). The group editor's "Every member busy" row sets it. A plain provider keeps only the same-one retries `passing` gives the last one left. An agent that goes away in either pause (the same-one retry's or a group's replan) ends the request there with 499: nobody is asked again, and the try whose pause it was is marked `Gone` (#1894, heng91: a relay down while its proxy was off, the agent's window closed). The Routing page says the agent canceled the request before the retry and lists it as canceled, rather than ending its story on "tried again in 2s", a retry that never came (`TestAgentGoneInTheRetryPause`, `routing-agent-gone.test.cjs`). A try that answered is recorded (`served`, `answered`) for routing, affinity and usage.

## Constraints and failure behavior

- A fallback happens only while none of the reply has been sent. An agent never gets half a reply from one upstream and the rest from another.
- A request is one usage record, counted once by how it ended (小一 on Discord: Codex on credits showed "5,482 · 1,094 failed" while rows said "2 tries/3 tries" and had been answered). The final record carries `tries` when the route took more than one (`rec.Tries`, from the trace's `Tries`). A try a vendor refused or turned away (`hw.refused`, `hw.turnedAway`) still writes its own record, for what it billed and why it failed, marked `handed_on`; `usage.Totals.count` skips such a record for calls and failures. A request failed only when the agent got an error (`LostRequest`); one answered after a failed try is counted beside it as answered on a retry (`Totals.Retried`, `RetriedRequest`, the `retried` filter). Logs written before `handed_on` are read the same way: the log index marks a failed, non-rejected record followed by another of the same route id as handed on (`routeRows` in [`log_index.go`](../../internal/usage/log_index.go)). Counts by account or route (`vias`, window holds) still count every try.
- Each record keeps the service tier three ways (#1784): `tier_asked` is what the client's body asked (`bodyTier`; Claude's speed fast reads `fast`), `tier_sent` is what that try's last request went out with, noted in `forwardOnce` after every rewrite (fast picks, Ultrafast to priority on a plan without it) onto the per-attempt `wireAt`, and `tier_served` is only what the reply said it ran at (`upstreamTier`, read by the sniffer and the translated readers), empty when it says nothing. The route's tries carry `tier` and `tier_served` the same way. A bridge that doesn't go through `forwardOnce` (the Claude subscription, Cursor's built-in) leaves `tier_sent` empty. Code: [`tier_record.go`](../../internal/gateway/tier_record.go).
- A usage record carries its prompt's cache beside `in` and `out` (#1839): `cache_read` (tokens read from the vendor's cache) and `cache_write` (cache creation, Anthropic's `cache_creation_input_tokens`; `cache_write_1h` the part written for an hour). `in` holds neither. Both are written on every record, 0 too, so a prompt that missed the cache reads as that. A record from before then has neither and reads as 0. Every route fills them: Anthropic's messages, Chat (OpenAI's `prompt_tokens_details.cached_tokens`, DeepSeek's `prompt_cache_hit_tokens`), Responses (`input_tokens_details.cached_tokens`) and Gemini (`cachedContentTokenCount`), passed through or translated, whole or streamed, a plugin's fetch, and the Claude subscription bridge. System One's decision calls report no cache. `TestUsageRecordsCacheTokensOnEveryRoute`, `TestPluginUsageRecordsCacheTokens`, `TestClaudeSubscriptionUsageKeepsCacheTokens`, `TestRecordAlwaysCarriesCacheTokens`.
- A request whose key is a Claude sign-in (`claudeSignIn`: `Authorization: Bearer sk-ant-oat…`, Claude Code signed in to claude.ai with magpie as its base URL) is never told a 401, nor a 403 saying "OAuth token has been revoked". magpie never passes that sign-in on, so such an answer is a provider refusing magpie's credential, or one of magpie's own Claude accounts lapsing; told it, Claude Code renews its own sign-in before each of its retries (ten for one request) and then asks to `/login`. Any error whose message mentions x-api-key, whatever its status, Claude Code tells as "Not logged in · Please run /login" too. ## Search results in translated Responses replies

When a search is done for a model (`searchReply`), or a Responses provider's
search is decoded for translation, its `KSearch` event and collected
`Search` part hold the query and pages found. [`responses.go`](../../internal/gateway/responses.go)'s
`responsesEncoder.event` and `renderResponses` return these as completed
`web_search_call` output items through the shared `responsesSearchItem`.
The action says `search`, carries both `query` (older clients) and `queries`,
and lists the nonempty source URLs in `action.sources`. An actual search
with no sources has an empty list; a text answer alone creates no search.

The stream adds and completes each search item, emits
`response.web_search_call.completed`, and keeps the same item in the final
response's `output`. Search events arrive after the search has run, so no
earlier progress is fabricated. Search items keep their order among text,
reasoning and client tool calls. They carry sources, not invented
`url_citation` annotations: the shared search result has no citation offsets
in the model's answer. Native Responses passthrough is unchanged. A client
that sends the item back in its next input (Codex replays its output) loses
nothing: `parseResponses` has no case for `web_search_call` and leaves it
out, as before.

This lets a Responses client verify search execution and display source
links without sending a separate Anthropic Messages request. Covered by
the `TestResponsesSearch` tests in
[`responses_search_test.go`](../../internal/gateway/responses_search_test.go)
and the Responses cases of `TestWebSearchForAModelThatCannot` in
[`search_test.go`](../../internal/gateway/search_test.go).

## A search API's base URL

Each search API ([`provider.SearchAPI`](../../internal/provider/search_api.go))
has an optional `url`, its base URL: an endpoint of the user's own that
answers as that API does (#1580). Empty is the vendor's own
(`SearchVendor.Base`); SearXNG has none, so its URL is required. `check`
takes only an `http://` or `https://` URL with a host and no `?query` or
`#fragment`, since `askSearchAPI` puts the vendor's path after it
(`/search`, `/res/v1/web/search`, `/v2/search`) with the slash at its end
trimmed. The request goes through the gateway's client, so it follows
magpie's proxy settings as the vendor's own address does
(`TestSearchFollowsTheSearchersProxy`).

The key is sent only to that URL. Go keeps Brave's `X-Subscription-Token`
and Exa's `x-api-key` across a redirect to another host, so `askSearchAPI`
doesn't follow one. The 3xx is the error, and it names where the search
was sent. magpie ships and lists no third-party search endpoint; the URL
is only ever the user's.

A value the user set is never replaced by the vendor's default. In
Settings › Models › Web search the field sits under the key for every API,
with the vendor's own address as its placeholder. Picking an API that is
already added fills in its saved URL, so Add with a new key alone keeps
the URL, and Add with no key changes only the URL. On the CLI,
`magpie search add <api> <key>` keeps the URL set before, and `url=` with
nothing after it puts the vendor's own back. Backup and sync carry `url`
with the rest of the entry.

Covered by `TestSearchAPIAtItsOwnBaseURL`, `TestSearchKeyStaysAtItsBaseURL`,
`TestSearchAPIBaseURLFromSettings`, `TestSearchCLI` and

## A search API's keys

A search API's `key` may hold several keys, separated by commas (#1477).
`askSearchAPIKeys` asks them in the order `searchKeyOrder` gives
([`search_keys.go`](../../internal/gateway/search_keys.go)), each with a
quarter of the search's time. By default they take turns (SlouchyQuill on
Discord, after dsh-tavily-pool): a counter per vendor moves the first key
asked on by one each search. `pick` `order` (`provider.SearchPickOrder`,
`magpie search add … pick=order`, In order in Settings) always starts from
the first. Only a refusal (`searchRefused`: 401, 402, 403, 429, 432, 433)
goes on to the next key; any other error ends the search there.

A refused key rests (`searchRestFor`): 401 and 403 ten minutes ("turned
away"), 402 an hour ("out of credit"), a rate limit its `Retry-After` held
to 30 seconds through 10 minutes (a minute without one). 432 and 433 are
Tavily's plan and pay-as-you-go limits, out of credit from Tavily only; from
any other vendor they rest as a rate limit. A resting key is not dropped:
it is asked after every key that isn't, the one back soonest first, so a
search still has every key to fall back on. A key that answers wakes.
Rests are held by vendor and a hash of the key (`searchKeyID`), never the
key itself, and the vendor's error has the key masked
(`provider.MaskSearchKey`, `tvly-…abcd`) before it is logged or returned.

What each Tavily key has used is read from `GET /usage` with that key
([`search_quota.go`](../../internal/gateway/search_quota.go),
`readTavilyUsage`): the key's own `limit` when it has one, else its account
plan's `plan_limit` and `plan_usage`, shared by the account's keys (a free
account's keys have `limit` null); both null is no limit. A read that fails
or a reply missing those fields is unknown, with why, never 0 used. A read
is kept two minutes (Tavily allows /usage 10 times in 10 minutes) unless
asked fresh. A key at its limit with no pay-as-you-go credit left rests an
hour as "used up"; a later read that finds credit wakes a key resting for
that or for being out of credit. Settings › Models › Web search shows a row
of the keys under an API with several or with Tavily's (In turn / In order,
each key masked with what it has used, Check again), and `magpie search`
lists the same, read fresh.

Covered by `TestReadTavilyUsage`, `TestSearchKeysTakeTurnsRoundRobin`,
`TestSearchKeyRefusedRests`, `TestSearchRestFor`, `TestSearchQuotas`,
`TestSearchKeyNeverInFull`, `TestSearchAPIKeysTakeTurns` and
`search-keys.test.cjs`.

## Web search as an MCP server

`SearchMCPPath`, `/mcp/magpie/web-search`, serves the same `webSearch` a
model that can't search is given (the searcher's model, a Kimi Code plan's
service, the search APIs, as Settings › Models › Web search orders them)
as an MCP server of its own, so Cursor, Claude Desktop or any agent can
mount it as a `web_search` tool (Kayphoon on Discord). It speaks Streamable
HTTP only: each POST of a JSON-RPC message or batch is answered with JSON
(`initialize`, `ping`, `tools/list`, `tools/call`), notifications get 202,
and GET and DELETE get 405, since the server has no stream or session of
its own. Legacy SSE isn't served; a client that only speaks stdio mounts it
through `mcp-remote`. The path has two segments under `/mcp/`, so it can't
hide a signed-in server's `/mcp/{name}`.

It is a gateway route like the others. `lanGuard` takes a gateway key from
another machine (only while magpie is shared) and refuses a rebound browser
host, and the handler checks `local`/`sharedWith` again as a backstop when
`Handler` is served without `lanGuard`. Unlike other routes, a web page on
this computer (a `localhost` Origin, which `corsGuard` lets through) is
refused too: only an origin listed in Settings, which `corsGuard` already
held to a gateway key, may call it, as the MCP spec has a server check
`Origin`. `keyLimited` passes `/mcp/` by, so each `tools/call` reserves the
calling key's limit itself (`budget.Reserve`), and a spent key's call is a
tool error with no search made. The search is marked `CallFor{Agent, MCP:
true}`, so Routing says the agent called magpie's web_search MCP tool rather
than that magpie searched for one of its models. With nothing that can
search, the tool error says where to add a search API. Settings › Models ›
Web search shows the address (`#searchMcpRow`, from the Settings page's own
`gateway` address).

A POST's body is read by `readMCPBody`, up to 1 MiB here and 32 MiB for
vision and for a signed-in server's `/mcp/{name}`. A longer body is refused
whole with 413, before any message in it runs or is passed on: the length is
told from the bytes read, one past the limit, not from Content-Length, so a
valid message padded past the limit is never run as its prefix (#1766).
`TestOwnMCPRejectsOversizedBody` and `TestMCPProxyRejectsOversizedBody`
cover it.

Covered by `TestSearchMCPServesWebSearch`, `TestSearchMCPWithNoSearcher`,
`TestSearchMCPGuarded`, `TestSearchMCPHeldToKeyLimit`,
`TestSearchMCPRoutedAsTheAgentsCall` and `search-mcp.test.cjs`.

## Side models magpie picks: allowance first

When magpie picks the model itself (`AutoVision` for image recognition,
`autoSearcher` and the turn in `modelSearch` for web search), it picks
before routing runs, so routing has one provider to try and would try it
"all the same" while every account of it rests. Each request would then be
refused upstream again (#1801). `spentModel` (fallback.go) says a model is
out of its allowance when every candidate routing would try for it is
barred at a usage cap, resting for quota or credit (not for rate), or has
a full window (`candidate.full`), and when it is back. `smallModel`
(`smallReady`) prefers models that aren't spent, and the pickers rank a
provider with allowance above any tier or searchRank. With every one spent
they still name a pick, so `seer`/`Described` and `canSearch`, which tell
agents what magpie offers, don't flip with a window. Such a pick isn't
asked: `askVisionWith` (`autoSpent`) answers with the reason and when it is
back, and `modelSearch` (`searcherSpent`) skips it, puts spent searchers
after the others and joins the reason into its error. A model named in
Settings is asked as before, and a searcher named there is not handed on
to another provider when it fails (see "A searcher that fails or finds
nothing"). Image and video generation (`AutoDrawer`,
`AutoVideomaker`) are not held this way.

`TestAutoVisionTierAmongThoseWithAllowance`, `TestSpentModelAcrossAccounts`,

## Model ids without the provider

A client moved from another proxy (love1sbug on X, from CLIProxyAPI) keeps
asking for `gpt-5.6-sol`, and picks from `/v1/models`, where magpie lists
only `codex/gpt-5.6-sol`. A bare request already routes (Model resolution,
above); the list didn't offer it. "Provider in model names" (`PlainNames`)
changes labels only, never ids.

Settings › Network and sharing › Model ids without the provider,
`POST /api/settings/bare-ids` (`settings.BareModelIDs`,
`provider.SetBareModelIDs`), off by default. On, `models` lists every row
it listed before, unchanged and first, then one row per bare model id
(`provider.BareEntries`, [`internal/provider/bare.go`](../../internal/provider/bare.go)):
the row of the entry that id reaches, with its label, under the bare id.
`GET /v1/models/{id}` answers a bare id the same way (`provider.BareEntry`).

- Which entry: the gateway's own resolution, so the list never offers what
  a request would not reach. A found or user group the id names (`groupForIn`,
  as `GroupFor`) gives the group's row; else `resolveIn` (as `Resolve`)
  gives the first provider in the Providers order that serves it. So a model
  several providers serve is listed once, and answered by its group with
  found groups on, else by the first provider, as before.
- An id already in the catalog as is (a group's or a provider's own id) is
  not listed twice. Group rows themselves add nothing.
- The target must be in the list shown: a gateway key held to some models
  sees only the bare ids that reach one of its models, so a key held to
  `b/*` doesn't see `glm-5.3` that would go to `a`.
- Never for another magpie (`DrawersHeader`), whose remote provider would
  list each model twice, nor for Claude Desktop's list, which has its own
  shape.
- No agent file changes: magpie still writes `provider/model` ids
  (`magpieModels`), so turning it on or off rewrites nothing.
- Tests: `TestBareModelIDsReporterCase` (Codex `gpt-5.6-sol` listed bare and
  answered on Chat, Responses and Messages, the list unchanged when off),
  `TestBareModelIDsShared` (several providers, found groups on and off, a
  held key, another magpie) in
  [`bare_ids_test.go`](../../internal/gateway/bare_ids_test.go),
  `TestBareModelIDsSetting` in `internal/gui`, and
  `internal/gui/tests/bare-ids.test.cjs`.
- An image a caller names by URL that magpie downloads itself (an `/v1/images/edits` or `/v1/images/generations` reference image, for an images API that takes files, Gemini's own API or Code Assist: `fetchPicture` in [`draw.go`](../../internal/gateway/draw.go)) is downloaded from public addresses only (`publicClient` in [`image_fetch_guard.go`](../../internal/gateway/image_fetch_guard.go)). Every address the host resolves to must be public (`publicAddr`: not loopback, RFC 1918, fc00::/7, link-local with 169.254.169.254, CGNAT 100.64/10, unspecified, multicast, documentation, reserved, Teredo, nor an IPv4-mapped, NAT64 or 6to4 form of one), and the request goes to the address checked, so a name that resolves elsewhere the second time changes nothing; a direct connection is checked again on the address dialled (`privateDialer`). Through a proxy the proxy is sent that address, never the name (an `https://` CONNECT or SOCKS keeps the name for TLS and Host; a plain `http://` URL through an HTTP proxy is asked for by the address in Host too). Each redirect, up to 5, is checked the same, and what comes must sniff as an image. A request from this computer (`local`: loopback, not through a proxy or tunnel, and not from a web page, `fromBrowser`) may name a private address, since its sender reaches it already and a local agent may serve its images on localhost; one with a gateway key from elsewhere may not. A URL left for the vendor to fetch (a chat model's message) is the vendor's to fetch, and an image the vendor itself answers by URL is downloaded as before (`FetchImage` with the gateway's client).
