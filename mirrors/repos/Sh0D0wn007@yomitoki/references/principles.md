# 可読性の判断基準

特定の言語の作法を全言語の必須ルールにはしていない。例はこのスキル用に作成したもの。

## 1. 理解しやすいコード

読み手が目的・入力・出力・例外を短時間で説明できるかを見る。短い一行でも、複数の判断や副作用が詰まっていれば分ける。明快な一行を行数のためだけに分けない。

## 2. 名前に情報を入れる

- `data` や `result` で何を表すか分からないなら、`activeReservations` や `totalPrice` のように実体や役割を示す。
- `tmp` は一時保管そのものが役割で、短い範囲で理解できるときに限る。単純なループの `i` は無理に長くしない。入れ子のインデックスは `rowIndex`、`columnIndex` などで区別する。
- 単位や状態が誤用を防ぐなら、`delayMs`、`sizeBytes`、`escapedHtml` のように名前へ含める。型名を機械的に付け足さない。
- スコープが広い名前ほど文脈を含める。既に文脈が明らかな名前からは重複した語を削る。
- 大文字小文字や接尾辞はプロジェクトの規約に従う。特定の言語の命名例を他言語へ強制しない。

## 3. 誤解されない名前

上限・下限は `max`・`min`、両端を含む範囲は `first`・`last` などで意図を示す。`begin`・`end` が半開区間を表すかは、その API の契約を確認する。名前変更と一緒に比較演算子を変更しない。

真偽値は `is`・`has`・`can` などで問いを表す。否定を重ねる名前を避ける。関数名から読み手が期待する取得・更新・計算の意味や処理コストにも注意する。

## 4. 配置と一貫性

似た処理は似た形にし、対応する引数・項目の順序をそろえる。空行で検証・計算・保存などの意味のまとまりを分ける。

手動の列合わせより既存のフォーマッターを優先する。順序が副作用や契約に関わる処理は、見た目のために並べ替えない。

## 5. コメントが必要な場所

コードの読み上げや、曖昧な名前の埋め合わせは避ける。代わりに名前や構造を直す。

コメントには、選択の理由、変更できない制約、意外な挙動、定数の根拠を残す。全体像がコードから分からない場合に概要を書く。ファイルや関数すべてに説明を追加しない。既存の TODO は意味を理解して保ち、推測で欠陥を書き足さない。

## 6. 正確で簡潔なコメント

「これ」「それ」の参照先が曖昧なら対象を明示する。契約や境界を説明するときは、読み手が判断できる具体例を選ぶ。変更したコードとコメントの矛盾を残さない。

意味不明な位置引数は、既存 API が許すなら名前付き引数や説明変数で示す。インラインコメントはそれでも説明が必要な場合に使う。意味を明らかにするだけのために公開 API を変更しない。

## 7. 自然な制御フロー

通常は変化する値を左、比較対象を右に置く。ヨーダ記法を一律には推奨せず、言語の慣習とプロジェクトの規約を優先する。

肯定形、簡単な条件、主処理を読みやすく配置する。ただし早期 return のガードは否定形でも自然なことがある。簡単な値の選択には三項演算子が適し、多段の条件や副作用があるなら if/else を検討する。

```ts
// 変更前
if (account !== null) {
  if (account.enabled) {
    return account.displayName;
  }
}
return "Guest";

// 変更後
if (account === null || !account.enabled) return "Guest";
return account.displayName;
```

これは通常のデータオブジェクトを想定した例。早期 return や continue は後続処理を飛ばさないか確認する。do/while は最低一回の実行という契約が必要なら残す。構文の禁止自体を目的にしない。

## 8. 大きな式を分ける

説明変数で業務上の判断に名前をつける。

```ts
const isPublished = post.status === "published";
const hasStarted = post.publishedAt <= now;
const hasNotExpired = post.expiresAt === null || post.expiresAt > now;
return isPublished && hasStarted && hasNotExpired;
```

この例は副作用のない通常のフィールド参照を想定する。関数呼び出しを短絡式の外へ出すと、元は実行されなかった処理まで実行されることがある。評価回数と順序を保つ。

ド・モルガンの法則は否定の整理に使えるが、変形後が読みやすい場合だけ採用する。複雑な否定は、意味のある肯定形の名前で説明できないか検討する。

## 9. 変数の追跡を減らす

不要な中継変数、途中結果、制御用フラグを減らす。宣言は使用箇所の近くに置き、可能なら一度だけ代入する。

説明変数と一時変数を区別する。一度しか使わなくても、単位変換や判断の意味が伝わる変数は有益。インライン化で処理が重複したり評価時点が変わったりしないか確認する。

## 10. 下位問題を分離する

主処理の目的を隠している日付整形、解析、集計などは、独立した入出力と意味のある名前を持つ関数にできるか考える。

抽出先を読むための往復が増えるだけなら、その場に残す。一度しか使わない関数でも責務の区切りを明らかにするなら有益だが、将来の再利用を理由に汎用ライブラリを作らない。

## 11. 一度に一つのこと

関数に検証・取得・変換・永続化などが混ざっていたら、役割を列挙して意味のまとまりを作る。空行や順序の整理で足りるか、関数分割が必要かを判断する。

単純な処理を細切れにせず、トランザクション、エラー処理、資源の寿命といった一緒に読むべき処理の境界を保つ。

## 12. 説明とコードを対応させる

同僚に説明するつもりで動作を言葉にする。説明中の概念が、変数名・関数名・処理順序に現れているか確認する。説明が複雑なら、仕様そのものが複雑なのか、実装が目的を隠しているのかを分ける。

## 13. 必要なコードだけにする

既存関数や標準ライブラリで明快に表せるなら使う。重複は同じ意味と変更理由を持つか確認してから共通化する。

未使用コードは参照、動的呼び出し、外部利用を確認してから削除する。「短くする」を理由に機能を削ったり、プロジェクトを分割したりしない。それらは別途依頼と根拠が必要な変更。

## 14. 読みやすいテスト

テスト名に状況と期待結果を示し、必要な性質が分かる最小の入力を使う。準備・実行・確認の流れと、失敗時に原因を特定できるアサーションを保つ。

一行化を目標にしない。過度なヘルパーや共通 fixture で重要な入力と期待値を隠さない。テストの整理でケースやアサーションを削減しない。公開挙動を検証し、リファクタリング後の内部構造へ過度に依存させない。
