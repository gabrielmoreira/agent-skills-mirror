# 状态与规则

解决“这一局要记住什么、什么会变、不确定性如何变成后果”。世界与角色见 `world-and-cast.md`，未来安排见 `planning-and-scenes.md`。

## 先判断要不要状态系统

状态系统是可选模块。不是每个游戏都需要一张角色面板。

需要状态，通常因为：

- 有跨回合保留的资源、关系、伤势、进度、库存、势力态度或已知信息；
- 这些值会改变玩家的选择，或玩家看到它们后会改变策略；
- 玩家会问“我现在有多少/他还信我吗/还剩多久”，而这些不能只靠正文记忆。

不需要状态，通常因为：

- 短局、纯对话或一次性场景；
- 后果可以由正文和既有 canon 自然承接；
- 没有任何决定会读取这个值；
- 加了字段只会增加记账负担，不会增加取舍。

如果只是“看起来像个游戏”，不要加状态。状态的价值是让玩家做有信息的决策，不是让界面更像 RPG。

## 从决定反推字段

先列玩家会反复做的 3–5 类决定，再问每个决定需要什么信息。

```text
玩家会做的决定：
1.
2.
3.

每个决定需要知道：
- 哪个值会变？
- 谁会读它？
- 如果它不变，玩家会少做什么选择？
```

字段契约：

```text
字段：
类型 / 范围：
它影响哪个决定：
谁会读它：
初始值：
更新触发：
更新方式（replace / delta）：
归零 / 满值 / 边界时发生什么：
是否对玩家可见：
```

如果找不到“读取它的决定”，删掉。找不到“更新触发”，说明它还不是状态，只是设定。

## 字段设计

### 类型选择

Denova 的状态字段支持：

- `number`：资源、信任、进度、时钟段数；需要 `min`/`max` 或容量字段时写清楚。
- `string`：当前地点、当前事件、称号、状态描述；不要用字符串装多个资源。
- `bool`：是否感染、是否暴露、是否拿到钥匙；只用于二值事实。
- `enum`：关系阶段、阵营、天气、任务状态；选项要穷尽且稳定。
- `object`：一组相关字段，例如基地、当前副本；不要把所有状态塞进一个 object。
- `list`：已掌握证据、持有物品、当前目标；需要明确“何时增删”。

### 原则

- **少而可读**：优先 5–15 个真正会被读取的字段；主角、重要角色、故事状态分别只保留必要的。
- **不要默认六维/HP/MP/AC/DC**：只有实际规则需要时才加。没有战斗轮的游戏不需要生命值；没有等级的游戏不需要等级。
- **数值要有边界**：`min`/`max` 或独立容量字段；当前值不能超过容量；容量变化时同时调整当前值。
- **关系要分维度**：关系类型（陌生/熟人/盟友/恋人/敌人）、关系阶段、好感/信任/恐惧/亏欠是不同维度；不要用一个数字代表所有关系。
- **状态要写更新指令**：`description` 说明“是什么”，`update_instruction` 说明“何时变、怎么变”。只写“好感度”不够。
- **不要把稳定设定塞进状态**：身份、性格、长期关系、世界规则属于 Lore。
- **不要把状态塞进资料**：当前伤势、当前位置、临时目标属于 State。
- **不要让状态重复叙事**：状态是当前投影，不是章节摘要；正文已经说清的细节不需要再记一遍。

### 可见性

Denova 的状态账本会出现在故事舞台（可收起，也可设为仅导演视图）。默认按“玩家能看到”来设计：

- 如果玩家看到这个值会改变决策，它适合做状态；
- 如果这个值必须隐藏，不要放进 Actor State；放 Lore/Planning，或用正文暗示；
- 如果玩家看不到它，却要求玩家基于它做精确决策，这是不公平的；
- 状态名称、数值和边界要能被玩家理解；不要用只有作者懂的缩写。

### 初始值

- 开局必须给所有必填字段具体值；不要用空字符串、`unknown`、`pending` 占位。
- 不同开局可以有不同初值；开局文本要与初值一致。
- 模板默认值只描述“创建时”，不是当前值；不要用默认值覆盖已经发生的事实。
- 开局已建立的关系、资源、位置要写进初值；不要等第一回合再补。

## 状态边界

| 内容 | 放哪 | 判断 |
| --- | --- | --- |
| 身份、性格、长期关系、能力体系、世界规则 | Lore | 去掉当前场景仍然成立，后文会反复引用 |
| 当前位置、时间、伤势、资源、关系阶段、已知信息、时钟 | State | 只对当前进度成立，下一回合可能改变 |
| 未来可能、NPC 议程、揭示时机、候选场景 | Planning | 还没发生，属于未来意图 |
| 已完成回合、正文事实 | Story 历史 | 已经发生，供连续游玩回看 |

- 永久变化（角色死亡、世界被毁、身份公开）用状态归档/世界状态或规划记录；不要静默改写 Lore 来“追上”当前剧情。
- 临时变化只进状态；不要每章都改 Lore。
- 同一事实不要同时出现在两层；冲突时以已确认正文和作者确认为准，并修正另一边。
- 不要让状态承担“作者笔记”的功能；作者备注放故事简介/创作说明，不进入玩家可见账本。

## 更新纪律

- 只根据本回合已经建立的事实更新；不要预支未来，不要用计划当既定事实。
- `replace` 写完整新值；`delta` 只用于已有数字；不要把缺失值当 0。
- 不要每回合重复提交未变化字段；不要静默重置；不要让数值自己“回到默认”。
- 状态变化要能被正文解释；不要让账本和叙事打架。
- 归档只用于确认死亡或永久离场；恢复只用于真正回归；不要用生命值或措辞推断。
- 一回合结束时只保留“下一回合马上要用”的当前事实；不要把整章摘要塞进状态。
- 如果一次变化影响多个字段，按因果一起更新；不要只改一个数，留下互相矛盾的其余字段。

## 状态规模

| 规模 | 建议字段数 | 说明 |
| --- | ---: | --- |
| 短局/一夜 | 0–5 | 可能只需要位置、一个压力时钟、一个关键关系 |
| 中局/一章 | 5–15 | 主角资源 + 2–4 个关系/时钟 + 已知信息 |
| 长局/连载 | 10–25 | 分主角、重要角色、故事状态、世界实体；仍然只保留会被读取的字段 |

字段多不等于游戏深。一个 8 字段但每个都影响选择的状态，通常比 30 个没人读的面板更好。

## 成长体系与金手指

如果游戏有境界/等级/职业/血统/系统/主神空间，先读 `web-novel-patterns.md` 的「成长体系」「金手指」，再决定状态字段。阶段名称、能力边界、社会意义、突破条件主要属于 Lore/规则设计；状态只记录当前会变化、会被读取的部分：

- 当前阶段/等级/境界，以及突破进度或瓶颈资源；
- 已获得的功法/技能/装备/异火/鬼眼等 build，以及它们的次数/冷却/污染/代价；
- 金手指的充能、冷却、暴露度、债务或反噬；
- 已解锁的权限、地图、机构地位、名声/贡献中会直接影响行动的部分；
- 基地/团队/副本的当前状态：基地资源与维护、队伍信任/分工、副本时限/任务/规则。

不要把所有成长内容塞进一个 `object` 或一段文字。阶段能力边界放 Lore，当前数值/状态放 State，未来突破计划放 Planning。基地、团队、副本也按同样原则拆分，不要用一个“大状态”代替多个会被单独读取的对象。

## 规则：何时启用

规则是可选模块。它适合：

- 行动有不确定性，失败有有意义的后果；
- 玩家能理解赌注和风险；
- 类型需要（生存、战斗、调查、策略），或需要公平/可审计；
- 规则能制造取舍，而不是只增加随机。

不适合：

- 纯叙事、关系对话、玩家无法理解难度的场景；
- 失败只会让故事停住；
- 规则只是“看起来像游戏”，但不改变选择；
- 每次行动都要掷骰，导致节奏碎裂。

Denova 当前的固定判定使用 d20；如果故事不启用固定判定，就直接按 fiction 裁定，不要假装有骰子。具体资源字段、难度档位和状态绑定写法按 `configuration` Skill 的规则系统参考执行。

## 判定设计

```text
检定名称：
触发（何时需要掷骰）：
不检定（何时直接裁定）：
赌注（失败会失去什么）：
难度依据（fiction anchors，不是固定数字）：
结果带（大成功 / 成功 / 失败 / 大失败）：
代价 / 推进（fail forward）：
状态绑定（可选；只绑定会反复读取的数值）：
```

### 触发与不触发

- 只在“有不确定性 + 有有意义后果”时检定。
- 普通观察、短距离移动、已知信息交流、没有代价的尝试，直接裁定。
- 玩家提出足够合理、资源足够、没有阻力的方案，直接成功；不要为了戏剧性强行掷骰。
- 检定前先说清赌注和风险；不要掷完再解释。

### 难度

- 难度来自 fiction：准备、工具、信息、时间、环境、对手、代价。
- 默认难度是“正常”；有利条件降一档，不利条件升一档；不要凭感觉加数字。
- 玩家应能大致判断风险；如果难度不可理解，先补充可观察的线索，而不是加隐藏修正。
- 同一个行动不要连续检定；一次检定应推进到一个新局势。

### 结果带

- 大成功：达成目标，并获得额外信息/资源/位置优势；不要跳过整个篇章。
- 成功：达成目标，但保留代价、压力或新问题。
- 失败：不达成目标，但改变局势：时间、位置、资源、关系、警戒、线索质量。
- 大失败：失败 + 明显恶化；不要用“搞笑事故”消解严肃后果，也不要把故事直接终止。

### 失败推进

失败应该回答“现在更糟/更复杂/更贵了，但接下来能做什么”。可用的代价：

- 时间：时钟推进、敌人先行动、机会窗口关闭；
- 位置：被逼退、被包围、失去有利地形；
- 资源：消耗、损坏、被夺走；
- 关系：怀疑、债务、承诺破裂；
- 信息：得到不完整/误导/带噪音的线索；
- 威胁：警戒升级、敌人增援、环境恶化。

“失败即卡死”只适合有明确替代路线的探索型玩法；如果不确定，优先 `fail_forward` 或 `success_at_cost`。

## 规则风格

| 失败策略 | 适合 | 注意 |
| --- | --- | --- |
| `fail_forward` | 冒险、调查、叙事驱动 | 失败必须带来新局势，不能只是“没做到” |
| `success_at_cost` | 电影英雄、戏剧张力、关系冲突 | 成功也要付代价，避免高光变成无风险 |
| `blocked` | OSR、谨慎探索、解谜 | 必须准备替代路线，否则一次失败会卡死 |
| `hard_failure` | 硬核生存、资源压力 | 后果要具体、可预期，不要突然惩罚 |

规则风格要服务体验：

- 调查游戏不要让核心线索因失败消失；
- 生存游戏不要让失败没有资源后果；
- 关系游戏不要让一个骰子决定爱不爱；
- 英雄游戏不要让普通失败打断高光；
- 策略游戏不要让随机盖过准备。

## 状态绑定

状态绑定只用于“会反复读取的数值效果”，例如：

- 信任影响交涉难度；
- 疲劳影响体力检定；
- 警戒影响潜行；
- 资源不足影响交易/制作。

不要把每个字段都绑定；不要把叙事状态（“他害怕你”）硬算成数字；不要让绑定替代 fiction 判断。具体绑定字段、修正和结果变化按 `configuration` Skill 的规则系统参考执行。

## 常见错误

- 状态字段没有读取者，或没有更新触发。
- 状态与 Lore 重复；当前变化被写进资料，稳定设定被写进状态。
- 字段太多，玩家/模型都不知道该看哪个。
- 隐藏状态却要求玩家做精确决策。
- 关系用一个数字代表全部维度。
- 数值没有边界，或当前值超过容量。
- 开局用占位值；第一回合才发现字段没初始化。
- 为一切掷骰；失败即停；难度不透明；规则与世界观冲突。
- 状态每回合大幅波动，或静默重置。
- 归档/恢复被滥用，角色死了又回来，或离开的人还在状态里。

## 检查清单

- 是否真的需要状态？如果删掉所有字段，游戏会失去什么选择？
- 每个字段是否有一个明确的读取者和更新触发？
- 字段是否少而可读？能否合并重复维度？
- 关系是否分了类型、阶段、好感/信任等必要维度？
- 数值是否有边界/容量？边界时会发生什么？
- 开局是否给了具体初值？是否与开局文本一致？
- 玩家能看到的状态是否足以做有信息的决策？
- 隐藏信息是否放对了层，而不是塞进状态？
- 是否只根据已建立事实更新？有没有预支未来/静默重置？
- 规则是否只在“不确定 + 有意义后果”时使用？
- 失败是否改变局势，而不是停住？
- 规则风格是否匹配题材和玩家预期？
- 状态绑定是否只用于反复读取的数值效果？
