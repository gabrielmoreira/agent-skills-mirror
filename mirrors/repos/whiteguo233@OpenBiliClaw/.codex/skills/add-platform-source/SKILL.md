# Add Platform Source

Treat `docs/platform-source-integration.md` as the repository authority. First read its execution protocol, source-contract, testing, E2E, completion, and failure-mode sections; then read each capability section selected by the frozen contract before implementing it. Before reporting completion, read the whole guide once as an omission audit. Keep implementation detail there instead of duplicating it in this entry skill.

## Operating protocol

1. Declare the integration level: `full`, `discovery-only`, `capability-increment`, or `audit-only`. Plain “add a source” means `full`. Isolate the work in a dedicated worktree, record the baseline, and prove that Python imports, CLI commands, backend data roots, and extension builds resolve to it.
2. Mine the current code, `git log --all`, relevant GitHub PRs/issues, and available local Codex sessions for both the analogous platform's first integration and its follow-up repairs. Treat sessions as leads, verify every lesson against current code/tests, and never copy credentials or secrets.
3. Freeze the source contract before editing. Give every row two independent fields: applicability (`required` or `N/A`, with evidence and a contract test where technically enforceable) and execution (`PASS`, `FAIL`, `NOT_RUN`, or `BLOCKED`). An external mutation that was not requested uses explicit scope/authorization evidence instead of a fake test. `deferred` is `NOT_RUN`, never `N/A`; implementation without the required proof is not `PASS`.
4. Choose references per capability instead of cloning one platform wholesale: auth, transport, browser tasking, bootstrap, discover, storage identity, UI, and release may each need a different precedent.
5. Implement and verify vertical slices in dependency order: canonical registry/contract, transport and normalization, task/event/bootstrap, formal discover/eval, config/status/init, user surfaces, then docs/release.
6. Run the repository Python 3.11+ interpreter as `PYTHONPATH="$PWD/src" "$SOURCE_SKILL_PYTHON" scripts/audit_platform_source.py --contract <contract> --check --json`, then an independent omission review against the raw contract, current diff, and real artifacts. The audit detects wiring evidence, not semantics; do not leak suspected answers into the review prompt.
7. Fill `docs/platform-source-acceptance.example.md` with unit proof, built-artifact proof, safe real E2E, state-changing E2E authorization, intentional exclusions, and blockers. Only all-required `PASS` earns `complete`; otherwise report `incremental only` or `blocked`.

## Non-negotiable gates

- Treat a source as an end-to-end product path, not a fetcher. Register canonical slug/aliases/hosts, source policy, auth/status, config, init, discover, storage identity, recommendation surfaces, tests, docs, and release claims, or record a tested exclusion.
- Classify auth as anonymous, login-required, anonymous with optional credentials, or capability-specific. If public discover and private bootstrap/incremental need different auth, freeze the per-capability matrix and extend the shared backend contract before source code; never force the difference into one boolean or client-side guards. Keep observed identity separate from verified identity, let authoritative current failure override stale positive hints, and keep account resolution and admission backend-owned.
- Preserve credential patch semantics everywhere: omitted keeps, explicit empty clears where supported, and masked never overwrites. Show successful 2xx warnings and stored/rejected credentials even while a source is disabled.
- Normalize real upstream envelopes defensively. Use namespaced stable item keys, universal `author_name`, authoritative publication time only, explicit engagement availability, and real counterexamples for placeholder filters; never derive platform time from discovery time or stringify arbitrary nested values.
- For browser tasks, gate capability/presence and acquire the local cross-source mutex before claim; enforce a backend atomic lease across extension instances; preserve first-final-wins staged replay, backend-owned scope caps, and bounded durable recovery. A zero-row result is `empty` only with affirmative valid-empty evidence; partial, login wall, challenge HTML, missing bundle, timeout, or unobserved response is degraded/failed and must preserve accepted rows.
- Prove task-mode isolation across real redirects/SPA navigation, prevent passive behavior capture, prefer inactive tabs when viable, and restore the user's tab when foreground execution is unavoidable. Verify the installed worktree build, both Chrome and Firefox assets, MAIN-world `document_start` ordering, and early-response replay when used.
- Keep smoke paths non-mutating beyond explicitly declared diagnostic/task records. Safe actions use the shared read-only grammar plus an exact `upstream-state-unchanged` machine assertion; free text never authorizes an upstream write. Isolate storage and classify every task/result, seen, affinity, snapshot, schedule, event-ingress, memory, and profile sink.
- If account signals contribute to a profile, either wire post-init incremental refresh through shared atomic admission, stable identity, bounded seen state, and durable ingress, or label and test the source as init-only/on-demand.
- For search-capable sources, wire both keyword-generation tracks and `KeywordFetchCoordinator.claim(<slug>)`, propagate `source_keyword_id`, preserve transactional rollback, and use the shared admission/source-share policy. Do not confuse scheduler execution with productive supply.
- Validate every user-facing surface: setup, desktop, mobile, extension, CLI, source status, source share, recommendation filters/cards/actions, and live convergence after credential/login changes.
- Use the user's configured LLM/embedding providers for eval/profile E2E. Keep safe E2E separate from state-changing like/favorite/follow/save/upvote actions, which require explicit authorization or a test account.
- Do not claim completion until focused and full backend gates, extension tests/typecheck/build/asset verification, relevant real E2E, documentation, and release-readiness checks have recorded evidence. Commits, version bumps, tags, pushes, marketplace uploads, releases, and upstream account mutations require explicit user authorization.
