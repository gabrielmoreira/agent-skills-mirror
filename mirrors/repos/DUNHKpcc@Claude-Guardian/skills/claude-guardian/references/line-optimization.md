# 线路优化：Agent 如何帮用户的机器优化线路

依据 [R02：VPS 线路优化与家宽中转教程](../sources/R02-vps-line-optimization.md)，回答线路优化问题时必附。适用对象：**VPS 路线的开发机**（见 [vps-guidance.md](vps-guidance.md)），以及**本机路线里自建梯的 VPS 节点**（见 [egress-ip-options.md](egress-ip-options.md)）。

**总原则（R02）：先选好线路，再考虑中转，最后按需要调整 TCP 和桌面画质。每次只改变一个因素。**对 Claude 浏览器和远程桌面，关注晚高峰连接稳定、操作响应及时、实际出口符合预期，而不是一次测速跑多高。

## Agent 的工作方式

线路优化会改用户机器上的东西，所以 Agent 按固定流程做，并按[授权档位](authorization-tiers.md)分工：只读诊断是 A 档，范围确认后自行做；SSH 转发、noVNC 入口、Realm 中转、临时切 BBR 是 B 档，合成一张计划批准一次，Agent 连续执行并可在计划范围内按环境调整参数；持久化 BBR、改 SSH 或防火墙使自己可能失联是 C 档，当场确认。流程是“先看、再说明、再批准、再改、再验证、可回滚”：

1. **绑定目标：**确认是哪台机器（A 优化线路机、B 家宽出口机，还是单台 VPS）、用户是谁、用途。Agent 在用户授权的 SSH 会话里操作，或者由用户自己运行、Agent 只给命令和解读，两种方式都可以，由用户选。
2. **只读诊断：**先收集现状，不改任何东西（见下一节）。
3. **出变更卡或计划：**B 档的各项合成一张计划，每项写清目标机器、原值→新值、影响、回滚命令、怎么验证，用户批准一次；C 档的每项单独出确认单。仍然**一次只改变一个因素**：计划里的各项按顺序做，每项做完立刻验证，再做下一项。
4. **执行并验证：**只执行这一项，立刻用同一方法复测，对比前后。
5. **记录与回滚：**保留原值和回滚方式；效果不好就按卡片回滚，再决定下一项。

**前提：**目标机器有云控制台的独立救援入口；动手前先打快照；改动 SSH、防火墙、转发前先有第二个会话保持连接。Agent 不在没有救援入口时改网络。

## 第一步：按现象定位要优化什么（R02 一、八）

| 现象 | 优先处理 | Agent 先查什么（只读） |
| --- | --- | --- |
| 晚上直连慢、绕路、频繁断流 | 换适合本地运营商的线路，或增加中转 | 对比常用时段（晚高峰）直连与中转的延迟、丢包 |
| 小流量正常，大文件传输效率差 | 检查方向差异、重传，再考虑 TCP 拥塞控制 | 当前拥塞算法和队列（见 BBR 一节），两个方向分别看 |
| 下载一跑满，桌面就卡 | 给下载限速、留带宽余量，必要时处理排队 | 是否有大流量任务占满，队列配置 |
| 桌面能用，但网站看到的 IP 不对 | 配置浏览器的出站代理 | 程序实际运行在哪台机器、代理配在哪里 |
| 画面卡，CPU 同时很高 | 降低分辨率和画质，检查浏览器与桌面负载 | CPU、内存、浏览器进程 |
| A 正常，A 到 B 特别慢 | 检查两机互联及方向差异；有 IPv6 时比较该段 IPv4 与 IPv6 | 两机间两个方向的实际 TCP 表现 |
| Ping 好看，业务依然慢 | 看实际业务吞吐与重传，不用 Ping 代替业务结果 | 业务吞吐、重传 |
| 出口没有变化 | 检查代理配置在本地、A 还是容器，浏览器是否实际使用 | 代理入口、浏览器代理设置 |

**注意（R02）：BBR 调整 TCP 拥塞控制，不能把普通线路变成 CN2 GIA；更换 DNS 也不会替换运营商的国际路由。**Agent 不向用户承诺“优化后一定更快”，中转收益取决于两段连接，不能保证加入 A 就一定更快。

## 第二步：决定搭配方案（R02 三、综合评价）

**已有一台好用的家宽机，就先直连；直连确实拖慢使用，再增加优化线路机。**两机方案里，A 负责连接与计算，B 负责出口。

- **方案 A：浏览器放在 A，网站请求从 B 出去。**本地电脑 → 远程桌面 → A（浏览器）→ 加密连接 → B（家宽出口）→ 网站。适合要远程桌面连接稳定、同时用固定家宽出口。浏览器运行在 A，必须在 A 的浏览器里配置通往 B 的代理。
- **方案 B：浏览器或服务放在 B，A 只做中转。**本地电脑 → A（端口中转）→ B（桌面或服务）→ 网站。适合 B 已有可用桌面或服务，但本地直连 B 较差；B 要承担浏览器和桌面的计算负载。

链路示意（R02）：单端中转由 realm 透明转发，业务协议自己加密、出口机解密；双端隧道在中转机和出口机之间多套一层加密。

![单端中转](../sources/R02-images/single-relay.png)

![双端隧道](../sources/R02-images/dual-tunnel.png)

**把连接桌面的入口转发了，不等于把浏览器的出口改了。**先确定程序运行在哪台机器，再决定在哪里配置出站。

选机时按顺序：确认本地运营商和目标地区；看对应套餐、同机房的路由资料，优先看自己常用时段；有两台机器时同时看“本地 → A”和“A → B”，增加一跳后仍要有收益；核对两台机器各自的流量计费方向、可用端口和剩余流量。三网优化要分别核对电信、联通、移动，去程、回程和 IPv4、IPv6 也分开判断。候选机器见 [VPS 推荐报告索引](../sources/vps-recommendations/INDEX.md)。

## 第三步：逐项应用（每项一张变更卡）

下面命令里的大写占位项要换成用户自己的信息，不要连尖括号一起执行。每一项执行前都要用户批准，执行后立刻验证。

### 3.1 用 SSH 连接家宽出口（方案 A，推荐入门）

前提：A 已有浏览器，B 的 SSH 可以从 A 访问并允许 TCP 转发。

1. **在 A 上建立 SOCKS5 入口**（在 A 的终端执行，前台运行，`Ctrl+C` 停止，不含开机启动）：
   ```
   ssh -N -D 127.0.0.1:1080 -p B_SSH_PORT \
     -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
     B_USER@B_IP
   ```
   首次连接核对 B 的主机指纹，指纹不明就停下，不关闭主机密钥检查。
2. **在 A 的浏览器里设置代理：**类型 SOCKS5，地址 `127.0.0.1`，端口 `1080`；浏览器支持时启用通过 SOCKS5 解析域名。这里的 `127.0.0.1` 指 **A 自己**；浏览器在容器里时，容器的本地地址指向容器，要另行配置可达的代理地址。
3. **验证出口：**在 A 另开终端运行 `curl --proxy socks5h://127.0.0.1:1080 https://api.ipify.org`，返回值应是 B 的预期出口（NAT 产品的公网出口可能与 SSH 入口不同）。再在**已设置代理的浏览器**里确认出口。curl 成功只证明这一条请求走通，不能证明浏览器的 DNS、WebRTC 或其他进程都用同一出口；WebRTC 可用包内的[本地探测页](../assets/webrtc-probe.html)检查。
4. **验收：**以实际网站访问结果为准；IP 标签和解锁脚本不能保证 Claude 账号状态。
5. **回滚：**停掉那条 SSH 进程，浏览器代理设置改回原值。

要让它开机自启、断线重连，需要另外的工具和服务，属于单独一项改动，另出变更卡、另行批准。

### 3.2 Xvfb / noVNC：让桌面连接更轻

假设 A 的 VNC 服务已监听 `127.0.0.1:5901`、已有 noVNC。在 A 的 noVNC 目录启动只监听本地的网页入口：`./utils/novnc_proxy --vnc 127.0.0.1:5901 --listen 127.0.0.1:6080`；在用户自己的电脑建立本地转发：`ssh -N -L 127.0.0.1:6080:127.0.0.1:6080 -p A_SSH_PORT A_USER@A_IP`，然后打开 `http://127.0.0.1:6080/vnc.html`。入口只监听本地、通过 SSH 访问，**不把 5900 和 6080 开放到公网**。

画面设置从 **1280×720** 开始，软件支持时降低画质和帧率上限，关闭不必要的视频和动态背景；这是减少传输量的起点，不是硬件门槛。带宽不足先保留文字可读性。

### 3.3 需要端口中转时：Realm 最小示例（方案 B，或改善 SSH 到 B）

只在 A 安装 Realm（按系统架构选 [Realm 发布版本](https://github.com/zhboner/realm/releases)）。在 A 保存 `config.toml`：

```
[[endpoints]]
listen = "0.0.0.0:2222"
remote = "B_IP:B_SSH_PORT"
```

在该文件所在目录前台启动 `realm -c config.toml`（`Ctrl+C` 停止；同一监听端口不能被其他程序占用）。在 A 的云防火墙和系统防火墙里，**只给用户自己的公网 IP 放行 TCP 2222**。本地连接 `ssh -p 2222 B_USER@A_IP`，最终登录的是 B，主机指纹要核对 B。**普通端口转发本身不提供额外加密**；已有加密业务可以按其协议转发。**回滚：**停掉 realm、删除配置、收回防火墙放行。中转收益取决于两段连接，不能保证更快。

### 3.4 BBR：可选调整，先保留原值（R02 七）

只在用户明确批准、且前面的更值得做的项目已处理后才考虑。

1. **只读查看并记录原值：**`sysctl net.ipv4.tcp_congestion_control`、`sysctl net.ipv4.tcp_available_congestion_control`、`sysctl net.core.default_qdisc`、`tc qdisc show`。**把原拥塞算法记下来**，这是回滚依据。
2. 可用列表里没有 `bbr` 时，可以尝试 `sudo modprobe tcp_bbr` 再看一次；仍没有就**跳过，不为教程更换内核**。
3. **临时切换：**`sudo sysctl -w net.ipv4.tcp_congestion_control=bbr`。它只影响新建的 TCP 连接，已建立的不变。重连实际业务，观察同一用途有没有改善。
4. **效果不好：**把命令末尾的 `bbr` 换回记录的原值。
5. **确定保留、且不存在同名配置文件时才持久化：**`printf '%s\n' 'net.ipv4.tcp_congestion_control=bbr' | sudo tee /etc/sysctl.d/90-vps-bbr.conf`，再 `sudo sysctl -p /etc/sysctl.d/90-vps-bbr.conf`。撤销要删除自己新增的这一文件**并**恢复记录的原算法，只删文件不会立即恢复运行值。
6. `default_qdisc` 和实际网卡队列分开看；多队列设备可能显示 `mq`，虚拟设备可能是 `noqueue`。**已有队列配置（如 CAKE 或其他整形规则）先保留，不直接覆盖。**

## 第四步：验证与记录

- **只做必要验收：**桌面操作顺畅、出口符合预期、常用业务连接稳定。
- **一次只改一个因素**，避免同时换内核、代理协议、DNS 和十几项参数后无法判断原因。
- 每次改动前后保存同一方法的对比，写清时段（晚高峰优先）。
- 排障案例（R02 引用）：终点延迟较低且没显示丢包，实际 TCP 两个方向却差异明显，改用两机间 IPv6 后部分业务恢复。该案例的原因只是推断，**不能推广为所有线路的问题，也不能推导 IPv6 一定更快**。

## Agent 不做的事

- 不默认运行优化：不自动装 BBR、不自动改内核、不跑“优化全家桶”。每项改动都是用户批准的一张变更卡。
- 不同时改多个因素；不在没有救援入口、没有快照时改 SSH、防火墙、转发。
- 不承诺更快或更稳，不把线路优化当成解封或免封的办法；出口 IP 或解锁结果不等于账号状态。
- 不关闭 SSH 主机密钥检查；不把 5900 和 6080 暴露公网；不把端口转发说成加密。
- 带宽和吞吐测试会消耗流量，单独征得同意；R02 里的第三方脚本由用户自己运行。
