# Contact phases and execution boundary

## Built-in capability and independent Agent action boundary

The generic preview supports interview, local read-only metadata where a real adapter exists, and offline plans; it does not execute `probe`, production `apply`, or online `verify`. The separate released `recovery_cli.py` provides scoped read-only POSIX exact-file `reconcile` observations and independent `rollback` / `restore-prepared` operations, each under its current entry-point scope, authorization and receipt/conflict checks. Recovery writes additionally require established writer exclusion and exact operation approval; read-only reconciliation does not require writer exclusion. See [the recovery procedure](host-libraries.md#prepared-recovery). That capability does not open production native repair or network/contact gates, and does not establish Windows recovery, application reload or effective routing. Explicit authorization alone does not turn an unsupported built-in action into a validated adapter. When a built-in cannot repair the problem, the Agent continues scoped investigation of the actual environment. A separately reviewed, specifically authorized minimal operation may use available host tools, exact configuration edits, or a reviewed temporary script, with backup, conflict checks, recovery and real re-detection. This is an independent Agent action, not permission to replace authorization callbacks, spoof native acceptance, or bypass a built-in denial. Hand off only concrete steps that require the user or cannot be safely performed with available tools.

These are workflow controls, not a firewall. The preview does not stop unrelated apps, restored browser tabs, or user activity, and cannot erase prior contact. Record known existing contact; do not claim an untouched environment. Strict no-egress requirements remain blocked without a tested technical boundary.

## Phase contract

- **PC0 / precontact:** interview, existing local metadata, packaged source snapshots, and offline plans. No requests to Claude/Anthropic web/API/auth/download/status/telemetry/documentation, including DNS, search-mediated fetch, HEAD, ping, client version/doctor commands, IDE extensions, or delegated Claude agents. Current external facts remain pending verification. Previously installed client metadata may be inspected without executing the client.
- **PC-G1:** preparation evidence for the actual target, browser/profile, path, address families, and required controls. List every unavailable or unmeasured requirement. A successful inventory, imported assertion, or synthetic test cannot close this gate. Do not require irrelevant client checks, but do not silently waive a strict user requirement.
- **PC1:** only after sufficient scoped PC-G1 evidence and explicit first-contact authorization. The handoff names target, action, destinations, configuration revision, evidence, and limits. The built-in preview does not execute that handoff. Any independent Agent operation still requires these exact contact conditions and host policy permission. Installation may trigger background startup and is contact. Current rules and compatibility are rechecked here before account actions.
- **PC-G2:** real client evidence. Separate unauthenticated tests from tests that require login; defer the latter explicitly rather than inventing success or creating a circular login requirement.
- **PC2:** separately authorized official login/subscription and subsequent client verification. Login is not payment authorization. A real-path failure pauses payment and returns to diagnosis.

Existing subscribers follow the same scoped preparation/contact distinction without pretending this is their first-ever service contact. Phones used for payment need their own preparation; a Mac check cannot pass a phone. Host, guest, remote server, browser profile, and client evidence remain separate.

## Permissions and reporting

**Authorization granularity (owner-confirmed 2026-10-21):** it follows [authorization-tiers.md](authorization-tiers.md): tier A runs inside a confirmed scope, tier B is approved once as a whole plan, tier C needs the user at the decision point. Phrases below and in other references such as "specific authorization" or "per-action approval" are read at that granularity: for tier B, one approval of the plan covers its steps; for tier C, an in-the-moment confirmation. The hard rules in this file (PC0/PC1/PC2, payment and login by the user, no credential collection, host policy first) are not relaxed.

Keep question answers, plan acceptance, host permission, OS privilege, first-contact authorization, and payment authorization distinct. Silence, cancellation, elapsed time, a default option, and accepting a route grant none of the others. User authorization cannot override host policy.

Before an authorized read, bind the target, minimum fields, expected source, timeout, and redaction. Do not scan ports, execute subscription JavaScript, read credential stores, dump `env`, or read all browser profiles. A local API GET can trigger work; the preview does not invent a controller adapter. Permission denied or missing capability is a result, not a reason to elevate automatically.

For active neutral probes, authorization must identify destination/service, protocol, data exposed (including source IP), request budget, path, and purpose. Neutral is not offline. No redirect or subresource may expand scope. The standalone CLI does not open these probes. Host libraries and any independent Agent probe must satisfy the actual runtime, endpoint, authorization and bounded-data contracts; missing or denied prerequisites remain blocked.

An offline change plan contains target binding, observed revision/time, finding and evidence, proposed difference, protected objects, dependencies, impact, validation criteria, rollback limitations, and exact missing authority/capability. Credentials, payments, destructive cleanup, firewall/routing, and remote-control changes require their own safeguards. Never promise rollback for revocation or deletion.

Report `proposed`, `applied`, and `verified` separately. Built-in preview outputs are proposals only. Independent Agent actions report their actual operation and verification evidence separately, without upgrading built-in capability or general native acceptance. User-supplied observations remain reported, not tool-verified. Changed targets/configuration/network/profile/version invalidate affected evidence and handoff scopes. On withdrawal, stop new operations; do not claim already-sent requests were undone.

## Persistence and interruption

Ask before saving a sanitized progress record. Include phase, target alias, route and choice basis, question IDs, field states/sources/times, unresolved items, evidence scope, and deferred post-contact checks. Do not store secrets or identifying paths. Resume only relevant missing items; never revive Q-C07 or apply an old plan to changed targets. If permission, capability, or required facts are missing, stop dependent actions and continue only independent safe work.

An actual interrupted session uses the explicit resume contract in [intake.md](intake.md#interruption-and-resume), before reusing retained facts for personalized planning. Ordinary state deserialization is not a new interruption. Preserve the chosen task route and known contact history; never reset PC2 to PC0 or treat a saved record as renewed permission. A scoped current user report can confirm unchanged conditions or identify only affected fields; it does not redate old observations or establish native verification. Unknown, refusal, or deferral permits limited guidance without repeated review prompts; urgent protective triage remains available. A reported target change requires explicit rebinding or a fresh correction from the user, and completing purchase cannot silently clear it. Review event labels provide retry identity only, not authorization or trusted target identity.
