# macOS DNS、IPv6 与 WebRTC：单机经验的通用提炼

本页是用户提供的 2026-10-18 单机排查记录的脱敏派生参考，不是原稿、通用配置模板或本项目已完成原生验收的证明。只提炼判断方法；不提供新的探测、配置修改或服务访问授权。当前 Skill 的 PC0、目标绑定、权限与能力门禁继续适用。

## 先分清观察、解释与未知

- **来源报告的历史观察**：某次 macOS、Clash Verge Rev / Mihomo、Tailscale 组合排查中，调整解析与路由职责后，浏览器 DNS 检测和限定 HTTPS 样本符合当时预期；独立绑定物理接口的 DNS 与 HTTPS 请求也成功
- **可提炼的判断**：系统实际解析器、核心配置、浏览器解析、地址族和请求路径必须分别核对，不能仅凭一个配置项或检测页标签判定整体状态
- **没有验证**：本项目未重演该次排查；来源没有完成全部 WebRTC/UDP 检测，也没有实际退出代理应用后的生命周期测试。随后系统 DNS 回读发生变化，来源未对变化后的状态重跑完整验证
- **不可推断**：不能据此说明读者或原作者设备当前状态，不能给出绝对无泄漏、服务可用、账号资格或免封保证

## 1. DNS 职责与路径分别记录

先记录操作系统实际选择的解析器、作用域和网络服务，再核对代理核心声明。将普通访问域名、上游解析器域名的引导解析、代理节点域名和私有域名分开。一个层次的查询成功不证明其他层次采用相同路径。

Mihomo 的 `default-nameserver` 用于解析 DNS 服务器域名，`proxy-server-nameserver` 用于代理节点域名；`respect-rules` 让 DNS 连接遵循路由规则，并不强制固定出口。规划时保留无循环依赖的引导路径。见 [Mihomo DNS 配置](https://wiki.metacubex.one/en/config/dns/)。

Fake-IP 映射应与真实上游解析证据分开。获取映射地址本身不能证明请求已到达指定上游；缓存、hosts、浏览器 DoH 与核心解析可能具有不同路径。权威侧关联观察仅覆盖相应查询，不由解析器品牌或地理标签推导完整递归链路。

## 2. 端口 53 接管不是所有 DNS 的覆盖证明

Mihomo 文档说明，`dns-hijack` 未指定协议时默认 UDP；`any:53` 因而不能当成 TCP DNS 接管证据。TCP 匹配须单独核对。文档还明确 macOS/Windows 无法自动劫持发送到局域网的 DNS 请求，不能假设 DHCP 提供的局域网解析器必然进入 TUN。见 [Mihomo TUN 的 dns-hijack](https://wiki.metacubex.one/en/config/inbound/tun/#dns-hijack)。

由这些匹配范围可推知：端口 53 配置也不能单独证明 DoH、DoT 或浏览器自身解析的路径。是否采用这些机制、实际目的地、路由和策略必须另有对应证据；不是看到加密 DNS 就直接认定泄漏或安全。

## 3. IPv6 开关具有不同作用域

`dns.ipv6: false` 表示对 AAAA 记录返回空解析结果，并不等于关闭操作系统接口 IPv6，也不构成所有 IPv6 连接被阻断的证明。见 [Mihomo DNS 的 IPv6 选项](https://wiki.metacubex.one/en/config/dns/#ipv6)。

应分别记录本地接口、应用/TUN 路由、代理外层传输、代理到目标、浏览器候选等作用域。保留 IPv6 依赖的外层连接；不要把单机成功组合写成必须全局关闭 IPv6 的要求。缺少 AAAA、IPv6 请求超时或没有候选均不能证明防绕过成功。

## 4. Tailscale、私有解析与应用退出依赖

Tailscale 接受 DNS 设置与 VPN 连通是不同事项；更改前应明确 MagicDNS、split DNS、exit node 及现有管理策略的影响。官方文档将接受 DNS 设置作为独立客户端选项。见 [Tailscale 客户端偏好](https://tailscale.com/docs/features/client/manage-preferences)。

Quad100 是设备本地 stub 服务，既处理本地名称也可能转发请求；其存在本身不能说明公共查询最终去向。见 [Tailscale Quad100](https://tailscale.com/docs/reference/quad100)。不要复制来源的私有域名、网卡名或接口编号；重连后需重新确认绑定。关闭 DNS 接管不是通用修复步骤，也不能假设私有名称仍可用。

核心 DNS 的回环监听与系统默认 DNS 指向回环是两项独立设置。若系统解析依赖一个可能退出的本地进程，就应明确该进程退出后的恢复机制。换成非回环地址也不自动证明解析可达、隐私合适或已被 TUN 接管。

若私有域名解析依赖代理核心，代理退出后隧道仍在线也不代表私有名称继续可用。需要持续私有解析时，应单独设计并核验系统级分域解析；不得在没有明确许可时更改系统或 Tailscale 设置。

## 5. 验收矩阵：样本不能互相代证

| 验证对象 | 必须绑定的条件 | 不能据此声称 |
|---|---|---|
| 系统解析样本 | 设备、解析作用域、查询类型、时间、配置版本 | 浏览器或核心也采用相同路径 |
| 核心 DNS 样本 | 活动实例、上游职责、缓存/映射限制 | 系统全部 DNS 被接管 |
| 浏览器 DNS/HTTPS 样本 | 浏览器、档案、origin、实际网络路径 | 其他档案、WebRTC 或 UDP 已通过 |
| IPv4/IPv6 样本 | 地址族、进程、入口、路由和时间 | 另一地址族无绕过或已阻断 |
| 物理接口绑定请求 | 测试进程、绑定接口、代理采用情况 | 实际退出代理后的系统生命周期通过 |
| WebRTC 样本 | 浏览器、档案、origin、策略、候选类型、完成/错误 | HTTPS 成功即可证明 WebRTC 安全 |
| 退出/重启回归 | 真正的状态切换、控制通道、恢复条件 | 当前连接正常就说明故障防直连可用 |

WebRTC 的 STUN 与媒体路径可能不同于传统应用代理；限制策略也可能影响媒体质量。应独立评估，而不是为了让检测页通过预先改变候选行为。见 [RFC 8828](https://www.rfc-editor.org/rfc/rfc8828.html)。

本案例的 WebRTC/UDP 与实际退出生命周期必须保持“未完整验证”。独立无登录浏览器的结果也不能替代用户实际档案。受限制网站直连失败与普通互联网连接不可用应分别解释。

## 6. 最小变更、回滚与时效

在未来获准的修复中，先确认目标、版本、活动配置及其持久化归属。隔离测试实例仍可能产生上游请求和端口冲突，不能视为天然离线或获得授权。不要同时改节点、严格路由、系统 DNS、引导解析及内网策略。

修复应给出最小差异、保留项、影响和独立恢复路径。自动回滚需要可靠启动和权限，可能被睡眠、崩溃或其他写入者影响；超时长度应由实际风险决定。不得覆盖后来发生的合法配置变更。确认读回与获准复测后再解除保护，不把回滚脚本存在当作恢复已验证。

持久化源、生成配置与运行时应分别核对；仅修改生成文件可能在重新加载后失效。不要为了检测结果给测试域名添加例外。若另行批准临时比较路径，报告必须标明它与自然路径的差异。

配置、接口、路由、档案或相关策略发生变化后，原成功记录只能说明旧条件；未复测的新状态保持未知。证据应附观察时间、适用条件与尚未覆盖的维度。来源所述后续 DNS 变化正是这种限制的案例，不应被写成当前已通过。

清理测试脚本不撤销持久化配置。清理范围须独立确认，保留正式配置、规则、订阅、数据及控制通道；不能因为文件看似临时就删除其他运维材料。
