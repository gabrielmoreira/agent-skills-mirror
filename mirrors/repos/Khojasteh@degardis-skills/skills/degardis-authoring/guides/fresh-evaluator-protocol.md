---
title: Fresh-evaluator protocol
applicability:
- When the work depends on how a fresh evaluator is run
---

A fresh evaluator coordinates a controlled observation, and the **blind subject** is the agent whose conduct supplies the evidence. The subject is not a delegated worker: it performs the ordinary request being observed rather than a coordinator-defined unit whose return closes part of the evaluator's work. [[principle:authority-before-effect]] governs obtaining the subject and every instance and host effect. If another agent is separately assigned analysis, verification, synthesis, or other coordinator-defined work whose return the evaluator will rely on, [[principle:bounded-delegation]] and [[principle:coordinating-delegated-work]] apply normally. A subject rule under test is observed rather than imposed; the host enforces only the authorized outer boundary.

**Fix two envelopes before a subject exists.** Together they form the completed experimental contract; only the performer envelope is disclosed to the subject. The **control contract**, held by the evaluator in re-readable working state, fixes the ordinary request and sanitized inputs; the artifact's identity as [[guide:artifact-identity]] defines it and where the subject loads it from; the question, claims, acceptance evidence, baseline, interaction protocol, observation and verification protocols, next safe checkpoint, and case dispositions; and every host configuration dimension that could change the answer. It also fixes the authorized **agent topology**: the primary subject count and schedule; the maximum total and simultaneously live subject-obtained instances; their permitted capabilities, instruction sources, reach, effects, spend, and concurrency; how the host enforces and records those bounds; and what establishes that the whole instance tree stopped. Do not launch while any required field, authority, host bound, or observation is missing.

The **performer envelope** contains only what a real performer in the claimed configuration would receive: the ordinary request, the smallest sanitized fixture it needs, its authority and effect boundary in performer-facing terms, and the evaluated-skill pointer and other-skill prohibition required for isolation. Do not reveal expected behavior, source rationale, claims under test, acceptance evidence, evidence standards, special return fields, the control contract's done signal, or its verification plan. Do not instruct the subject to obtain or avoid another agent merely to simplify evaluation. When agent use is part of the question, let the subject make that decision inside the host-enforced topology; an evaluator-imposed no-other-unit instruction would decide the branch being measured. The subject gives the ordinary response the real request calls for and does not classify its own conduct for the evaluator.

Put the exact evaluated artifact, built from the evaluated source with the effective compiler or supplied as it stands, where the host loads it for this subject alone. Establish before launch that the loaded bytes hold the contracted artifact. Point the subject to it and prohibit every other skill; record both additions as configuration, since they leave host skill selection unexercised. A run that loads another skill is inconclusive for this one. This authorized fixture input lives and goes with the fixture and never goes where the requester's own agents load skills.

Establish the topology from host-native evidence before launch. Use the smallest bound that can settle the question, but do not remove a capability whose use or non-use is being tested. The host must prevent creation beyond the authorized maximum while leaving in-bound decisions to the subject. If no enforceable maximum exists, proceed only when a finite host maximum is established and every reachable instance and effect within it is authorized; otherwise do not launch. A blocked attempt beyond the bound is behavior evidence. If an instance is actually created outside the contract, account for the unauthorized effect and leave claims depending on that case inconclusive. Confine every instance to the authorized evaluation boundary.

Designate before launch the host-exposed interaction record and named post-run state that will record the whole instance tree. Observe the subject's routing, pages opened, tool calls, questions, output, and mutable effects and, for every subject-obtained instance relevant to a claim, its creation, brief, effective instruction sources and configuration, interactions, return, effects, and stop. This host observation replaces special evidence return fields and the subject's self-classification because the subject's conduct, not a delegated conclusion, is the evidence. Read those records only after the host establishes that the primary subject and every instance it obtained stopped. Where the host cannot expose a record a claim needs, leave that claim inconclusive. Close each launched case as supported, failed, blocked, or inconclusive before synthesis; silence, inactivity, a stopped primary with a live descendant, or partial state does not establish a stop.

When an acceptance claim depends on the post-run condition of a workspace or other mutable output, that state becomes evidence when the whole instance tree stops. A verification step is observational only when it cannot change a property the acceptance decision may use; calling an executing command a check does not make it an observation. Make each transient tell name both the observation that settles it and the point at which it must be captured. Capture and retain every acceptance-relevant observation from the original state before any verifier step that could change it. If further verification can change that state, run it only on a throwaway copy whose creation, destination, and contents are authorized. When no such isolated copy is available or authorized, leave the affected verification blocked or inconclusive. If the original state was disturbed first, use independent evidence that distinguishes the subject's effects from the verifier's; without it, close the affected tell as inconclusive rather than failed.

For a comprehension case, use an ordinary request and no artificial fixture; for execution, use the smallest sanitized fixture a performer would have. Where that fixture is a Degardis source, make it from the effective manual and [[guide:construct-ownership]] so that its only defects are those the case tests, since any other defect measures the fixture rather than the skill. Never use real sensitive material for convenience. When delegation behavior is under test, put the decision conditions in the ordinary request and environment without telling the subject which branch should win. Establish the configuration in force from host-native evidence and test a capability floor at the least capable claimed configuration.

Run primary subjects one at a time. Start a second live primary only when the fixed question requires concurrent independent replication and the control contract establishes that serial execution would harm the result, authority and host capacity cover the width, losing the whole batch is tolerable, and synthesis will wait until every case is closed; use disjoint equivalent fixtures. Instances obtained by one subject are behavior inside that case, not evaluator replication, and remain governed by its topology. After a repair, rerun the same case from a fresh equivalent starting fixture under the same conditions, and stop when an unchanged recheck reveals no new general cause.
