A guide is detail loaded as a separate page from the task or facet pages that reference it, and read on such a path only when its applicability holds, or always when it has none; take the mechanics from the effective manual. Which provisions a guide may own, including one reachable only from a facet, is decided under [[guide:construct-ownership]]; a condition written for task-owned baseline detail says when that detail applies, never that it is optional.

## Content

A guide may assume what every owner path that opens it establishes, plus what its applicability establishes before the page is opened.

A guide can restate its own condition, and that is easier to write than to notice. An agent opens a page because it was already told the condition and decided the condition holds, so a page opening with when to consult it spends its first paragraph on the one thing its reader has just read and acted on. Open with what the condition could not carry — the framing that changes how everything below is read, such as which agent the page governs or what a plan rather than a change should take from it — and where there is no such framing, open with the material.

## References

Take applicability mechanics from the effective manual, including that a guide's applicability decides whether it applies on every path that references it, and that prose creates no condition the compiler carries. So the sentence around a reference cannot make a guide conditional, and a guide without applicability applies wherever it is referenced, however that sentence is worded.

State each condition once, in applicability. Prose at an inline reference adds only what applicability cannot carry, such as the step the guide must precede or the part of the open page's decision it serves, and refers to the condition as the guide's own (*when it applies*) rather than restating it. A condition restated in prose is a second owner of it, and the two drift.

Place the reference where its reader needs it: an owner's guide list reaches the reader where the manual says owner links render, and an inline reference puts the pointer at the step it governs. Either way, reference the guide from each page whose own work makes the decision it informs. Where that page is another guide, the nested guide is reached only after its parent opens, so its reach is both guides' applicability together; keep that placement, since listing the nested guide on a task as well gives every run of the task one more link to assess for detail it can need only once the parent is open. A path needs the guide outside its parent's conditions only when that path's own pages require the decision the guide informs; that the detail would be useful on some run of the path is not such a need.

Keep prose gating for a branch that stays local to an already-open page and loads nothing separately.

## Applicability

When only some executions reaching a guide need its detail and that need is decidable before opening it, give it applicability; when every one needs it, omit applicability.

Write the condition from the guide's body: the decision or result the page informs, and the observable point in the work at which that decision is at stake. Because that one condition decides reach on every path that references the page, it names no task, route, or activity standing for one; which pages reach it is placement's business, so adding, removing, or re-homing a referencing page changes where the page is referenced, never its condition. For example, a house-style guide conditioned *When a draft is being written, edited, or reviewed* lists the tasks that open it and misses any other work that produces such a draft, while *When the result will be published under the organization's name* names the need and holds wherever it arises. A referencing page whose runs need the page while its condition does not hold shows a condition that names its readers rather than the need: rewrite it at the width of the need instead of appending an item. *Depends on* names a point only when what follows is concrete enough for the reader to tell whether its own result turns on it.

Make every item decidable before the page opens, from what any path that references it can observe; one that restates the heading of the page it gates has said nothing about when it is true.

## Items

One holding item is enough for the guide to apply, and conditions that must all hold share one item, so each item is one situation that alone makes the page needed, and the list holds each situation once. Decide what is one situation by what the reader checks, not by how the prose divides.

Cases the reader decides from one observable fact are one situation: name that fact once, at the width of the need, rather than listing its instances as sibling items or as a series joined by *or* inside one. A list of instances reads as the boundary, so the next instance goes undecided or is decided from prior belief; the condition above naming publication under the organization's name decides a press release, a web page, and a signed letter with one check, where an item for each would miss the next format. Cases decided from different evidence or at different points in the work are separate situations, even where one sentence could join them. Joined in one item, they hide that either suffices alone, make the reader parse which clause holds, and let an edit meant for one change the other.

Test each item alone: suppose it is the only one that holds, and ask whether the page is then needed. An item that fails is not a situation but part of one, such as a precondition, qualifier, or narrowing of another item, so join it to the item it qualifies with *and*, or delete it where it qualifies none; left as a sibling, it decides alone and extends reach to every case where it holds without the rest. An item that needs a sibling's words to be read, through *also*, *otherwise*, or a pronoun pointing across, depends on that sibling the same way, so every item stands alone, with its own opener.

Before keeping two items, find for each a case that satisfies it and not the other. Where neither has one, they are one situation worded twice, whether as paraphrases or as a series of synonyms, and the same holds for two clauses of one item: keep the wording that decides it most directly and delete the rest, since copies left in place drift apart until they name different situations and nothing says which was meant. Where only one has such a case, that one is the wider and the other adds nothing, since every case of the narrower already satisfies the wider; delete the narrower, unless the wider item is broader than the need, which makes the wider one the item to narrow.

The number of items follows from these tests and is never a target: one where the need is one situation, and one for each situation otherwise.

A long list that survives these tests is the usual sign that the guide carries more than one responsibility. Ask what work each item brings its reader to the page for: where items bring readers for different work, split the guide along that work, each part with its own shorter condition.
