---
title: Task cues
applicability:
- When the work depends on a task's cues
---

Take the routing model from the effective manual: what a cue routes and how order among matching tasks is settled. The judgments below follow from that model.

A cue is request-visible evidence of one outcome: decidable from the request, standing instructions, and host limits the child agent can observe, never from a classification the reader can reach only after routing, and silent about other outcomes. Under that model a request for two outcomes is routed once per outcome, so a cue that excludes or bundles a second outcome stops matching exactly when both are asked for, and the outcome it was written for goes unrouted. A distinction the request does not show cannot route at the root; one that only a task's work reveals belongs to that task's hand-off.

Where cues overlap, manifest order settles which task takes the outcome and the default order of a route, so list a task whose cue names the narrower request before one whose cue would also take it, and a task whose result another consumes before that consumer. Where the compiled first-match winner for an outcome, or the compiled order of a compound request, is not the intended one, reorder or narrow the cues.

## Items

One matching cue is enough for its task to take an outcome, so each cue is one kind of request that alone asks for the task's outcome, and the list holds each kind once. Decide what is one kind by what the reader checks in the request, not by how the prose divides.

Requests recognized from one observable fact are one kind: name that fact once, at the width of the outcome, rather than listing its phrasings or instances as sibling cues or as a series joined by *or* inside one; a list of phrasings reads as the boundary, and the next phrasing goes unrouted. Requests recognized from different evidence are different kinds even where one sentence could join them: joined in one cue, they hide that either suffices alone, make the reader parse which clause holds, and let an edit meant for one change the other. A request for a plan to change a source and a request for a change the host forbids, for example, reach one task on different facts, so each takes its own cue.

Test each cue alone: suppose a request matches it and no other, and ask whether that request asks for the outcome. A cue that fails, such as a permission or a precondition, is part of another kind rather than one of its own: join it with *and* to the cue it qualifies, or delete it where it qualifies none; standing alone, it routes every request where it holds. A cue that needs a sibling's words to be read, through *also*, *otherwise*, or a pronoun pointing across, depends on that sibling the same way, so each cue stands alone, with its own opener.

Before keeping two cues, find for each a request that matches it and not the other. Where neither has one, they are one kind worded twice, whether as paraphrases or as a series of synonyms, and the same holds for two clauses of one cue: keep the wording that recognizes it most directly and delete the rest, since copies drift apart until they route different requests. Where only one has such a request, it is the wider and the other adds nothing: delete the narrower, unless the wider cue is broader than the outcome, which makes the wider the one to narrow. The number of cues follows from these tests and is never a target.

A long list that survives these tests is the usual sign that the task carries more than one request class. Ask what finished state each cue's request asks for: where cues ask for different finished states, each is its own task with its own cues, placed in the manifest as above.
