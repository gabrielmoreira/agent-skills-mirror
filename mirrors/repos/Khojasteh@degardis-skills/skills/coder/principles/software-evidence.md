---
title: Evidence that can establish a software outcome
---

A capable agent lets the implementation define its own expected value, reads a passing build or suite as proof of behavior it never exercised, and adjusts a test or expectation until a check passes; each produces a confident claim that the evidence cannot carry.

An observable software contract comes from requirements, accepted criteria, public interfaces, schemas, persisted formats, protocols, standards, documented guarantees, compatibility promises, operational invariants, verified historical behavior, and consumers that constrain the result. The implementation under question cannot be its own expected value. When these sources disagree, preserve the disagreement until an authority or stronger evidence resolves it.

Evidence answers only the behavior, revision, configuration, environment, and workload it exercised. Inspection establishes structure and plausible paths. A build establishes that its configured compilation succeeds. A type or static check establishes only the properties it analyzes. A test establishes the behavior its assertions can distinguish. A benchmark establishes the metric under its workload and environment. None substitutes for another without an explicit relationship between their questions. A test, benchmark, end-to-end suite, or any other command that exercises the software's behavior produces fresh execution evidence; an adopted build, type check, linter, analyzer, or diagnostic that exercises no behavior and writes only disposable output outside the analyzed surface does not, and each task's approach and guides decide which kinds it may run, if any.

Select evidence from the completion conditions rather than from the fact that files changed, and fix the expected result and what would count as pass, fail, or inconclusive before running a check. Prefer existing current evidence, and manufacture no fresh execution evidence when inspection or current evidence already settles the question; otherwise use the least costly adopted observation that can distinguish success from a plausible failure, whether inspection, search, static analysis, build, focused execution, test, benchmark, render, or another project mechanism, and a broader check only when the change or risk crosses its boundary. Classify a failure before changing code or expectations in response. A failure belongs to the first layer that diverges from an independently established contract. Common, non-exhaustive layers are production behavior, the test or its expectation, the harness or fixture, environment, configuration, a dependency or service, the toolchain, data, and operations; within them, distinguish a stale expectation, a fixture or seed mismatch, interference between tests, an unavailable service, a permission or exhaustion condition, and a toolchain failure from a production defect. Classify an unlisted cause by the same standard, and leave the failure unclassified when the evidence cannot decide. Never change production code to accommodate a broken test or environment, or update an expectation merely because the current implementation produced it.

When a new or revised automated check is the proof, observe it fail for the intended reason before the correction and pass afterward where safe and practical. Otherwise name the substitute evidence and the limitation it leaves. Verification closes only over the final state.

A preservation claim needs evidence from both sides of the change. Prefer the same recorded input and observation before and after, or a focused adopted check whose expectation is independent of the implementation. Record pre-existing failures and environmental instability in re-readable working state before relying on a baseline. If the baseline cannot reliably distinguish the preserved behavior, narrow the claim or stop and name the missing evidence.
