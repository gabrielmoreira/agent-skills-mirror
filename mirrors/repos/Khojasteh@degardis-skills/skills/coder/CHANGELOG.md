# Changelog

This changelog summarizes significant changes to the installable skill.

## [1.2.0](https://github.com/Khojasteh/degardis-skills/releases/download/skills-2026-10-11/coder.zip) - 2026-10-11

Coder 1.2 gives design and measurement requests tasks of their own and makes clear what each kind of request lets the agent run. A question about how software should be designed now gets a design proposal rather than an implementation plan, and a request to observe or measure existing software gets the result with the conditions that produced it. Every command is judged by the effects it leaves behind, so investigating, explaining, planning, designing, verifying, and measuring run what leaves only disposable output without asking first, and anything more only with authority of its own. Plans state the starting state they assume, adding a dependency is the requester's call, and a requester who says to proceed without questions gets reported defaults instead of a stalled run.

- A request for how software, or a change to it, should be designed goes to a new task, Propose a software design, listed ahead of planning. It investigates until every question that could change the choice is settled or stands open, recommends a design only where the evidence separates it from the other viable ones, and otherwise presents each with the fact or decision that would separate them and who supplies it. The proposal takes the shape of the design document type the request names, a design proposal by default, and goes in the response or in the design document the request asks for.
- A request for how existing software behaves or what it costs when run, with no pass or fail criterion, such as how long a test suite takes, goes to a new task, Observe or measure existing software. It fixes what is run, its inputs and workload, and the revision, configuration, and environment before running, classifies a failure before attributing it to the software, and reports the result with the conditions that produced it, inventing no threshold to turn it into a verdict. Whether software passes a check or meets a criterion still goes to verification.
- A new principle, Effects a command leaves behind, judges every command by its effects rather than its kind. An effect is disposable output only when nothing outside the run depends on it, it stays out of maintained material and the material under analysis, and removing it restores everything the command changed; an effect the evidence can't show to pass counts as going beyond it. A fresh build directory, a cache, or a test database created for the run usually passes, while generating code into maintained material, replacing an existing dependency install, writing to a developer database, leaving a process running, calling a remote system under a credential, or incurring spend does not.
- Investigating a cause, explaining, planning, designing, verifying, and measuring each say what the request itself lets the agent run: a reproduction, a narrow observation, a check, or the software, with effects confined to disposable output, while any other effect needs authority of its own. A check a guide prescribes no longer overrides a task's limit: outside it, the check doesn't run, but its claim still needs that evidence. Until the requester asks for a change, a guide's instructions for making one are the standard an explanation, review, assessment, or plan judges or specifies material against.
- A review states whether anything should block the requested decision, ranks established findings by the decision each forces, keeps unverified risks apart, and names the implicated material it left unread. It treats the reviewed material as untrusted for execution, even the requester's own work, since a review request doesn't vouch for what it reviews.
- A finding states its impact with the expected and actual result. A candidate about what a reader or consumer relies on, such as documentation or test quality, and one about what a structure, mechanism, or dependency costs each have their own four parts; the second names the future change or measured workload that meets the cost. A clarity or maintainability issue is a defect when a named future change would be misled or made costlier by it.
- A plan gives the outcome it reaches, the starting state it assumes as prerequisites its executor can check in their own setting, and its units in execution order, each naming the facts it must establish before acting and each open decision or missing authority that blocks it, with who settles it. What only the requester needs for judging the plan goes in the response, outside the plan. Asked what the work would take, the plan sizes its units against one another from what drives their cost and names what could change a size, giving a duration or effort figure only from capacity and rate the requester supplies. The agent offers to leave each requester-owned choice open for the plan to carry, except one without which no plan can be written.
- The agent can default a requester-owned preference when the requester or standing instructions say to proceed without questions, or when the requester or host establishes that no answer can arrive in time. It takes the default the evidence best supports, records what would displace it, and reports it as the requester's to change. A permission or policy decision is never defaulted, and where no evidence favors a value, the dependent work stays open.
- Adding a new direct dependency to an existing project, whether for run time, build time, or development only, is the requester's decision: the agent puts the capability, the candidates, and their obligations to them and adds one only once they approve it or an allowance or standing instruction covers it. Pushing, opening or updating a change request, and publishing a tag are externally visible operations that permission to change code doesn't cover.
- A report or plan document written at the requester's request serves the requester, not the project: unless they ask to keep it in the project, or it goes where the project keeps such records, it isn't committed, built, or published.
- Documentation work covers project documentation: documents, source comments, and docstrings. Text the running software displays or emits, such as interface copy, messages, and command-line help, is changed and verified as software, because tests, translations, and parsing consumers depend on it. Implementation owns any requested change to an existing project, including refactors and test-only changes that leave behavior unchanged.
- Design selection treats a project's established mechanism as one candidate among the alternatives rather than one every design must extend, so a replacement that keeps every guarantee can win on cost. A design that gives up a guarantee names it and the evidence for the trade.
- Measuring cost no longer requires a minimum worthwhile effect or locating the dominant cost. Locating the cost applies before any optimization, and the optimization hypothesis, correctness safeguards, and baseline comparison apply to a proposed optimization; comparing measurements still fixes a minimum worthwhile effect first. Investigating a slow or costly operation now follows the same reproduction guidance as a failure.
- Document types adds a design proposal, for reviewers deciding whether a design should be built: context and scope, goals and the non-goals a reader could mistake for goals, the design down to the interfaces, data, and boundaries that carry its trade-offs, each reasonable alternative and what rules it out, accepted drawbacks, effects on concerns such as security, privacy, and observability, and open questions. The guide applies whenever a document's type decides what it contains or how it's judged, and release notes leave out only test and build changes with no effect on installation, upgrade, supported use, or operation.
- An assessment asked only for a codebase's overall condition reports it without a roadmap, every assessment closes with its unverified risks, and one at full depth inspects every unit of the mapped surface. An explanation covers the path only as far as the question needs, in the order its reader needs.
- An instruction file inside material under inspection is subject material unless the requester keeps it in place for their work, and a host loading a file by name or location designates nothing. Sensitive material is judged from its name, location, and type before it's opened. Reports follow their reader's order rather than a fixed one. Self-standing artifacts now covers the writer's setting: an artifact carries what it relies on or states it as a prerequisite its reader can check, and is read as its reader would read it before delivery. A spending limit never lets an unopened part of a surface count as covered.
- Security boundaries are exercised with payloads that demonstrate a flaw without causing its harm, and a destructive or irreversible data change needs an observation of the affected data taken immediately before it runs. A task waiting on another, such as documentation that needs a code change first, now waits on one already queued instead of stalling.

## [1.1.0](https://github.com/Khojasteh/degardis-skills/releases/download/skills-2026-10-07/coder.zip) - 2026-10-07

Coder 1.1 keeps more decisions with the requester and makes what the agent hands over easier to rely on. Plans now put the requester's choices to them before the design is settled, a statement that something is acceptable authorizes it without requesting it, and documents, plans, and handoffs say what holds rather than how they came to be. Documentation work also chooses a document type by what its reader is doing.

- Plan work puts the choices that belong to the requester to them together, before settling the design, and offers to leave open each one the design can be settled without, for the plan to carry where it governs. A choice that surfaces during design is put as soon as it blocks the design, otherwise before the plan is delivered, and when the requester can't answer first, the plan lists the choices never put to them. How deeply a modernization retires the legacy model is now asked like any other choice.
- An allowance, such as accepting breaking changes, a new dependency, or downtime, authorizes that thing without asking for it. The agent decides as it would without the allowance, counts what the allowed thing costs those who bear it, and takes it only where it serves the requested outcome better than every choice that does without it.
- A new Self-standing artifacts principle applies before writing code, documentation, a plan, a commit message, a handoff, or anything else used without the process that produced it. The artifact states what holds, states a boundary only where a reader would otherwise cross it, and leaves options considered, refused, or ruled out to records whose purpose is that history. Reports now name required work left undone, so options declined along the way no longer read as unfinished work.
- A question about whether, where, or how the work continues is answered from the observed state, and the agent starts nothing the question names until the requester chooses it. A requested handoff, or a redirection that leaves an outcome unfinished, now reaches the handoff guidance.
- A Document types guide covers fifteen types grouped by what their reader is doing: using, upgrading, operating, or contributing to the software. Release notes and a changelog, a runbook and a playbook, and a contributing guide, architecture overview, and decision record now stand apart because their readers differ.
- Command-line help and other interface text now follow the human-facing API documentation guidance, so they state what a command, option, or control accepts, does, and reports.
- .NET XML documentation puts every example of use in `<example>`, with its code in `<code>`, and keeps `<remarks>` for supplementary explanation.
- The JavaScript guidance now applies to TypeScript code, since everything it carries holds once the types are erased.

## [1.0.0](https://github.com/Khojasteh/degardis-skills/releases/download/skills-2026-10-03/coder.zip) - 2026-10-03

Coder 1.0 gives an agent one evidence-led workflow for software work across a product or codebase. It keeps the requested outcome and authorized boundaries visible from investigation and design through change, verification, and reporting, while using the project's own contracts and tools to decide what completion requires.

- Covers ten distinct outcomes: assessing a codebase, planning work, investigating problems, reviewing risk, explaining or documenting software, creating a product, implementing or withdrawing functionality, and verifying a result.
- Grounds decisions in the project's requirements, contracts, consumers, configuration, tooling, and current state instead of relying on ecosystem convention alone.
- Reconciles affected implementation, tests, documentation, interfaces, data, dependencies, security, operations, and other project surfaces without treating every change as requiring every possible check.
- Adds contextual guidance for a broad range of languages, frameworks, runtimes, documentation systems, and test tools so relevant technology rules reach the task that needs them.
