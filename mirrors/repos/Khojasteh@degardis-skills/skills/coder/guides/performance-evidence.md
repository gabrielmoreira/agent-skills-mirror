---
title: Performance evidence
applicability:
- When a result of the work depends on a performance or resource-cost measure
---

Define the metric, workload, scale, environment, configuration, sample method, natural variation, and every existing budget, service objective, or contractual limit before measuring. Capacity and tail behavior require offered load and concurrency to be stated; a single-operation timing cannot establish them.

Name the statistic the outcome depends on, such as a tail percentile, sustained throughput, peak footprint, cold start, transferred size, or unit cost. Take that statistic from what the consumer of the work gets for what it spends, not from the code the request names. A performance outcome relates what the work delivers to what it costs, and a cost measured alone holds the delivered side fixed, which is sound only when every version compared delivers the same thing; where a change can alter how much, how well, or how often the work delivers, measure that side too, in the consumer's terms, and combine the two as the consumer does, such as cost per unit delivered, what is delivered within a budget, or the cost of reaching a required level. Make the workload representative in input shape, scale, state, concurrency, and lifecycle, including the common case and any boundary or high-load case the outcome depends on, and state what production dimensions it misses. If a representative input is unavailable, label any synthesized or sampled workload as a proxy, state how it was derived and what would validate it, and do not claim a representative result from it. Do not measure against a default invented for an indispensable missing outcome, workload, environment, or guardrail.

Account for sampling bias, instrumentation overhead, missing spans, and aggregation that can hide a dominant tail. Suspect the instrument when the reported cost is implausible for the work. Report a defect, misconfiguration, saturated dependency, or contended environment as such rather than absorbing it into an optimization.

Generating load, profiling a shared or live system, raising production diagnostics, or incurring spend requires separate bounded authority.

## Attributing cost

Before any optimization, and whenever else [[guide:performance-cost-domains]] applies, use a focused profile, trace, plan, counter, or benchmark that can attribute the dominant cost to one of the resource domains in that guide. Apply the following cost-localization steps to that attribution.

Locate the path or bounded set owning the largest material share of the resource named by the outcome, not the first code that looks expensive. When representative measurement is unavailable, keep the causal proxy, its claim limits, and the workload and environment needed to validate it; code shape or a familiar optimization target does not establish cost.

Establish the layer that owns the cost before choosing a change. Common, non-exhaustive candidates are the implementation, a correctness defect, environment contention, configuration, a dependency, the data shape, an external system, and the measurement itself. When a lower layer owns the resource use, separately test whether this project's call frequency, transferred volume, resource lifetime, or requested buffering owns a material share; neither stopping at the dependency boundary nor compensating downstream establishes the cause.

## Optimizing

Apply the following to a proposed optimization.

Make one falsifiable optimization hypothesis before editing: the causal cost, the mechanism the change alters, the predicted effect on the primary metric, possible regressions, and the comparable result that would disprove it. Change one causal factor at a time when practical. Do not bundle changes beyond attribution, apply a familiar optimization before its mechanism owns the cost, or add speculative structure, dependency churn, or a benchmark-only fast path in place of a hypothesis.

A gain measured on one machine can belong to that machine rather than to the change, so the mechanism must hold on other machines too. A mechanism such as doing less work, allocating less, or keeping data smaller and closer together carries its gain to other machines through its own measure, such as work done, allocations, or bytes moved, which does not depend on the machine as elapsed time does; tuning code, constants, or build or runtime options to properties of the measured machine, such as its cache sizes, branch prediction, instruction timings, code alignment, instruction-set extensions, core count, memory size, storage or network speed, or operating-system or runtime version, buys a gain another machine can lose or reverse. Selecting a machine-dependent value or code path on the machine the code runs on, such as a worker count taken from the available cores or a vector path chosen after detecting the processor's support, makes it applicable there, not faster: retain the selection only when evidence shows it improves the primary metric on every target that selects it, such as measurements on them or results the project already holds for them. Tune to such a property only when the request or project evidence establishes that the software's targets have it, such as a named board, a single declared deployment platform, or a pinned runtime version, and report the gain as holding on those targets alone; the machine this work runs on does not become a target because the measurements were taken there.

A change can make each unit of work cheaper or make each unit deliver more, and gaining on one side can lose on the other: consider both, predict each change's effect on both sides, and choose by the primary metric rather than by the cost of one unit, holding whatever the contract requires the work to deliver.

Settle independently grounded correctness checks and resource guardrails before editing, treating documented timing, capacity, ordering, and resource guarantees as contract. The measurement proving lower cost cannot also prove that required work still happened; do not gain speed by weakening an assertion, skipping validation or work, loosening a tolerance, returning an incomplete result, or changing values, failures, effects, ordering, or compatibility; a change in how much or how well the work delivers, where the contract permits it, is weighed in the primary metric instead. When optimizing a test suite, preserve behavioral coverage, independent oracles, determinism, isolation, diagnostics, and the required test levels; do not delete, disable, or merge tests merely to reduce suite duration.

Compare the final state with the baseline under the same material conditions. Retain a change only when [[guide:performance-comparisons]] credits its effect, the measure its mechanism alters, such as work done, allocations, or bytes moved, changed with it, correctness evidence passes, and the tradeoff is acceptable. Quantify any cost moved to another metric, path, system, team, or future maintainer where possible, and obtain approval when it exceeds a budget or changes a contract. Otherwise remove the change and report the attempted effect as unproved or insufficient; preserve failed or inconclusive findings only when they change what should be tried or avoided next.
