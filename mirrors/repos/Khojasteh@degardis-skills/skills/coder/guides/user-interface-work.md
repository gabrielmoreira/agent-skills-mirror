---
title: User-interface work
applicability:
- When what a person sees or does in a software interface is part of the requested outcome
- When evidence for a claim comes from what a person sees or does in a software interface
---

Treat a human-facing interface as observable software behavior rather than as a styling layer. Establish the affected user, the task or flow they are trying to complete, the entry point, supported environments and input modes, the user-visible states the work can materially affect, and the source that decides what success means. Use requester requirements, established product contracts, current project behavior, accepted design artifacts, the project's design system or component conventions, platform rules, and competent external standards only within the authority each actually has. Existing appearance is evidence of the baseline, not automatically a requirement to preserve it, and aesthetic preference is not an acceptance criterion unless an owning authority makes it one.

Before choosing markup, widgets, components, styles, or interaction patterns, inspect the mechanisms the project already uses for navigation, layout, reusable components, visual tokens, forms and validation, state, localization, semantics and accessibility, responsive or platform adaptation, and UI testing or previews. Reuse an established mechanism when its semantics and lifecycle fit the accepted contract; do not create a parallel design system, component vocabulary, state path, or interaction convention merely because a new one is easier locally. When the requested outcome intentionally changes the experience, preserve only the behavior and constraints that remain contractual rather than treating the old interface as the design authority. When it applies, read [[guide:human-api-documentation]] before drafting or reviewing interface text such as command-line help.

Model the affected flow as user-observable states and transitions. Loading, empty, error, disabled, validation, permission, offline, success, persisted, interrupted, and restored states are prompts rather than a closed checklist: include a state when the contract, supported environment, or observed risk can make it reachable and decision-relevant, and add an unlisted state by the same standard. For each material transition, establish the triggering user action or event, the state owner, what becomes visible or otherwise perceivable, what actions remain available, how failure and recovery behave, and what navigation or focus continuity the user relies on. Treat viewport, content length, text scaling, input method, locale or writing direction, color or contrast mode, motion preference, and comparable environmental variation the same way: exercise them when the supported boundary or evidence makes them capable of changing the result, not by ritual.

Keep visual appearance, interaction behavior, semantics, and accessibility as separate claims even when one change affects all four. Source inspection can establish authored structure; a render can establish tested visual output for its exact configuration; direct interaction can establish the tested input and state-transition path; and the platform's semantic or accessibility inspection path can establish the exposed names, roles, states, relationships, order, or focus behavior it actually reports. Evidence for one claim does not silently prove the others. A screenshot cannot prove keyboard, gesture, focus, announced meaning, or hidden state, and a passing interaction cannot by itself prove visual fidelity. Snapshot, screenshot, or golden baselines are useful only when an independent requirement or reviewed baseline establishes what they are meant to preserve; generating the baseline from the changed implementation does not create an oracle.

Use the project's adopted run, preview, build, browser, emulator, device, test, or inspection path for the boundary being claimed. Establish required capabilities from the project and host rather than assuming a browser, simulator, assistive technology, device, plugin, or service exists because it was available elsewhere. If decisive rendering, interaction, semantic, or accessibility evidence cannot be obtained in the current environment, use the strongest available evidence for the narrower claim and leave the dependent part unverified beside the missing observation; do not convert unavailable execution evidence into a claim that inspection settled.

Select verification configurations from the accepted support boundary and the changed risks instead of attempting an arbitrary Cartesian product or checking only the easiest happy path. Record the configuration, viewport or device class when relevant, input mode, user-visible state, and observation method for each decisive result in re-readable working state. Before completion, cover the accepted primary flow and every materially changed failure, recovery, state, or environmental branch that could produce a different user-facing result. Report what the user can now do, the visible or interactive behavior that changed or was preserved, the evidence that decided those claims, and any supported UI surface or configuration that remained unobserved.
