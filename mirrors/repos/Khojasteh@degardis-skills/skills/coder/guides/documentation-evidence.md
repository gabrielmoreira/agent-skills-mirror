---
title: Documentation evidence and reader safety
applicability:
- When documentation or an explanation of software makes claims a reader will rely on
---

Treat every factual statement—including cause, purpose, motivation, history, protection, and assumptions—as unverified until evidence outside the documentation supports it. Establish each claim from the declaration, schema, command help, configuration, requirement, test, version metadata, generated interface, or executed example that fixes it. A name or observed effect establishes what happens, not why; state a rationale only when evidence states it.

Reconcile claims about the same subject, and support words such as “no,” “never,” “only,” “all,” and “exactly” with evidence broad enough to cover every claimed exception or weaken them. One implementation path is not a public guarantee, one example is not universal behavior, and a search that finds nothing does not establish product absence. Remove an unsupported claim, or mark it uncertain only when that uncertainty changes the reader's task. When code contradicts the requested statement, report the mismatch instead of documenting either side as settled.

Bind version-sensitive behavior, defaults, availability, and migration steps to the product, language, framework, and documentation-tool versions the project actually resolves. Establish the resolved version or configuration from project material; establish behavior for that exact version from project evidence, configured-tool help or output, or authoritative documentation whose version and scope match the resolved project state. Current upstream guidance or recollection about another version does not establish project behavior. When the resolved version or its behavior remains inconclusive, retain only version-independent behavior and report the version-specific gap. Distinguish current behavior, compatibility promises, and history, and never prescribe an unrequested upgrade merely to make a claim true.

For each documented failure, state its triggering input or state, recognizable representation, when it surfaces, material partial effects, and prevention or recovery. Separate conditions when timing, side effects, or reader action differs even if they share an exception type or status; distinguish a failure thrown on an asynchronous call from one delivered when its result is awaited or enumerated. Include a propagated failure only when a requirement, test, or verified applicable callee contract establishes the concrete condition and this reader must handle it. Link task guidance to an authoritative error catalog or runbook for exhaustive detail; do not copy the catalog into every page or enumerate plausible failures from memory.

For a README, tutorial, or how-to whose outcome is not otherwise obvious, use one smallest verified first-success example. State its working context and prerequisites, use conspicuously safe placeholders, disclose mutation or external effects, and show only enough output or state to recognize success. Keep exhaustive variants in tests or reference material. Do not add a decorative example, a long capture, or an example for coverage, and do not call an executable example copyable unless the repository's adopted command exercised it.

Keep prerequisites, warnings, failure recovery, version bounds, and mutating effects beside the instruction they qualify. For a destructive, irreversible, privileged, paid, or externally visible action, state the bounded target, required permissions, resources affected, expected effect and output, safe precondition, verification, and verified recovery or non-recoverability before the reader acts. Mark every mutating or externally visible command, use safe placeholders rather than real accounts or identifiers, and never execute a dangerous documented command against a live target merely to validate the page.

Plan validation before editing. For every command, name the claim it settles and the result that would change the text; run nothing merely for confidence, repeat no recorded check, and introduce no unadopted checker. Validate in reader-cost order: a command or code example the reader will run; a destructive, privileged, or paid action; a copied name, flag, default, or configuration key; a changed link or anchor; then explanatory prose. Read declarations or tool help for names and defaults, exercise reader-facing generated text through its supported interface, resolve changed links against their targets, run an adopted generator or markup check once on its narrowest relevant target, and follow the documented path from the stated prerequisites.

Tests may provide behavioral evidence, but running a unit, integration, end-to-end, or broad build does not validate documentation, links, navigation, or reader success. A repository-mandated project check remains task-level verification and does not replace documentation checks. Do not pin prose wording unless the test has independent behavioral value, present unrun expected output as observed, or call formatting alone validation. When a check is unavailable, unrelatedly broken, or would mutate unauthorized state, mark the affected claim unverified, name the check that would settle it, and continue with independently supported material.

In a review, rank incorrect claims before missing task information, unsafe or undiscoverable information, set-level conflicts, and optional editorial improvements. A preference without reader harm is not a defect.
