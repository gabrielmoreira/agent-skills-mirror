Add or revise a maintained automated test only when it is the appropriate durable observer for a contract or material regression risk not already covered; if no distinct future contract violation would make a proposed test fail, do not add it merely because code changed. Establish the configured runner, harness command, selector syntax, environment, and a known test that proves the harness before editing tests.

Choose the smallest credible level whose observer matches the contract: a narrow unit for local logic, a component or integration boundary for collaboration and state, and an end-to-end path only for behavior that depends on the assembled system. Derive cases from the contract's equivalence classes, boundaries, state transitions, failure modes, and significant interactions rather than from implementation branches. Take one case per distinction; add another only when it can expose a distinct plausible contract violation, including a named regression or material risk the selected coverage does not already distinguish. For a range, exercise the boundary and both sides instead of enumerating interior values. When interactions rather than single values drive behavior, use a decision table or a justified combinatorial selection to cover materially distinct combinations without claiming an open cross-product is exhaustive. When examples do not provide a scalable oracle, use a stable property, invariant, metamorphic relation, simpler reference implementation, or independently derived differential oracle. Use grammar- or fuzz-generated inputs to explore parser and robustness surfaces, fault injection to exercise otherwise rare failure paths, and mutation analysis only to judge whether a test suite can distinguish seeded faults—not as evidence that the product contract is complete. Use these techniques only when their discriminator matches the risk and the project can support them without introducing an unauthorized tool.

When the contract fixes a finite allowed enumeration and leaves an open rejected domain, cover every allowed value positively; samples from the rejected domain are risk checks, not exhaustive negative coverage. Reverse that rule for a finite forbidden enumeration and an open accepted domain. State the selection rule for any open-domain sample, never turn that sample into the set, and do not offer a case count or coverage percentage as the behavioral outcome.

Keep each assertion at the scope of one meaningful departure and make its message or test name identify the behavior that changed. Before writing it, separate the parts of the result the contract fixes from those allowed to vary. Assert a structured result through its contractual fields, types, keys, rows, counts, or statuses; compare the whole exactly only when an independent specification, translation catalog, or reviewed baseline fixes the complete result.

A substring or incidental phrase found somewhere in a larger output does not establish the behavior it once represented and can survive while that behavior breaks. Assert the predicate the case owns instead: the triggering condition and the resulting code, marker, field, type, artifact, status, state, or structure, with a variation that would change it. Exact wording is appropriate only when an independent contract fixes that wording. Incidental calls, fixture details, representation, and ordering remain free unless the contract makes them observable.

A check has value only when a plausible contract violation would make it fail. A check with no assertion, a return-only or did-not-raise check, a broad truthiness, non-null, count, or catch-all failure assertion, a tautology, or an expected result copied or recomputed from production does not meet that bar unless the asserted property is itself the specific contract. A direct check of a language, framework, or standard-library guarantee is not project evidence unless project code or configuration can violate the observed behavior, or that compatibility claim is itself the contract. Control time, randomness, ordering, concurrency, environment, shared resources, and external systems through project-supported seams when they would make the result nondeterministic. Use tolerances derived from the contract or measured variation rather than arbitrary slack.

Use a double when the real collaborator is unavailable, unsafe, nondeterministic, slow beyond the test's purpose, or cannot produce a required rare or failure behavior. Define the interaction contract it stands for, configure only behavior the case needs, and do not reproduce the production algorithm in the double. Restore patched global state after the case, and patch where the subject resolves the collaborator rather than where it happened to be defined. Treat snapshots and golden files as reviewed specifications; never bulk-update them to whatever the current implementation emits.

When a test fails, classify its layer under [[principle:software-evidence]]. A retry, repeat, shuffle, seed, serialized, or isolated run is diagnostic: a pass under changed conditions is a lead about the failure's dependencies, not proof of its cause or correction. Repair demonstrated leaked state rather than hide it with a setting. A project-supported scheduling or isolation constraint can repair a harness or fixture defect when independent evidence establishes that the original execution violated the harness or shared resource contract and the constraint preserves required behavior and coverage. A focus or skip introduced by the work is work-in-progress state to remove before completion, while a pre-existing skip with a recorded reason is a separate unresolved condition rather than something to enable silently. When independent evidence establishes a product defect, keep the contract expectation and the test that exhibits it intact and failing; do not weaken it, update a snapshot to defective output, or skip, quarantine, delete, or narrow it merely to return green. Leave the correction to the task that owns it, and report the defect when no correction was requested.

When removing behavior or a test, preserve evidence for the surviving contract. An absence earns a maintained assertion only when an independent contract makes the absence itself observable to a consumer — for example a specified rejection, a closed finite domain, a security invariant, or a compatibility boundary pinned by a complete specified comparison such as a published API or schema surface. A case outside these examples qualifies only by meeting the same test. Otherwise cover the complete surviving result and establish static absence by search, build, or type check instead of inverting an old test; a removal may need no new test when surviving coverage and artifact deletion are its complete evidence. Which existing tests and fixtures are removed, revised, or retained follows [[guide:existing-test-maintenance]].
