---
title: Abstraction and ownership boundaries
applicability:
- When a decision depends on whether an abstraction or ownership boundary earns its place
x-claim-provenance:
- claim: Duplicated code violates DRY only when it duplicates knowledge; code that looks alike but serves a different intent is not knowledge duplication.
  source: The Pragmatic Programmer, 20th Anniversary Edition (Thomas and Hunt), Topic 9, "Not All Code Duplication Is Knowledge Duplication"
- claim: A shared abstraction that takes a parameter and adds a conditional for each new case that is not exactly the same gains another parameter and conditional with every new requirement, and duplication is far cheaper than the wrong abstraction.
  source: https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction
- claim: Type-based dispatch repeated across units makes every dispatch site change when a type is added, a default case can hide a site that was missed, and a single dispatch isolated in a factory or mapper is not the smell.
  source: https://deviq.com/code-smells/switch-statements/
- claim: A capability presumed to be needed in the future should not be built now, though this does not apply to effort that makes the software easier to modify.
  source: https://martinfowler.com/bliki/Yagni.html
---

Prefer improving names, existing boundaries, and direct control flow before adding an abstraction. Use the fewest cohesive concepts, files, layers, dependencies, and indirections that the demonstrated behavior needs. Keep each changed unit and the common execution path locally followable, make every added navigation jump earn its cost, preserve clear ownership and construction paths, and group behavior by demonstrated reasons to change rather than unit size.

Every abstraction names a real concept, variation, ownership boundary, or evidence seam, and each indirection earns its navigation and lifecycle cost. Derive an interface from concrete caller needs and add an extension point only for demonstrated variation. Add another boundary only when project evidence shows a real substitution, isolation, nondeterminism, external-ownership, or policy boundary. Prefer direct composition when no established substitutability relationship requires inheritance. Each retained abstraction must identify the concept it owns, the pressure that requires it, and the comprehension, cohesion, coupling, navigation, or testing benefit it supplies.

Variation is demonstrated when behavior depends on which member of a set of alternatives, such as output targets, providers, file formats, or platforms, is in force, each member defining its own rules, and the finished work keeps more than one member, counting the project's members the request leaves in place and those it asks for. Count members, not the rules that differ today: rules each member defines for itself can come to differ in any respect, so the likely next change is another member or another rule that differs between members. Give each member one unit that owns its rules, choose the member once where the project resolves which one is in force, naming every member there so that none arrives by falling through to a default, and keep in shared units only what no member defines for itself, so a member's own rule stays in its unit even while it matches another member's. Branching on a selector a shared unit receives, whether a flag, an enumeration, or a string, mixes every member's rules into each unit that branches on it: each new member is an edit to each of those units, each rule that comes to differ is another branch in one of them, and a flag that outgrows two members also changes every site that passes it. A shared unit that carries one member's rules as its default hands them to every member that does not override them, so a new member inherits rules it may not follow and a change meant for the default member reaches the rest. A value that tunes one behavior the same way for every member, such as a limit, a level, or an optional feature, is an option rather than a selector. Variation is hypothetical when the finished work keeps only one: a member the request removes or replaces is not kept, and one it mentions only as possible or planned is not asked for.

Do not invert every dependency, introduce hypothetical extensibility, or hide straightforward behavior behind factories, strategies, wrappers, or configuration merely to conform to a pattern. When inheritance or polymorphism changes, preserve established exceptions, invariants, and accepted input ranges.
