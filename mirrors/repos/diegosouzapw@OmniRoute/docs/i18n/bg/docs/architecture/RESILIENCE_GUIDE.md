OmniRoute има три отделни, но свързани механизма за устойчивост. Всеки има различен обхват и предназначение. Разглеждайте ги отделно при отстраняване на проблеми с поведението на маршрутизирането.

## 1. Прекъсвач на веригата за доставчика

**Обхват:** целият доставчик (напр. `glm`, `openai`, `anthropic`).

**Предназначение:** да спре изпращането на трафик към доставчик, при който многократно възникват неизправности на ниво външна услуга.

**Реализация:**

- Основен клас: `src/shared/utils/circuitBreaker.ts`
- Свързване: `src/sse/handlers/chatHelpers.ts`, `src/sse/handlers/chat.ts`
- API за състоянието: `GET /api/monitoring/health`
- API за нулиране: `POST /api/resilience/reset`
- Обвивки: `open-sse/services/accountFallback.ts`
- Таблица в БД: `domain_circuit_breakers`

**Състояния:**

- `CLOSED` — нормалният трафик е разрешен
- `DEGRADED` — трафикът все още е разрешен, но се следи увеличеният брой неизправности на доставчика
- `OPEN` — доставчикът е временно блокиран; комбинираното маршрутизиране го пропуска
- `HALF_OPEN` — времето за изчакване преди нулиране е изтекло; разрешена е пробна заявка

**Конфигурируеми стойности по подразбиране (`open-sse/config/constants.ts`, достъпни в Табло → Настройки → Устойчивост):**

| Клас     | Влошаване при   | Отваряне при     | Време до нулиране |
| -------- | --------------- | ---------------- | ----------------- |
| OAuth    | 5 неизправности | 8 неизправности  | 60s               |
| API ключ | 7 неизправности | 12 неизправности | 30s               |
| Локален  | изчислено       | 2 неизправности  | 15s               |

`degradationThreshold` определя кога даден доставчик преминава в `DEGRADED`; `failureThreshold` определя кога веригата се отваря и доставчикът се пропуска. Профилите на локалните доставчици все още не са достъпни на страницата с настройки за устойчивост.

**Кодове за задействане:** само състояния на ниво доставчик `[408, 500, 502, 503, 504]`. НЕ задействайте прекъсвача при грешки на ниво акаунт (повечето 401/403/429 — те се обработват чрез период на изчакване или блокиране).

**Отложено възстановяване:** когато срокът на `OPEN` изтече, `getStatus()`, `canExecute()`, `getRetryAfterMs()` обновяват състоянието до `HALF_OPEN`. Не е необходим фонов таймер.

### Глобален период на изчакване за доставчика с изрично активиране (времеви ограничител)

Четвърти слой с **изрично активиране** (`PROVIDER_COOLDOWN_ENABLED`, по подразбиране е **изключен**) поддържа
между отделните заявки информация за доставчиците с неизправности в
`open-sse/services/providerCooldownTracker.ts`; тази информация се използва при определянето на целта за комбинирано
маршрутизиране, така че последователните комбинирани заявки да не обхождат отново доставчик, при който току-що
е възникнала неизправност. Записите на ниво доставчик спазват времевия ограничител `PROVIDER_PROFILES`:

| Профил   | задейства се след (`providerFailureThreshold`) | в рамките на (`providerFailureWindowMs`) | период на изчакване (`providerCooldownMs`) |
| -------- | ---------------------------------------------: | ---------------------------------------: | -----------------------------------------: |
| OAuth    |                                           `10` |                                  `15min` |                                     `5min` |
| API ключ |                                           `15` |                                  `30min` |                                    `10min` |

Под прага доставчикът **не** се счита за намиращ се в период на изчакване; успешна заявка изчиства
времевия прозорец. Записите на ниво връзка (`provider:connectionId`) вместо това запазват
експоненциалното отстъпление `minRetryCooldownMs → maxRetryCooldownMs`. Заместващи настройки:
`OMNIROUTE_PROVIDER_BREAKER_{OAUTH,API_KEY}_{FAILURE_THRESHOLD,FAILURE_WINDOW_MS,COOLDOWN_MS}`.
Защита срещу регресии: `tests/unit/provider-cooldown-window-gate.test.ts`.

## 2. Период на изчакване за връзка

**Обхват:** единична връзка/акаунт/ключ на доставчик.

**Цел:** пропускане на един проблемен ключ, докато другите връзки за същия доставчик продължават да обслужват заявки.

**Имплементация:**

- Маркиране като недостъпен: `src/sse/services/auth.ts::markAccountUnavailable()`
- Избор: `getProviderCredentials*` в същия файл
- Изчисляване на периода на изчакване: `open-sse/services/accountFallback.ts::checkFallbackError()`
- Настройки: `src/lib/resilience/settings.ts`

**Полета за всяка връзка:**

- `rateLimitedUntil` — времева отметка, до която продължава периодът на изчакване
- `testStatus: "unavailable"`
- `lastError`, `lastErrorType`, `errorCode`
- `backoffLevel` — брояч за експоненциално отстъпване

**Периоди на изчакване по подразбиране:**

- Базов период за OAuth: 5s
- Базов период за API ключ: 3s
- 429 за API ключ: предпочитат се `Retry-After`/заглавките за нулиране/подлежащият на анализ текст за нулиране от услугата нагоре по веригата
- Отстъпване: `baseCooldownMs * 2 ** failureIndex`

**Защита срещу лавинообразни едновременни заявки:** предотвратява прекомерното удължаване на периода на изчакване или двойното увеличаване на `backoffLevel` при едновременни грешки.

**Крайни състояния (НЕ са периоди на изчакване):**

- `banned` — задава се при откриване на забранена ключова дума/блокиран акаунт (вижте [BAN_DETECTION](../security/BAN_DETECTION.md)), както и при три последователни отказа от услугата нагоре по веригата за отделни заявки (`request_rejected`, напр. Anthropic OAuth 403 „Request not allowed“ — `open-sse/services/requestRejectedStreak.ts`); единичен отказ само поставя връзката в период на изчакване
- `expired` (преминава в крайно състояние след ограничен брой повторни опити — `EXPIRED_RETRY_MAX = 3` с експоненциално отстъпване — така че временните OAuth грешки могат да се коригират автоматично, преди акаунтът да бъде деактивиран окончателно)
- `credits_exhausted`

Тези състояния се запазват, докато идентификационните данни не се променят или оператор не ги нулира. Не презаписвайте крайните състояния с временно състояние на изчакване.

**Отложено възстановяване:** когато `rateLimitedUntil` е в миналото, връзката отново става допустима. След успешно използване `clearAccountError()` изчиства всички полета за грешки.

### Афинитет на сесията (#7274)

**Обхват:** една клиентска сесия (заглавка `X-Session-Id` / `x-codex-session-id` / `x-omniroute-session`), прикрепена към една връзка за **всеки** доставчик.

**Цел:** запазване на многоходов агент (Claude Code, aider, персонализирани агенти) в същия акаунт между заявките, което намалява загубата на контекст при смяна на акаунт и повтарящите се 429 при студен старт от доставчици със сесийно състояние за всеки акаунт.

**Имплементация:**

- Определяне на TTL: `src/sse/services/sessionAffinityPin.ts::resolveSessionAffinityTtlMs()`
- Избор/създаване на прикрепяне: `src/sse/services/sessionAffinityPin.ts::selectSessionAffinityConnection()`
- Извличане на заглавката (общо, за всеки доставчик): `src/sse/services/auth.ts::extractSessionAffinityKey()`
- Таблица с постоянно съхранявани прикрепяния: `sessionAccountAffinity` (`src/lib/db/sessionAccountAffinity.ts`)
- Настройка: `sessionAffinityTtlMs` (глобален TTL в ms, `0` деактивира) — `src/lib/db/settings.ts`. Преименувано от специфичното само за Codex `codexSessionAffinityTtlMs` чрез миграцията `124_generic_session_affinity_ttl.sql`, която прехвърля всеки предварително конфигуриран TTL за Codex като новата стойност по подразбиране.

Преди #7274 `resolveSessionAffinityTtlMs()` принудително връщаше `0` за всеки доставчик с изключение на `codex`, така че настройката за TTL (и заглавките на сесията) нямаха ефект никъде другаде, въпреки че механизмът за прикрепяне и извличането на заглавките вече не зависеха от конкретен доставчик. Корекцията премахна това ранно връщане; вече TTL се прилага еднакво към всеки доставчик, след като глобално бъде зададен на стойност над `0`.

Трите заглавки за афинитет на сесията никога не се препращат нагоре по веригата — изпълнителите изграждат собствените си заглавки към услугата нагоре по веригата от нулата, вместо да препращат клиентските заглавки, така че това остава само вътрешен идентификатор за корелация.

### Ексклузивни наеми на връзки за управлявани сесии

**Обхват:** един активен управляван HTTP клиент/сесия притежава една допустима OmniRoute връзка.

**Цел:** осигуряване на устойчиво ексклузивно притежание на връзка за клиенти, които се нуждаят от строга граница при маршрутизиране между заявките. Това се различава от афинитета на сесията, който е меко предпочитание за непрекъснатост: ексклузивният наем съхранява постоянно състоянието на жизнения цикъл в SQLite, налага глобална уникалност на активния собственик и активната връзка и отхвърля остаряло поколение преди изпращането към доставчика.

Функционалността се включва по желание за всеки API ключ. Управляваният ключ трябва да има обхвата `lease:exclusive` и изричен непразен списък `allowedConnections`. Всеки HTTP клиент може да използва крайната точка за жизнения цикъл; не се изискват име на клиент, потребителски агент, доставчик, OAuth метод или модел. Наемът притежава връзка, а не модел, така че промяната на модела запазва обвързването, докато връзката остава допустима при обичайните условия. Обичайните правила за модел, квота, изправност, период на изчакване и списък с разрешения остават водещи и могат да прехвърлят същото поколение към друга свободна допустима връзка.

Жизненият цикъл е `POST /api/v1/session-leases` с JSON действия `acquire`, `renew` и `release`. Управляваните заявки за инференция подават непрозрачната стойност `X-OmniRoute-Lease-Owner` и точната `X-OmniRoute-Lease-Generation`. Собственикът използва `vlo_`, последвано от 43 base64url знака; съхранява се само неговият SHA-256 хеш. Всяка крайна проверка преди изпращане също обвързва ID на удостоверения API ключ и ID на активната връзка. Заглавките за управление на наема се премахват от регистрационните файлове, запазените моментни снимки на заявките и заглавките на изпълнителя към услугата нагоре по веригата.

Ако обичайното маршрутизиране има допустими управлявани кандидати, но всеки свободен кандидат е зает от чужд активен наем, OmniRoute връща HTTP `429`, код за липса на капацитет за наем, състояние на изчакване за капацитет и ограничен `Retry-After`, изведен от най-ранното релевантно изтичане. Обичайната липса на допустими кандидати не е конфликт за наем и запазва съществуващата семантика за грешки при маршрутизиране.

Свързаните механизми остават отделни:

- Заетостта на OAuth сесии е локално за процеса меко разпределение за OAuth акаунти.
- Семафорите на акаунтите предоставят разрешения за едновременни заявки и приключват при завършване на заявката.
- Ексклузивните наеми на връзки за управлявани сесии представляват устойчиво притежание в рамките на жизнения цикъл с проверка на поколението.

## 3. Блокиране на модел

**Обхват:** тройка доставчик + връзка + модел.

**Обхват на ключа според статуса:** статусът на неуспешната заявка определя към кой ключ се записва блокирането (`resolveLockoutScope()` в `open-sse/services/accountFallback/exactModelLock.ts`):

- `429` / `403` / `402` — сигнал за квота или право на достъп — блокира **семейството на квотата**:
  за codex — целия обхват `codex` / `spark` (всеки модел `gpt-5*` на
  връзката), а за останалите доставчици — `getQuotaScopedModelForProvider()`.
- `404` блокира конкретния модел (`getModelLockKey()` стеснява обхвата на `not_found`).
- Всеки друг статус — транспортни/сървърни грешки `5xx` и собственият
  синтезиран от OmniRoute статус `502` при проверка на качеството — блокира само
  **точната** тройка доставчик/връзка/модел. Невалиден поток при един модел не е
  доказателство за квотата на акаунта; преди това правило един празен отговор от
  `codex/gpt-5.6-luna` премахваше всеки модел `gpt-5*` на тази връзка от
  маршрутизирането за 2–30 минути (с ескалация), въпреки че квотата ѝ оставаше незасегната.
- Изрично зададената от извикващия опция `scope` винаги има предимство (Antigravity подава `"exact"`).

**Цел:** да се избегне деактивирането на цяла връзка, когато само един модел е недостъпен или е ограничен от квота.

**Примери:**

- Доставчици с квота за отделен модел, които връщат 429
- Локални доставчици, които връщат 404 за един липсващ модел
- Специфични за доставчика грешки в разрешенията за режим/модел (напр. режими на Grok)

**Реализация:** `open-sse/services/accountFallback.ts` — `lockModel()`, `clearModelLock()`, `getAllModelLockouts()`.

**REST API:**

- `GET /api/resilience/model-cooldowns` — изброяване на активните блокирания
- `DELETE /api/resilience/model-cooldowns` — ръчно повторно активиране. Тяло: `{provider, connection, model}`. Удостоверяване: управление.

### ПИ за настройките за блокиране + възстановяване чрез намаляване при успех (v3.8.23)

Блокирането на модели се промени от винаги включено, твърдо кодирано поведение във
функция с пълни възможности за конфигуриране и изрично включване, със собствена карта с настройки и самовъзстановяващ се механизъм.

**Карта с настройки:** Настройки → Блокиране на модел
(`src/app/(dashboard)/dashboard/settings/components/ModelLockoutCard.tsx`).
Тя е **отделна** от достъпната само за четене `ModelCooldownsCard` по-горе (която само
_изброява_ активните блокирания) — новата карта _конфигурира параметрите_. Стойностите по
подразбиране се намират в `DEFAULT_MODEL_LOCKOUT_SETTINGS`
(`src/lib/resilience/modelLockoutSettings.ts`):

| Настройка               | По подразбиране                  | Значение                                                                      |
| ----------------------- | -------------------------------- | ----------------------------------------------------------------------------- |
| `enabled`               | `false`                          | Главен превключвател — блокирането на модели е **изключено по подразбиране**. |
| `errorCodes`            | `[403, 404, 429, 502, 503, 504]` | Статуси от източника, които се отчитат като грешка в обхвата на модела.       |
| `baseCooldownMs`        | `120_000` (120 сек)              | Начална продължителност на блокирането при първата грешка.                    |
| `maxCooldownMs`         | `1_800_000` (30 мин)             | Горна граница на ескалирания период на изчакване.                             |
| `maxBackoffSteps`       | `10`                             | Максимален брой стъпки на ескалация при експоненциално отстъпване.            |
| `useExponentialBackoff` | `true`                           | Дали повтарящите се грешки увеличават експоненциално периода на изчакване.    |

Настройките се съхраняват чрез стандартното хранилище за настройки и се валидират чрез
схемата за настройки за устойчивост; картата ограничава `baseCooldownMs`/`maxCooldownMs`
(като `maxCooldownMs ≥ baseCooldownMs`) и `maxBackoffSteps`.

**Възстановяване чрез намаляване при успех:** възстановяването **не** се извършва единствено чрез изтичане на таймера. Изправен
отговор намалява броя на грешките на модела, така че модел, който се е възстановил
по време на текущия прозорец, спира да ескалира (и блокирането му се премахва), преди таймерът му да изтече. При успешна
комбинирана цел `open-sse/services/combo.ts` извиква `decayModelFailureCount()`
(`open-sse/services/accountFallback.ts`), която **намалява наполовина** съхранената стойност на
`failureCount` (`Math.floor(failureCount / 2)`); когато тя достигне `0`, записът за блокиране
се изтрива изцяло. Съответната функция `recordModelLockoutFailure()`
увеличава броя (и ескалира периода на изчакване) при грешки в рамките на
прозореца за ескалация. Това намаляване при успех допълва обикновеното изтичане на таймера —
всеки от двата механизма може да активира отново модел.

**Състояние:** блокиранията се съхраняват **в паметта** (`Map` обекти за отделния процес от тип
`ModelLockoutEntry`, индексирани по `provider:connectionId:model`, а блокиранията с точен обхват — по
`provider:connectionId:exact:model`), а не се съхраняват
в БД — те се губят при рестартиране. _Настройките_ се съхраняват постоянно; активното
_състояние_ на блокиранията е временно.

## 4. Контрол на паралелизма при споделяне на квота (v3.8.36)

Абонаментните акаунти (GLM, MiniMax и др.) често приемат само ~1–3 паралелни
заявки; превишаването на този брой води до грешки 429 и периоди на изчакване. Това е особено осезаемо при
комбинации с **quota-share** (`qtSd/…`), при които няколко API ключа споделят един
акаунт към доставчика. Три слоя предотвратяват претоварването на споделен акаунт.

### Ограничение на паралелизма за връзка (`max_concurrent`)

Всяка връзка с доставчик може да зададе максимална стойност чрез `max_concurrent`
(`provider_connections.max_concurrent`, задавана в модалния прозорец за връзката / API / БД).
Оставете полето празно, за да няма ограничение. Това е единствената настройка, която управлява слоя
за сериализация по-долу — задайте я според действителния паралелизъм на акаунта (напр. GLM ~1, MiniMax ~2).

### Сериализация на заявки при споделяне на квота

Когато диспечиране чрез quota-share е насочено към връзка, която декларира положителна стойност за
`max_concurrent`, паралелните заявки към този **акаунт** се сериализират чрез
семафор за всяка връзка (ключ `qsconn:<connectionId>`): излишните заявки **изчакват в
опашката**, вместо да претоварват акаунта. Механизмът е **fail-open** — при запълнена
опашка или изтичане на времето заявката продължава без слот, вместо да се отхвърля заявка,
която може да бъде диспечирана. Превключва се от **Настройки → Устойчивост → Паралелизъм за
връзка при споделяне на квота** (`resilienceSettings.quotaShareConcurrencyLimit.enabled`, включено
по подразбиране). Без ограничение чрез `max_concurrent` поведението остава непроменено.

> Шлюзът за маршрутизиране при quota-share (`selectQuotaShareTarget`, DRR + P2C) сам по себе си е
> fail-open и само _понижава приоритета_ на връзка, достигнала лимита — при
> пул само с една връзка той не може да наложи твърдо ограничение, така че именно този семафор
> действително овладява претоварването.

### Повторен опит за комбинации с отчитане на периода на изчакване

За всяка стратегия за комбинации (когато е активирана) заявка, която би довела до окончателна грешка 429
поради КРАТЪК временен период на изчакване, изчаква края му и се диспечира отново, вместо
да върне грешката 429 — това обхваща TPM/RPM прозорците от клас Gemini (~60s retry-after)
при комбинации от няколко модела, напр. когато и двете цели на комбинация от 2 модела достигнат
ограничение на честотата за съответния модел. Ограничено е чрез `comboCooldownWait` (`enabled`, `maxWaitMs`, `maxAttempts`,
`budgetMs`) в **Настройки → Устойчивост**. Никога не изчаква при `quota_exhausted`
(заключено до полунощ), нито при причини, свързани с удостоверяване или ненамерен ресурс.

## 5. Контрол на допускането до опашката със заявки (v3.8.49 · проблем #6593)

**Обхват**: локалната опашка за ограничаване на честотата за всяка двойка доставчик+връзка (`open-sse/services/rateLimitManager.ts`,
реализирана чрез Bottleneck), намираща се един слой под трите механизма по-горе.

**`maxWaitMs` е наследено персистирано име за изтичане на времето за изпълнение.**
`resilienceSettings.requestQueue.maxWaitMs` се подава към Bottleneck като
`expiration` на задача, чийто таймер се стартира едва след диспечирането. Следователно то ограничава
управляваното от ограничителя изпълнение, а не времето, прекарано в локалната опашка. Изтичането на времето
се представя като доверено локално `code: "RATE_LIMIT_EXECUTION_TIMEOUT"` (HTTP 504);
предишното име на кода за изтичане на времето в опашката се приема само за доверена вътрешна
обратна съвместимост. Стойността по подразбиране е 15000ms; заменете я чрез
`RATE_LIMIT_MAX_WAIT_MS` (променлива на средата) или таблото за управление (**Настройки → Устойчивост**,
максимум 1–30000ms в потребителския интерфейс). Престоят в опашката няма времеви лимит; използвайте
`maxQueueDepth` по-долу, за да ограничите броя на чакащите заявки.

**`maxQueueDepth` — незадължително ограничение за допускане (ново).** `resilienceSettings.requestQueue.maxQueueDepth`
ограничава броя на заявките, които могат едновременно да чакат на опашка (все още недиспечирани) за една
двойка доставчик+връзка. Когато опашката вече съдържа `maxQueueDepth`
заявки, нова заявка се отхвърля незабавно с типизирана грешка
`code: "RATE_LIMIT_QUEUE_FULL"` **преди** изобщо да достигне до `limiter.schedule()`
— така отхвърлянето е евтино и се случва преди каквато и да е последваща
компресия / транслация на подканата за тази заявка. Стойността по подразбиране `0` =
деактивирано, което запазва съществуващото поведение с неограничена опашка; допустимият диапазон е 0–100000.
Заменете чрез `RATE_LIMIT_MAX_QUEUE_DEPTH` (променлива на средата) или
`resilienceSettings.requestQueue.maxQueueDepth` (табло за управление/API корекция).

Самата проверка за допускане е чиста функция
(`open-sse/services/rateLimitManager/admission.ts::checkQueueAdmission`), така че
може да бъде тествана модулно без реален ограничител Bottleneck.

> RFC документът, с който беше открит #6593, предложи също флаг `bypassCompressionOnRateLimit`.
> Конвейерът `open-sse/services/compression/` в това хранилище извършва
> компресия на подканата/контекста в изходящата LLM заявка (`chatCore.ts`,
> около блока `resolveCompressionSettings`/`selectCompressionStrategy`),
> а не компресия на HTTP отговора за генерирани тела с грешка 429 — не съществува
> съответстващ път в кода за буквален флаг за заобикаляне. Понастоящем тази стъпка за компресия на подканата
> също се изпълнява _преди_ `withRateLimit()` в конвейера за заявки, така че
> пренареждането с цел пропускането ѝ при отхвърляне поради пълна опашка е отделна и по-мащабна
> промяна извън обхвата на този проблем; тя умишлено **не** беше реализирана
> тук и е оставена за последваща работа, ако спестяването на процесорни ресурси оправдава
> риска от пренареждането.

## 6. Механизъм за наблюдение на пропускателната способност при бавен поток (#9709)

Незадължителната защита `resilienceSettings.streamRecovery.throughputWatchdog` открива
upstream източник, който все още изпраща фрагменти, но генерира изход от асистента под
конфигурираната скорост на полезния изход. Тя умишлено е отделена от времето за изчакване
при неактивност: heartbeat съобщенията и метаданните не нулират нито един от двата таймера
и не се считат за напредък. Тя също така е отделена от твърдия краен срок за опита (#9153),
който остава абсолютна горна граница за безопасност независимо от качеството на изхода.

Механизмът за наблюдение изисква период за загряване, последван от пълен плъзгащ се прозорец,
преди да може да прекрати изпълнението. Той отчита текстовите делти от изходните събития на
Chat Completions и Responses API (консервативно приближение чрез броя UTF-8 байтове), игнорира
събитията само с данни за употребата и празните събития и преустановява оценяването, докато
има текущи събития за извикване на инструменти или разсъждение. По подразбиране е деактивиран
и може да бъде активиран с `STREAM_THROUGHPUT_WATCHDOG_ENABLED=true`; прозорецът, периодът за
загряване, минималната скорост и минималният измерим изход са ограничени от стандартния слой
за нормализиране на настройките за устойчивост.

Когато е активирано, прекратяването от механизма за наблюдение се прилага само към активния
upstream опит. Преди изпращането на каквито и да било видими за клиента байтове съществуващият
път за ранно възстановяване в рамките на същия акаунт може да отвори опита отново. След
потвърждаване потокът никога не се възпроизвежда сляпо; само съществуващият договор за безопасно
продължаване по средата на потока може да съедини суфикс. Финализирането остава еднократно,
така че отчитането на употребата и освобождаването на семафора не се дублират.

## 7. Преопределяне на upstream статуса (неправилно зададени грешки за квота)

**Обхват:** един upstream шлюз, който съобщава временно изчерпване на квотата с грешен HTTP статус.

**Цел:** коригиране на подвеждащ статус ПРЕДИ класифицирането, така че downstream потребителите (механизмът за fallback, combo агрегирането и отговорът към клиента) да виждат действителния характер на грешката, позволяващ повторен опит.

Някои шлюзове сигнализират за ВРЕМЕННО изчерпване на квотата с HTTP статус,
който не позволява повторен опит. `agentrouter.org` връща `403` (понякога `400`)
с текст на китайски (`用户额度不足` / `额度不足`) вместо стандартния `429`. Клиенти
като Claude Code третират `403` като постоянна грешка и прекратяват сесията, а без
корекция механизмът за fallback би я класифицирал като `AUTH_ERROR` вместо като
събитие, свързано с квотата.

**Реализация:**

- Регистър + механизъм за съпоставяне: `open-sse/config/upstreamStatusRestatement.ts` —
  списък с правила за всеки доставчик (`{id, fromStatuses, toStatus, textMarkers,
excludeMarkers, defaultRetryAfterMs}`), съпоставяни чрез `applyStatusRestatement()`.
- Място на извикване: блокът `providerFailure:` в `open-sse/handlers/chatCore.ts`
  (около ред 3654), непосредствено след като `parseUpstreamError()` анализира upstream
  отговор с HTTP статус за грешка (`!providerResponse.ok`) и преди извършването на
  каквото и да било класифициране, така че всеки downstream потребител да вижда
  коригирания статус. Грешките, вградени в `200` SSE поток, преминават през отделен,
  по-късен път за анализиране на потока и към днешна дата **не** се обработват от тази
  точка за прихващане — това е известно ограничение, което все още не е необходимо за
  неправилния статус на agentrouter (който се проявява като HTTP статус за грешка).
- Допустимост за повторен опит: `429` е включен в `RETRY_AFTER_ELIGIBLE_STATUSES`
  (`open-sse/services/combo/unavailableRetryGate.ts`), така че грешка с преопределен
  статус носи реален прозорец за повторен опит, вместо да се показва като безизходен `403`.
- Синтетичният `60s` `defaultRetryAfterMs` (`upstreamStatusRestatement.ts`) указва
  единствено какво съобщава на **клиента** отговорът с преопределен статус; сам по себе
  си той не е продължителността на вътрешното изчакване/блокиране на връзката — тя се
  управлява отделно от механизма, който действително обработва грешката с преопределен
  статус (ескалиращото отлагане на Connection Cooldown, §2, с базова стойност `3s` за
  доставчици с API ключове; или Model Lockout, §3, за доставчици с квота на ниво модел,
  като agentrouter). Маршрутизаторът може вътрешно да стане допустим за повторен опит
  преди изтичането на 60-секундния прозорец, който съобщава на клиента — това е
  преднамерен резерв, а не дефект.

Постоянните грешки (`无权访问模型` от agentrouter — няма достъп до този модел)
НИКОГА не се преопределят: `excludeMarkers` отменя правилото дори при съвпадение с
`textMarkers`, така че грешката запазва първоначалния си статус и нищо не прави
безкрайни повторни опити за нея. Съответстващото правило за класифициране на доставчика
(`agentrouter-model-access-denied` в `open-sse/config/providerErrorRules.ts`:
`reason: "auth_error"`, `scope: "model"`, декларирано базово изчакване от `6h`) се
проверява от `checkFallbackError` (`open-sse/services/accountFallback.ts`)
_преди_ общото ранно връщане `FORBIDDEN` за категорията apikey, като прилагането му
зависи от `honorsRuleLockScope(provider)` (#10334 — понастоящем само за agentrouter
чрез списъка с разрешени стойности `HONORS_RULE_LOCK_SCOPE_PROVIDERS` в
`providerErrorRules.ts`). Декларираното от правилото 6-часово изчакване се предава
като `fallbackResult.baseCooldownMs`, но все пак захранва вече съществуващия път за
блокиране при квота на ниво модел (`lockModelIfPerModelQuota()` /
`recordModelLockoutFailure()`, непроменен от #10334 с изключение на източника на
продължителността на изчакване): стойността му се ограничава надолу до зададената от
оператора `mlSettings.maxCooldownMs` (по подразбиране `1_800_000ms` / 30min), както
при всяко друго блокиране на модел, а _запазената причина за блокиране_ остава
съществуващата твърдо зададена стойност `"forbidden"`, а не `"auth_error"` от
правилото — от край до край се зачита само продължителността на изчакването, но не и
низът с причината. Самата връзка остава активна; останалите модели в същата връзка
не са засегнати.

Преформулираните грешки за квота (`额度不足`) достигат до правило за доставчик в продукционна среда
(`agentrouter-user-quota-exhausted`: `reason: "quota_exhausted"`, `scope:
"connection"`, без собствено декларирано време за изчакване — прилага се
подразбиращото се мащабирано обратно отстъпване на слоя за съхранение). След #10334 `scope` в
`ProviderErrorRuleMatch` СЕ използва от край до край, но **само** за доставчици в
списъка с разрешени стойности `HONORS_RULE_LOCK_SCOPE_PROVIDERS` (`providerErrorRules.ts` —
към момента само `"agentrouter"`, ограничено чрез `honorsRuleLockScope()`). За всеки
друг доставчик `scope` остава информативно, точно както преди #10334.
`checkFallbackError` предоставя обхвата на съвпадналото правило като
`fallbackResult.ruleScope`; `isAgentrouterConnectionQuotaScope()`
(`src/sse/services/auth.ts`) е споделената проверка, която потвърждава, че
даден `ruleScope` действително е безопасно да бъде зачетен като сигнал за цялата връзка,
който позволява автоматично възстановяване (обхват `"connection"`, причина `quota_exhausted`, никога
`permanent`, никога `creditsExhausted` — защита срещу бъдещо правило, съчетаващо обхват
`"connection"` с постоянно състояние на акаунта). Два потребителя го извикват:

- **Съхранение** (`markAccountUnavailable()`, `src/sse/services/auth.ts`):
  вместо да попадне в клона за блокиране **по модел** на passthrough доставчика
  (agentrouter е с `passthroughModels: true` → `hasPerModelQuota()`
  връща `true`), се прилага **временно време за изчакване на връзката** —
  `testStatus: "unavailable"` + `rateLimitedUntil`, никога крайно състояние
  (`credits_exhausted`/`banned`/`expired`) — така връзката се възстановява
  автоматично след изтичане на времето за изчакване, вместо да изисква ръчно нулиране на идентификационните данни.
  Пропуска се за връзки с `disableCooling: true` (#2997): при това отказване
  изпълнението вместо това продължава към блокирането по модел (документиран компромис —
  вижте коментара в кода над клона).
- **Комбинирано маршрутизиране в рамките на същата заявка** (`applyComboTargetExhaustion()`,
  `open-sse/services/combo/targetExhaustion.ts`): същата проверка маркира
  връзката в набора `exhaustedConnections` в паметта, индексиран с
  `${provider}:${connectionId}`. Това пропуска само оставаща цел В РАМКИТЕ НА СЪЩАТА ЗАЯВКА,
  която _сама вече съдържа точно този `connectionId`_ в собствения си
  обект на целта (`getExhaustedTargetSkipReason()`,
  `open-sse/services/combo/comboPredicates.ts`, `if (provider &&
connectionId)` преди търсенето в `exhaustedConnections`) — обикновена
  комбинация от списък с модели, при която съседните цели нямат собствен фиксиран `connectionId`
  и такъв се разрешава едва при всяко изпращане от заглавката
  `X-OmniRoute-Selected-Connection-Id` на отговора, никога не достига съвпадение с този ключ. За
  този често срещан случай действителната защита срещу повторното използване на току-що изчерпания
  акаунт от оставащ клон НЕ е този Set — тя е горният слой за съхранение
  (`rateLimitedUntil` на връзката вече е в бъдещето), в комбинация с
  потискането на `transientRateLimitedProviders` за
  грешката от същата проверка (вижте „Двуетапна архитектура“ и коментара в кода при
  клона `isAgentrouterConnectionQuotaScope` в `targetExhaustion.ts`): тъй като
  този Set остава немаркиран, принудителното разрешаване чрез `allowRateLimitedConnection` в `combo.ts`
  (`open-sse/services/combo.ts:1005-1013`, `:2734-2738`) НЕ се задейства за
  оставащите клонове на доставчика, така че филтърът `rateLimitedUntil` при избора
  на идентификационни данни (`src/sse/services/auth.ts:1238`) се спазва нормално и
  оставащият клон или избира друга, все още допустима agentrouter
  връзка, или се проваля поради липса на налични идентификационни данни — той не си
  проправя принудително път обратно към връзката, за която този клон току-що е задал време за изчакване.

### Двуетапна архитектура: преформулиране на състоянието, последвано от класификация

Преформулирането на състоянието (`upstreamStatusRestatement.ts`) и правилата за
класификация на доставчици (`open-sse/config/providerErrorRules.ts`,
`providerRuleRegistry`) са отделни регистри, които използват като ключ както идентификатора на доставчика,
така и текстови маркери, но се изпълняват на различни места и служат за различни
цели: преформулирането пренаписва HTTP състоянието рано в `chatCore.ts`;
правилата за класификация избират резервната `reason` и заключващия `scope`
(`model` / `provider` / `connection`) в `checkFallbackError()`
(`open-sse/services/accountFallback.ts`).

Правилата за класификация виждат пълния **текст** на грешката (необходим за съпоставяне с
маркери в тялото като `额度不足`) само за доставчици, включени в списъка с разрешени стойности
`FULL_TEXT_RULE_PROVIDERS` в `providerErrorRules.ts` — към момента само `"agentrouter"`. За
всеки друг доставчик от **вградения каталог** `checkFallbackError` предава
на `getProviderErrorRuleMatch` само структурираната грешка (`{code, type}`), което
е достатъчно за правила, базирани на заглавки/състояние/код, но не позволява разпознаване на маркери в текста на тялото.
Помощната функция `resolveRuleMatchBody()` извършва този избор: пълния текст на грешката
за доставчици от списъка с разрешени стойности и структурираната грешка за останалите. Добавянето на
**вграден** доставчик към `FULL_TEXT_RULE_PROVIDERS` е изрично включване за конкретен доставчик
— то съществува, така че подразбиращият се път за всеки доставчик, който не е в
списъка, да остане непроменен байт по байт.

`scope` на дадено правило (`model` / `provider` / `connection`) е отделно изрично включване
от `FULL_TEXT_RULE_PROVIDERS`: `checkFallbackError` само го предоставя като
`fallbackResult.ruleScope`, а потребителите надолу по веригата го зачитат като
нещо различно от информативен етикет само за доставчици в списъка с разрешени стойности
`HONORS_RULE_LOCK_SCOPE_PROVIDERS` в същия файл (`ограничено чрез
honorsRuleLockScope()` — към момента само `"agentrouter"`). Вижте „Преформулираните грешки
за квота“ по-горе за това какво действително прави съвпадение със `scope: "connection"`, след като
даден доставчик бъде включен в този списък с разрешени стойности.

**#11104 — декларираните от оператора правила заобикалят и двата списъка с разрешени стойности.** Оператор може
да декларира правило за конкретен доставчик по време на изпълнение чрез `settings.providerErrorRules`
(`open-sse/config/providerErrorRules.ts::setOperatorProviderErrorRules`),
без да редактира този файл. Ограничаването на операторско правило чрез
`FULL_TEXT_RULE_PROVIDERS`/`HONORS_RULE_LOCK_SCOPE_PROVIDERS` — списъци с разрешени стойности,
предназначени да защитават поведението **по подразбиране** на вградените каталожни правила — би
направило механизма за настройки неактивен за всеки доставчик освен вече
изброените там, тъй като самото деклариране на правилото вече е изричното
съгласие на оператора. `resolveRuleMatchBody()` и `honorsRuleLockScope()` първо
проверяват `hasOperatorRuleForProvider()`: доставчик с операторско правило получава
необработения текст на грешката и декларираният му `scope` се зачита, независимо
дали присъства и в някой от двата списъка с разрешени стойности.

**Известен пропуск — `providerRuleRegistry` никога не се проверява при HTTP 400.**
Разклонението `BAD_REQUEST` на `checkFallbackError` класифицира статус 400 изцяло
чрез собствените си масиви от шаблони (`MODEL_ACCESS_DENIED_PATTERNS`,
`CONTEXT_OVERFLOW_PATTERNS` и т.н. в `accountFallback.ts`) и връща резултат, преди
да бъде достигнато предходното разклонение `configuredRule`/`getProviderErrorRuleMatch`.
Вградено каталожно правило (или операторско правило) със `status: 400` е
синтактично валидно, но никога няма да се задейства. Понастоящем няма съществуващо правило,
насочено към 400, така че нищо в продукционната среда не е засегнато — но бъдещо правило за 400
изисква първо промяна на това разклонение, което е по-голяма промяна от добавянето на правило (то
прекласифицира 400 за всеки доставчик, който вече разчита на поведението с масиви
от шаблони), и е извън обхвата на добавянето на правило за един доставчик.

### Добавяне на нов шлюз, който представя неправилно квотата

1. Регистрирайте един масив от правила в `statusRestatementRegistry`
   (`open-sse/config/upstreamStatusRestatement.ts`). Поддържайте `textMarkers`
   специфични за доставчика; никога не използвайте повторно общи английски фрази, които съвпадат с
   `CREDITS_EXHAUSTED_SIGNALS` (`open-sse/services/accountFallback.ts`).
2. По желание регистрирайте правила за класификация в
   `open-sse/config/providerErrorRules.ts` (`providerRuleRegistry`), за да изберете
   правилния обхват на заключване (`connection` за квота на ниво акаунт, `model` за
   грешки на ниво модел). Тази стъпка има ефект в продукционна среда само за
   доставчици, чиито правила се нуждаят от пълния текст на грешката (маркери в тялото): добавете
   идентификатора на доставчика към `FULL_TEXT_RULE_PROVIDERS` в същия файл — в противен случай
   `checkFallbackError` подава на правилото единствено структурираната
   `{code, type}` грешка и правило, базирано на текста на тялото, никога няма да съвпадне с реалния трафик.
   Правила, които съвпадат само по `status`/`headers` (като тези на Opencode или
   Minimax), не се нуждаят от това изрично активиране. Отделно, ако правилото декларира
   `scope: "connection"` и целта е действително изчакване за цялата връзка
   плюс пропускане на комбинацията в рамките на същата заявка (а не просто информативен етикет), добавете
   идентификатора на доставчика към `HONORS_RULE_LOCK_SCOPE_PROVIDERS` в същия файл — именно
   това управлява използването в стил `isAgentrouterConnectionQuotaScope()` в
   `markAccountUnavailable()` (`src/sse/services/auth.ts`) и
   `applyComboTargetExhaustion()`
   (`open-sse/services/combo/targetExhaustion.ts`); без него `scope`
   продължава да се предава чрез `fallbackResult.ruleScope`, но нищо не предприема действие въз основа на него.
3. Добавете модулни тестове по образеца на `tests/unit/upstream-status-restatement.test.ts`
   и `tests/unit/agentrouter-error-rules.test.ts` (включително
   проверките за not-permanent / not-creditsExhausted и — ако доставчикът се нуждае
   от списъка с разрешени стойности — тест, удостоверяващ, че `resolveRuleMatchBody()` връща
   пълния текст само за този доставчик).

Не са необходими промени в `chatCore.ts`, `classifyError` или combo.

#### Заключване по групи за изходящ трафик (#10880)

Доставчиците в `EGRESS_BUCKETED_LOCK_PROVIDERS` (семейството opencode) се третират
като upstream услуги, групирани по IP (безплатното ниво на opencode е групирано по IP, а не
по акаунт — вижте #9611): статус 429, класифициран като `quota_exhausted`
**или** `rate_limit_exceeded`, поставя в период на изчакване всяка връзка от разрешеното семейство,
чийто последно известен изходящ IP адрес съвпада с този на неуспешната връзка, преди ротацията
да може да ги изпробва
— така се избягват N-1 upstream извиквания, които със сигурност ще са неуспешни (същият модел като #10460/#10525).
`rate_limit_exceeded` е включено умишлено: по пътя `markAccountUnavailable`
специфичните за opencode правила никога не съвпадат (към
`checkFallbackError` не се подават заглавки/тяло, а opencode не е в `FULL_TEXT_RULE_PROVIDERS`), така че 429,
чието тяло съдържа текста за абонаментна квота („достигнат е месечният лимит
за използване“), се класифицира като `quota_exhausted` чрез резервната логика за текст за квота
(`buildSubscriptionQuotaFallback`, `accountFallback.ts`; 1 ч. период на изчакване), преди
правилото `status_429` изобщо да бъде достигнато — докато 429 без текст за квота (обикновено
ограничаване на честотата) се класифицира чрез правилото `status_429` като `rate_limit_exceeded`
и въпреки това поставя IP семейството в период на изчакване. За доставчик от списъка с разрешени стойности ограничение на честотата,
групирано по IP, е същият сигнал като изчерпана квота. Реални ограничения:

- **Максимално възможно покритие**: заключването определя последния известен `egress_ip`
  на връзката от `proxy_logs` (24-часов прозорец, синхронно, без кеш). При празен
  кеш (изходящият IP никога не е бил проверяван) или липса на ред → неуспешната
  връзка все пак се поставя в период на изчакване от клона (записва се както
  досега), но не се заключва друга връзка.
- **Никога окончателно**: периодът на изчакване е обновяващ се квотен прозорец
  (`testStatus: "unavailable"`); от сигнал на ниво IP никога не се извежда
  постоянно състояние. Връзките с `disableCooling` пропускат клона изцяло.
- **Промяна в гранулярността на заключването за семейството от списъка с разрешени**:
  това е промяна на обхвата, а не само оптимизация за сродни връзки. opencode е
  доставчик с `passthroughModels`, така че преди този клон грешка 429 създаваше
  заключване за отделен МОДЕЛ; сега тя поставя връзката в период на изчакване —
  включително за оператор, който изпълнява една-единствена връзка без никакви
  сродни връзки. Това е гранулярността, която таблицата с правила на opencode
  вече определя като правилна (`scope: "connection"`,
  `providerErrorRules.ts`), но досега никога не е била спазвана, защото
  opencode не е в `HONORS_RULE_LOCK_SCOPE_PROVIDERS`. Клонът сам записва
  периода на изчакване + `backoffLevel` на неуспешната връзка, аналогично на
  клона на agentrouter с обхват на ниво връзка, след което връща резултат —
  блокирането за отделен модел и общият път по-долу никога не се достигат.
- **Включени комбинирани извиквания**: подобно на клона на agentrouter, обхватът
  умишлено пренебрегва понижаването чрез
  `persistUnavailableState`/`isCombo`, което извикваща комбинирана операция
  прилага към грешка 429. Заключването за отделен модел не е по-слаба форма на
  този обхват, а грешната единица: то не казва нищо за изчерпания IP, така че
  комбинираното превключване ще продължи да изразходва по едно гарантирано
  неуспешно извикване за всяка сродна връзка.
- **Безопасност на сродните връзки**: сродна връзка, която вече е в окончателно
  състояние (banned/credits_exhausted) или вече е в по-дълъг период на
  изчакване, никога не се презаписва.
- **Изключителен списък с разрешени**: разширяването на
  `EGRESS_BUCKETED_LOCK_PROVIDERS` е изрично решение на собственика; няма общо
  свързване (шаблон #10334/#10419). Заявката за сродни връзки използва като
  параметър същия списък с разрешени, вместо да го повтаря като SQL литерал,
  така че разширяването му остава промяна на един ред.
- **Ротация на изходящия IP в двете посоки**: прозорецът за търсене (24h) е
  значително по-широк от TTL на кеша за изходящия IP (5 min), така че
  „последният известен IP“ е историческа, а не текуща информация. Ако проксито
  на дадена връзка се е сменило в рамките на прозореца, заключването може да
  **пропусне** действително споделен IP (записаният IP е новият, неизчерпан
  такъв) — и симетрично може да **постави в период на изчакване сродна връзка,
  която междувременно се е преместила** от изчерпания IP. Вторият случай
  струва на тази сродна връзка един прозорец за изчакване; и двата се приемат
  като ограничения на подхода с максимално възможно покритие, базиран на
  исторически данни.
- **Цена**: две ограничени сканирания на `proxy_logs` (филтрирани по времевия
  прозорец чрез `idx_pl_timestamp`), само с честотата на грешките 429. Без нов
  индекс (миграция 134, YAGNI). Измерено върху копие на база данни с реален
  трафик и умерен размер; инстанция с висока пропускателна способност съдържа
  пропорционално повече редове в същия прозорец.

## Отстраняване на грешки

- Комбинация с претегляне връща `503 all_targets_cooling_down` (зададен е `Retry-After`, а `diagnostics.excluded` изброява всяка цел с `model_lockout` / `circuit_open` / `provider_cooldown` / `unavailable`) → пулът е конфигуриран и свързан, но всяка цел е изключена от таймер за устойчивост; предупреждението `[COMBO] Weighted selection: every target excluded before dispatch — …` посочва причините и оставащите секунди. Отговор `404 no_executable_targets` от същата комбинация означава, че не е бил задействан таймер за устойчивост (няма нищо за изпълнение или проверката за наличност е неуспешна за всеки акаунт). Вградено в `open-sse/services/combo/pinRecovery.ts` въз основа на изключванията, събрани в `targetResolution.ts`.
- Всички ключове за даден доставчик са пропуснати → проверете както състоянието на прекъсвача на веригата, така и `rateLimitedUntil`/`testStatus` на всяка връзка.
- Доставчикът остава трайно изключен след изтичането на прозореца за нулиране → кодът чете директно `state` вместо `getStatus()`/`canExecute()`.
- Един ключ е неуспешен, но останалите трябва да работят → предпочитайте период на изчакване за връзката пред прекъсвач на веригата.
- Само един модел е неуспешен → предпочитайте блокиране на модела пред период на изчакване за връзката.
- Състоянието трябва да се възстановява автоматично, но това не се случва → проверете за времеви печат в бъдещето и път за четене, който опреснява изтеклото състояние. Постоянните състояния изискват ръчни промени.

## Тестване на устойчивостта (Фаза 8 · Блок C)

Освен модулните тестове за логиката за устойчивост, три теста проверяват поведението по време на изпълнение при
реални условия на натоварване/отказ (всички са интеграционни/еженощни — никой не блокира PR заявки):

| Тест                                 | Какво                                                                                                                                                                                                                              | Изпълнение                                |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| Хаос                                 | Фиктивен upstream възел внася реално забавяне/нулиране/изтичане на времето/503; проверява дали прекъсвачът на веригата се отваря/възстановява и дали `checkFallbackError` класифицира 503 като възстановимо резервно превключване. | `RUN_CHAOS_INT=1 npm run test:chaos`      |
| Нарастване на heap паметта           | ~500 потока за `createSSEStream` при `--expose-gc`; тестът е неуспешен, ако heap паметта нарасне над зададения лимит (OOM защита #3069).                                                                                           | `npm run test:heap`                       |
| k6 тест за продължително натоварване | Продължително натоварване към `/api/monitoring/health`; прагове за p95/грешки.                                                                                                                                                     | `k6 run tests/load/k6-soak.js` (еженощно) |

Оркестрира се от `.github/workflows/nightly-resilience.yml` (cron + ръчно стартиране). При
стандартния `test:integration` тестовете за хаос и heap памет се пропускат автоматично (без `RUN_CHAOS_INT`/`--expose-gc`).
