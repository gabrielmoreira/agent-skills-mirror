Το OmniRoute διαθέτει τρεις διακριτούς αλλά συναφείς μηχανισμούς ανθεκτικότητας. Καθένας έχει διαφορετική εμβέλεια και σκοπό. Διατηρείτε τους ξεχωριστούς κατά την αποσφαλμάτωση της συμπεριφοράς δρομολόγησης.

## 1. Αυτόματος διακόπτης παρόχου

**Εμβέλεια:** ολόκληρος ο πάροχος (π.χ. `glm`, `openai`, `anthropic`).

**Σκοπός:** διακοπή αποστολής κίνησης σε έναν πάροχο που αποτυγχάνει επανειλημμένα σε επίπεδο ανάντη υπηρεσίας.

**Υλοποίηση:**

- Βασική κλάση: `src/shared/utils/circuitBreaker.ts`
- Διασύνδεση: `src/sse/handlers/chatHelpers.ts`, `src/sse/handlers/chat.ts`
- API κατάστασης: `GET /api/monitoring/health`
- API επαναφοράς: `POST /api/resilience/reset`
- Περιτυλίγματα: `open-sse/services/accountFallback.ts`
- Πίνακας βάσης δεδομένων: `domain_circuit_breakers`

**Καταστάσεις:**

- `CLOSED` — επιτρέπεται η κανονική κίνηση
- `DEGRADED` — η κίνηση εξακολουθεί να επιτρέπεται, αλλά παρακολουθούνται οι αυξημένες αποτυχίες του παρόχου
- `OPEN` — ο πάροχος αποκλείεται προσωρινά· η συνδυαστική δρομολόγηση τον παραλείπει
- `HALF_OPEN` — έληξε το χρονικό όριο επαναφοράς· επιτρέπεται ένα δοκιμαστικό αίτημα

**Διαμορφώσιμες προεπιλογές (`open-sse/config/constants.ts`, διαθέσιμες στο Πίνακας ελέγχου → Ρυθμίσεις → Ανθεκτικότητα):**

| Κλάση   | Υποβάθμιση στις | Άνοιγμα στις | Χρονικό όριο επαναφοράς |
| ------- | --------------- | ------------ | ----------------------- |
| OAuth   | 5 αποτυχίες     | 8 αποτυχίες  | 60s                     |
| API-key | 7 αποτυχίες     | 12 αποτυχίες | 30s                     |
| Τοπικός | παράγεται       | 2 αποτυχίες  | 15s                     |

Το `degradationThreshold` ελέγχει πότε ένας πάροχος εισέρχεται σε κατάσταση `DEGRADED`· το `failureThreshold` ελέγχει πότε ανοίγει και παραλείπεται. Τα προφίλ τοπικών παρόχων δεν είναι ακόμη διαθέσιμα στη σελίδα ρυθμίσεων Ανθεκτικότητας.

**Κωδικοί ενεργοποίησης:** μόνο καταστάσεις επιπέδου παρόχου `[408, 500, 502, 503, 504]`. ΜΗΝ ενεργοποιείτε τον διακόπτη για σφάλματα επιπέδου λογαριασμού (τα περισσότερα 401/403/429 — αυτά ανήκουν στην περίοδο αναμονής ή στο κλείδωμα).

**Παθητική ανάκαμψη:** όταν λήξει η κατάσταση `OPEN`, τα `getStatus()`, `canExecute()`, `getRetryAfterMs()` ανανεώνουν την κατάσταση σε `HALF_OPEN`. Δεν απαιτείται χρονομετρητής παρασκηνίου.

### Προαιρετική καθολική περίοδος αναμονής παρόχου (πύλη χρονικού παραθύρου)

Ένα τέταρτο, **προαιρετικό** επίπεδο (`PROVIDER_COOLDOWN_ENABLED`, από προεπιλογή **απενεργοποιημένο**) διατηρεί μια
διααιτηματική μνήμη των παρόχων που αποτυγχάνουν στο
`open-sse/services/providerCooldownTracker.ts`, η οποία χρησιμοποιείται κατά την επίλυση συνδυαστικών στόχων,
ώστε διαδοχικά συνδυαστικά αιτήματα να σταματούν να επανεξετάζουν έναν πάροχο που μόλις
απέτυχε. Οι καταχωρίσεις επιπέδου παρόχου ακολουθούν την πύλη χρονικού παραθύρου `PROVIDER_PROFILES`:

| Προφίλ     | ενεργοποιείται μετά από (`providerFailureThreshold`) | εντός (`providerFailureWindowMs`) | αναμονή για (`providerCooldownMs`) |
| ---------- | ---------------------------------------------------: | --------------------------------: | ---------------------------------: |
| OAuth      |                                                 `10` |                           `15min` |                             `5min` |
| Κλειδί API |                                                 `15` |                           `30min` |                            `10min` |

Κάτω από το όριο, ο πάροχος **δεν** θεωρείται ότι βρίσκεται σε περίοδο αναμονής· μια επιτυχία εκκαθαρίζει
το χρονικό παράθυρο. Αντίθετα, οι καταχωρίσεις επιπέδου σύνδεσης (`provider:connectionId`) διατηρούν
την εκθετική υποχώρηση `minRetryCooldownMs → maxRetryCooldownMs`. Παρακάμψεις:
`OMNIROUTE_PROVIDER_BREAKER_{OAUTH,API_KEY}_{FAILURE_THRESHOLD,FAILURE_WINDOW_MS,COOLDOWN_MS}`.
Προστασία από παλινδρόμηση: `tests/unit/provider-cooldown-window-gate.test.ts`.

## 2. Χρόνος αναμονής σύνδεσης

**Πεδίο εφαρμογής:** μία σύνδεση/ένας λογαριασμός/ένα κλειδί παρόχου.

**Σκοπός:** παράκαμψη ενός προβληματικού κλειδιού, ενώ οι άλλες συνδέσεις για τον ίδιο πάροχο συνεχίζουν να εξυπηρετούν αιτήματα.

**Υλοποίηση:**

- Επισήμανση ως μη διαθέσιμου: `src/sse/services/auth.ts::markAccountUnavailable()`
- Επιλογή: `getProviderCredentials*` στο ίδιο αρχείο
- Υπολογισμός χρόνου αναμονής: `open-sse/services/accountFallback.ts::checkFallbackError()`
- Ρυθμίσεις: `src/lib/resilience/settings.ts`

**Πεδία ανά σύνδεση:**

- `rateLimitedUntil` — χρονική σήμανση έως τη λήξη του χρόνου αναμονής
- `testStatus: "unavailable"`
- `lastError`, `lastErrorType`, `errorCode`
- `backoffLevel` — μετρητής εκθετικής οπισθοχώρησης

**Προεπιλεγμένοι χρόνοι αναμονής:**

- Βάση OAuth: 5s
- Βάση κλειδιού API: 3s
- 429 κλειδιού API: προτιμώνται οι κεφαλίδες `Retry-After`/επαναφοράς της ανάντη υπηρεσίας ή αναλύσιμο κείμενο επαναφοράς
- Οπισθοχώρηση: `baseCooldownMs * 2 ** failureIndex`

**Προστασία από ταυτόχρονες μαζικές επαναλήψεις:** αποτρέπει τις ταυτόχρονες αποτυχίες από το να παρατείνουν υπερβολικά τον χρόνο αναμονής ή να αυξήσουν δύο φορές το `backoffLevel`.

**Τερματικές καταστάσεις (ΟΧΙ χρόνοι αναμονής):**

- `banned` — ορίζεται από την ανίχνευση απαγορευμένης λέξης-κλειδιού / αποκλεισμού λογαριασμού (βλ. [BAN_DETECTION](../security/BAN_DETECTION.md)) και από τρεις διαδοχικές ανάντη απορρίψεις ανά αίτημα (`request_rejected`, π.χ. Anthropic OAuth 403 "Request not allowed" — `open-sse/services/requestRejectedStreak.ts`)· μία μόνο απόρριψη απλώς θέτει τη σύνδεση σε χρόνο αναμονής
- `expired` (μεταβαίνει σε τερματική κατάσταση μετά από περιορισμένο αριθμό επαναλήψεων — `EXPIRED_RETRY_MAX = 3` με εκθετική οπισθοχώρηση — ώστε τα παροδικά σφάλματα OAuth να μπορούν να αποκατασταθούν αυτόματα προτού ο λογαριασμός απενεργοποιηθεί οριστικά)
- `credits_exhausted`

Αυτές παραμένουν μέχρι να αλλάξουν τα διαπιστευτήρια ή να τις επαναφέρει ένας χειριστής. Μην αντικαθιστάτε τις τερματικές καταστάσεις με κατάσταση παροδικού χρόνου αναμονής.

**Οκνηρή ανάκτηση:** όταν παρέλθει το `rateLimitedUntil`, η σύνδεση καθίσταται ξανά επιλέξιμη. Μετά από επιτυχή χρήση, το `clearAccountError()` εκκαθαρίζει όλα τα πεδία σφάλματος.

### Συνάφεια συνεδρίας (#7274)

**Πεδίο εφαρμογής:** μία συνεδρία πελάτη (κεφαλίδα `X-Session-Id` / `x-codex-session-id` / `x-omniroute-session`) καρφιτσωμένη σε μία σύνδεση, για **οποιονδήποτε** πάροχο.

**Σκοπός:** διατήρηση ενός πράκτορα πολλαπλών γύρων (Claude Code, aider, προσαρμοσμένοι πράκτορες) στον ίδιο λογαριασμό μεταξύ αιτημάτων, μειώνοντας την απώλεια περιβάλλοντος μεταξύ λογαριασμών και τα επαναλαμβανόμενα 429 ψυχρής εκκίνησης σε παρόχους με κατάσταση συνεδρίας ανά λογαριασμό.

**Υλοποίηση:**

- Επίλυση TTL: `src/sse/services/sessionAffinityPin.ts::resolveSessionAffinityTtlMs()`
- Επιλογή/δημιουργία καρφιτσώματος: `src/sse/services/sessionAffinityPin.ts::selectSessionAffinityConnection()`
- Εξαγωγή κεφαλίδας (γενική, για οποιονδήποτε πάροχο): `src/sse/services/auth.ts::extractSessionAffinityKey()`
- Μόνιμος πίνακας καρφιτσωμάτων: `sessionAccountAffinity` (`src/lib/db/sessionAccountAffinity.ts`)
- Ρύθμιση: `sessionAffinityTtlMs` (καθολικό TTL σε ms, το `0` το απενεργοποιεί) — `src/lib/db/settings.ts`. Μετονομάστηκε από το αποκλειστικό για το Codex `codexSessionAffinityTtlMs` μέσω της μετεγκατάστασης `124_generic_session_affinity_ttl.sql`, η οποία μεταφέρει οποιοδήποτε προηγουμένως διαμορφωμένο TTL του Codex ως τη νέα προεπιλογή.

Πριν από το #7274, το `resolveSessionAffinityTtlMs()` επέστρεφε αμέσως `0` για κάθε πάροχο εκτός του `codex`, επομένως η ρύθμιση TTL (και οι κεφαλίδες συνεδρίας) δεν είχαν καμία επίδραση οπουδήποτε αλλού, παρόλο που ο μηχανισμός καρφιτσώματος και η εξαγωγή κεφαλίδων ήταν ήδη ανεξάρτητα από τον πάροχο. Η διόρθωση αφαίρεσε αυτήν την πρόωρη επιστροφή· το TTL εφαρμόζεται πλέον ομοιόμορφα σε κάθε πάροχο, μόλις οριστεί καθολικά σε τιμή μεγαλύτερη από `0`.

Οι τρεις κεφαλίδες συνάφειας συνεδρίας δεν προωθούνται ποτέ στην ανάντη υπηρεσία — οι εκτελεστές δημιουργούν τις δικές τους ανάντη κεφαλίδες από την αρχή αντί να διαβιβάζουν τις κεφαλίδες του πελάτη, επομένως αυτό παραμένει μόνο ένα εσωτερικό αναγνωριστικό συσχέτισης.

### Αποκλειστικές μισθώσεις συνδέσεων διαχειριζόμενων συνεδριών

**Πεδίο εφαρμογής:** ένας ενεργός διαχειριζόμενος πελάτης/μία ενεργή διαχειριζόμενη συνεδρία HTTP κατέχει μία επιλέξιμη σύνδεση OmniRoute.

**Σκοπός:** παροχή ανθεκτικής αποκλειστικής κατοχής σύνδεσης για πελάτες που χρειάζονται έναν αυστηρό
φραγμό δρομολόγησης μεταξύ αιτημάτων. Αυτό διαφέρει από τη συνάφεια συνεδρίας, η οποία αποτελεί ήπια προτίμηση συνέχειας:
μια αποκλειστική μίσθωση διατηρεί την κατάσταση κύκλου ζωής στο SQLite, επιβάλλει καθολική μοναδικότητα ενεργού κατόχου και
ενεργής σύνδεσης και απορρίπτει μια παρωχημένη γενιά πριν από την αποστολή προς τον πάροχο.

Η δυνατότητα ενεργοποιείται προαιρετικά ανά κλειδί API. Ένα διαχειριζόμενο κλειδί πρέπει να διαθέτει το πεδίο εφαρμογής `lease:exclusive` και μια
ρητή, μη κενή λίστα `allowedConnections`. Οποιοσδήποτε πελάτης HTTP μπορεί να χρησιμοποιήσει το τελικό σημείο κύκλου ζωής· δεν
απαιτείται όνομα πελάτη, user-agent, πάροχος, μέθοδος OAuth ή μοντέλο. Η μίσθωση κατέχει μια σύνδεση,
όχι ένα μοντέλο, επομένως μια αλλαγή μοντέλου διατηρεί τη δέσμευση όσο η σύνδεση παραμένει κανονικά
επιλέξιμη. Οι συνήθεις κανόνες μοντέλου, ποσόστωσης, εύρυθμης λειτουργίας, χρόνου αναμονής και λίστας επιτρεπόμενων συνδέσεων παραμένουν δεσμευτικοί και μπορούν
να μεταφέρουν την ίδια γενιά σε άλλη ελεύθερη επιλέξιμη σύνδεση.

Ο κύκλος ζωής είναι `POST /api/v1/session-leases` με ενέργειες JSON `acquire`, `renew` και `release`.
Τα διαχειριζόμενα αιτήματα εξαγωγής συμπερασμάτων παρέχουν την αδιαφανή τιμή `X-OmniRoute-Lease-Owner` και την ακριβή
`X-OmniRoute-Lease-Generation`. Ο κάτοχος χρησιμοποιεί το πρόθεμα `vlo_` ακολουθούμενο από 43 χαρακτήρες base64url· αποθηκεύεται μόνο
ο κατακερματισμός SHA-256. Κάθε τελικός φραγμός αποστολής δεσμεύει επίσης το αναγνωριστικό του επαληθευμένου κλειδιού API και
το αναγνωριστικό της ενεργής σύνδεσης. Οι κεφαλίδες ελέγχου μίσθωσης αφαιρούνται από τα αρχεία καταγραφής, τα διατηρούμενα στιγμιότυπα αιτημάτων και
τις κεφαλίδες των ανάντη εκτελεστών.

Εάν η συνήθης δρομολόγηση διαθέτει επιλέξιμες διαχειριζόμενες υποψήφιες συνδέσεις, αλλά κάθε ελεύθερη υποψήφια σύνδεση καταλαμβάνεται από μια
ξένη ενεργή μίσθωση, το OmniRoute επιστρέφει HTTP `429`, κωδικό μη διαθεσιμότητας χωρητικότητας μίσθωσης, μια
κατάσταση αναμονής χωρητικότητας και ένα περιορισμένο `Retry-After` που προκύπτει από την ενωρίτερη σχετική λήξη.
Η συνήθης απουσία επιλέξιμων συνδέσεων δεν αποτελεί διένεξη μίσθωσης και διατηρεί την υπάρχουσα σημασιολογία σφαλμάτων δρομολόγησης.

Οι σχετικοί μηχανισμοί παραμένουν διακριτοί:

- Η κατάληψη συνεδρίας OAuth είναι μια ήπια κατανομή εντός της διεργασίας για λογαριασμούς OAuth.
- Οι σημαφόροι λογαριασμών χορηγούν άδειες ταυτόχρονων αιτημάτων και τερματίζονται όταν ολοκληρωθεί ένα αίτημα.
- Οι αποκλειστικές μισθώσεις διαχειριζόμενων συνεδριών συνιστούν ανθεκτική κατοχή κύκλου ζωής με φραγμό γενιάς.

## 3. Αποκλεισμός μοντέλου

**Εμβέλεια:** τριάδα παρόχου + σύνδεσης + μοντέλου.

**Εμβέλεια κλειδιού ανά κατάσταση:** η κατάσταση αποτυχίας καθορίζει σε ποιο κλειδί εγγράφεται ένας αποκλεισμός
(`resolveLockoutScope()` στο `open-sse/services/accountFallback/exactModelLock.ts`):

- `429` / `403` / `402` — ένδειξη ορίου χρήσης ή δικαιώματος πρόσβασης — κλειδώνουν την **οικογένεια ορίου χρήσης**:
  για το codex, ολόκληρη την εμβέλεια `codex` / `spark` (κάθε μοντέλο `gpt-5*` της
  σύνδεσης), ενώ για άλλους παρόχους το `getQuotaScopedModelForProvider()`.
- Το `404` κλειδώνει το βασικό μοντέλο (το `getModelLockKey()` περιορίζει το `not_found`).
- Οποιαδήποτε άλλη κατάσταση — αποτυχίες μεταφοράς/διακομιστή `5xx` και το
  συνθετικό `502` του ίδιου του OmniRoute από την επικύρωση ποιότητας — κλειδώνει μόνο
  την **ακριβή** πλειάδα παρόχου/σύνδεσης/μοντέλου. Μια προβληματική ροή σε ένα μοντέλο δεν αποτελεί ένδειξη
  για το όριο χρήσης του λογαριασμού· πριν από αυτόν τον κανόνα, μία κενή απόκριση στο
  `codex/gpt-5.6-luna` αφαιρούσε κάθε μοντέλο `gpt-5*` αυτής της σύνδεσης από τη
  δρομολόγηση για 2–30 λεπτά (με κλιμάκωση), ενώ το όριο χρήσης της παρέμενε ανέπαφο.
- Η ρητή επιλογή `scope` του καλούντος υπερισχύει πάντα (το Antigravity περνά `"exact"`).

**Σκοπός:** να αποφεύγεται η απενεργοποίηση ολόκληρης σύνδεσης όταν μόνο ένα μοντέλο δεν είναι διαθέσιμο ή υπόκειται σε περιορισμό χρήσης.

**Παραδείγματα:**

- Πάροχοι με όριο χρήσης ανά μοντέλο που επιστρέφουν 429
- Τοπικοί πάροχοι που επιστρέφουν 404 για ένα μοντέλο που λείπει
- Αποτυχίες δικαιωμάτων πρόσβασης ειδικές για λειτουργία/μοντέλο ενός παρόχου (π.χ. λειτουργίες Grok)

**Υλοποίηση:** `open-sse/services/accountFallback.ts` — `lockModel()`, `clearModelLock()`, `getAllModelLockouts()`.

### Πίνακας εργαλείων περιόδων αναμονής μοντέλων (v3.8.0)

Διεπαφή χρήστη: Ρυθμίσεις → Περίοδοι αναμονής μοντέλων (`src/app/(dashboard)/dashboard/settings/components/ModelCooldownsCard.tsx`)

Παραθέτει τους ενεργούς αποκλεισμούς με: πάροχο, σύνδεση, μοντέλο, αιτία, expiresAt. Οι διαχειριστές μπορούν να επανενεργοποιήσουν χειροκίνητα ένα μοντέλο από την κάρτα.

**REST API:**

- `GET /api/resilience/model-cooldowns` — παράθεση ενεργών αποκλεισμών
- `DELETE /api/resilience/model-cooldowns` — χειροκίνητη επανενεργοποίηση. Σώμα: `{provider, connection, model}`. Έλεγχος ταυτότητας: διαχείριση.

### Διεπαφή ρυθμίσεων αποκλεισμού + ανάκτηση με εξασθένηση κατά την επιτυχία (v3.8.23)

Ο αποκλεισμός μοντέλου μετατράπηκε από μόνιμα ενεργή, ενσωματωμένη συμπεριφορά σε μια πλήρως παραμετροποιήσιμη
λειτουργία προαιρετικής ενεργοποίησης, με δική της κάρτα ρυθμίσεων και μηχανισμό αυτοΐασης για την ανάκτηση.

**Κάρτα ρυθμίσεων:** Ρυθμίσεις → Αποκλεισμός μοντέλου
(`src/app/(dashboard)/dashboard/settings/components/ModelLockoutCard.tsx`).
Αυτή είναι **διαφορετική** από την παραπάνω `ModelCooldownsCard` μόνο για ανάγνωση (η οποία απλώς
_παραθέτει_ τους ενεργούς αποκλεισμούς) — η νέα κάρτα _διαμορφώνει τις παραμέτρους_. Οι προεπιλογές
βρίσκονται στο `DEFAULT_MODEL_LOCKOUT_SETTINGS`
(`src/lib/resilience/modelLockoutSettings.ts`):

| Ρύθμιση                 | Προεπιλογή                       | Σημασία                                                                          |
| ----------------------- | -------------------------------- | -------------------------------------------------------------------------------- |
| `enabled`               | `false`                          | Κύριος διακόπτης — ο αποκλεισμός μοντέλου είναι **ανενεργός από προεπιλογή**.    |
| `errorCodes`            | `[403, 404, 429, 502, 503, 504]` | Καταστάσεις ανάντη υπηρεσίας που υπολογίζονται ως αποτυχία με εμβέλεια μοντέλου. |
| `baseCooldownMs`        | `120_000` (120 δευτ.)            | Αρχική διάρκεια αποκλεισμού για την πρώτη αποτυχία.                              |
| `maxCooldownMs`         | `1_800_000` (30 λεπτά)           | Ανώτατο όριο της κλιμακούμενης περιόδου αναμονής.                                |
| `maxBackoffSteps`       | `10`                             | Μέγιστος αριθμός βημάτων κλιμάκωσης εκθετικής υποχώρησης.                        |
| `useExponentialBackoff` | `true`                           | Αν οι επαναλαμβανόμενες αποτυχίες κλιμακώνουν εκθετικά την περίοδο αναμονής.     |

Οι ρυθμίσεις διατηρούνται μέσω του κανονικού χώρου αποθήκευσης ρυθμίσεων και επικυρώνονται μέσω του
σχήματος ρυθμίσεων ανθεκτικότητας· η κάρτα περιορίζει τα `baseCooldownMs`/`maxCooldownMs`
(με `maxCooldownMs ≥ baseCooldownMs`) και το `maxBackoffSteps`.

**Ανάκτηση με εξασθένηση κατά την επιτυχία:** η ανάκτηση **δεν** βασίζεται αποκλειστικά στη λήξη χρονομέτρου. Μια υγιής
απόκριση μειώνει σταδιακά τον αριθμό αποτυχιών του μοντέλου, ώστε ένα μοντέλο που ανέκαμψε
εντός του χρονικού παραθύρου να σταματά να κλιμακώνεται (και να εκκαθαρίζεται) πριν από τη λήξη του χρονομέτρου του. Σε έναν επιτυχή
συνδυαστικό στόχο, το `open-sse/services/combo.ts` καλεί το `decayModelFailureCount()`
(`open-sse/services/accountFallback.ts`), το οποίο **υποδιπλασιάζει** το αποθηκευμένο
`failureCount` (`Math.floor(failureCount / 2)`), ενώ όταν αυτό φτάσει στο `0`, η καταχώριση αποκλεισμού
διαγράφεται πλήρως. Το αντίστοιχο `recordModelLockoutFailure()`
αυξάνει τον αριθμό (και κλιμακώνει την περίοδο αναμονής) για αποτυχίες εντός του
παραθύρου κλιμάκωσης. Αυτή η εξασθένηση κατά την επιτυχία λειτουργεί επιπλέον της απλής λήξης χρονομέτρου —
οποιαδήποτε από τις δύο διαδρομές μπορεί να επανενεργοποιήσει ένα μοντέλο.

**Κατάσταση:** οι αποκλεισμοί διατηρούνται **στη μνήμη** (`Map` ανά διεργασία με καταχωρίσεις
`ModelLockoutEntry` που χρησιμοποιούν ως κλειδί το `provider:connectionId:model`, ενώ οι αποκλεισμοί ακριβούς εμβέλειας χρησιμοποιούν
`provider:connectionId:exact:model`) και δεν αποθηκεύονται μόνιμα
στη βάση δεδομένων — χάνονται κατά την επανεκκίνηση. Οι _ρυθμίσεις_ αποθηκεύονται μόνιμα· η ενεργή
_κατάσταση_ αποκλεισμού είναι προσωρινή.

## 4. Έλεγχος ταυτοχρονισμού κοινόχρηστου ορίου χρήσης (v3.8.36)

Οι λογαριασμοί συνδρομής (GLM, MiniMax κ.λπ.) συχνά δέχονται μόνο ~1–3 ταυτόχρονα
αιτήματα· η υπέρβαση αυτού του ορίου προκαλεί αποκρίσεις 429 και περιόδους αναμονής. Αυτό είναι ιδιαίτερα έντονο σε
συνδυασμούς **quota-share** (`qtSd/…`), όπου πολλά κλειδιά API μοιράζονται έναν ανάντη
λογαριασμό. Τρία επίπεδα αποτρέπουν την υπερφόρτωση ενός κοινόχρηστου λογαριασμού.

### Όριο ταυτοχρονισμού ανά σύνδεση (`max_concurrent`)

Κάθε σύνδεση παρόχου μπορεί να δηλώνει ένα ανώτατο όριο `max_concurrent`
(`provider_connections.max_concurrent`, το οποίο ορίζεται στο παράθυρο σύνδεσης / API / DB).
Αφήστε το κενό για να μην υπάρχει όριο. Αυτή είναι η μοναδική ρύθμιση που ελέγχει το επίπεδο σειριοποίησης
παρακάτω — ορίστε την σύμφωνα με τον πραγματικό ταυτοχρονισμό του λογαριασμού (π.χ. GLM ~1, MiniMax ~2).

### Σειριοποίηση αιτημάτων quota-share

Όταν μια δρομολόγηση quota-share στοχεύει μια σύνδεση που δηλώνει θετικό
`max_concurrent`, τα ταυτόχρονα αιτήματα προς αυτόν τον **λογαριασμό** σειριοποιούνται μέσω ενός
σηματοφόρου ανά σύνδεση (κλειδί `qsconn:<connectionId>`): τα επιπλέον αιτήματα **περιμένουν στην
ουρά** αντί να υπερφορτώνουν τον λογαριασμό. Λειτουργεί με αρχή **fail-open** — αν η ουρά
είναι κορεσμένη ή λήξει το χρονικό όριο, το αίτημα συνεχίζει χωρίς θέση αντί να απορρίπτεται ποτέ ένα
αίτημα που μπορεί να δρομολογηθεί. Ενεργοποιήστε ή απενεργοποιήστε το στη διαδρομή **Ρυθμίσεις → Ανθεκτικότητα → Ταυτοχρονισμός ανά σύνδεση
quota-share** (`resilienceSettings.quotaShareConcurrencyLimit.enabled`, ενεργοποιημένο από
προεπιλογή). Χωρίς όριο `max_concurrent`, η συμπεριφορά παραμένει αμετάβλητη.

> Η πύλη δρομολόγησης quota-share (`selectQuotaShareTarget`, DRR + P2C) είναι και η ίδια
> fail-open και απλώς _υποβαθμίζει την προτεραιότητα_ μιας σύνδεσης που έχει φτάσει το όριό της — με ένα
> σύνολο μίας μόνο σύνδεσης δεν μπορεί να επιβάλει αυστηρό όριο, επομένως αυτός ο σηματοφόρος είναι εκείνος που στην πράξη
> συγκρατεί την πλημμυρίδα αιτημάτων.

### Επανάληψη με επίγνωση της περιόδου αναμονής συνδυασμών

Για κάθε στρατηγική συνδυασμού (όταν είναι ενεργοποιημένη), ένα αίτημα που θα οριστικοποιούσε μια απόκριση 429
λόγω μιας ΣΥΝΤΟΜΗΣ παροδικής περιόδου αναμονής περιμένει μέχρι αυτή να λήξει και δρομολογείται ξανά αντί να
επιστρέψει την απόκριση 429 — αυτό καλύπτει χρονικά παράθυρα TPM/RPM τύπου Gemini (~60s retry-after)
σε συνδυασμούς πολλών μοντέλων, π.χ. όταν και οι δύο προορισμοί ενός συνδυασμού 2 μοντέλων φτάνουν ένα όριο ρυθμού
ανά μοντέλο. Περιορίζεται από το `comboCooldownWait` (`enabled`, `maxWaitMs`, `maxAttempts`,
`budgetMs`) στη διαδρομή **Ρυθμίσεις → Ανθεκτικότητα**. Δεν περιμένει ποτέ για λόγους `quota_exhausted`
(κλειδωμένο έως τα μεσάνυχτα), ελέγχου ταυτότητας ή μη εύρεσης.

## 5. Έλεγχος αποδοχής στην ουρά αιτημάτων (v3.8.49 · ζήτημα #6593)

**Πεδίο εφαρμογής**: η τοπική ουρά περιορισμού ρυθμού ανά πάροχο+σύνδεση (`open-sse/services/rateLimitManager.ts`,
η οποία υποστηρίζεται από το Bottleneck), ένα επίπεδο κάτω από τους τρεις παραπάνω μηχανισμούς.

**Το `maxWaitMs` είναι μια παλαιότερη, διατηρούμενη ονομασία για τη λήξη εκτέλεσης.**
Το `resilienceSettings.requestQueue.maxWaitMs` μεταβιβάζεται στο Bottleneck ως `expiration`
εργασίας, του οποίου ο χρονομετρητής ξεκινά μόνο μετά τη δρομολόγηση. Επομένως, περιορίζει
την εκτέλεση που διαχειρίζεται ο περιοριστής και όχι τον χρόνο παραμονής στην τοπική ουρά. Η λήξη
εμφανίζεται ως αξιόπιστο τοπικό `code: "RATE_LIMIT_EXECUTION_TIMEOUT"` (HTTP 504)·
η προηγούμενη ονομασία κωδικού χρονικού ορίου ουράς γίνεται αποδεκτή μόνο για αξιόπιστη εσωτερική
συμβατότητα προς τα πίσω. Η προεπιλογή είναι 15000ms· παρακάμψτε την μέσω
`RATE_LIMIT_MAX_WAIT_MS` (μεταβλητή περιβάλλοντος) ή από τον πίνακα ελέγχου (**Ρυθμίσεις → Ανθεκτικότητα**,
ανώτατο όριο UI 1–30000ms). Η παραμονή στην ουρά δεν έχει χρονική προθεσμία· χρησιμοποιήστε το
`maxQueueDepth` παρακάτω για να περιορίσετε τους αιτούντες που βρίσκονται στην ουρά.

**`maxQueueDepth` — προαιρετικό όριο αποδοχής (νέο).** Το `resilienceSettings.requestQueue.maxQueueDepth`
περιορίζει πόσα αιτήματα μπορούν να βρίσκονται ταυτόχρονα στην ουρά (χωρίς να έχουν ακόμη δρομολογηθεί) για έναν
πάροχο+σύνδεση. Όταν η ουρά περιέχει ήδη `maxQueueDepth`
αιτήματα, ένα νέο αίτημα απορρίπτεται άμεσα με ένα τυποποιημένο σφάλμα
`code: "RATE_LIMIT_QUEUE_FULL"` **πριν** φτάσει ποτέ στο `limiter.schedule()`
— επομένως, η απόρριψη έχει χαμηλό κόστος και πραγματοποιείται πριν από οποιαδήποτε μεταγενέστερη
συμπίεση / μετάφραση προτροπής για το συγκεκριμένο αίτημα. Προεπιλογή `0` =
απενεργοποιημένο, διατηρώντας την υπάρχουσα συμπεριφορά ουράς χωρίς όριο· επιτρεπόμενο εύρος 0–100000.
Παρακάμψτε το μέσω `RATE_LIMIT_MAX_QUEUE_DEPTH` (μεταβλητή περιβάλλοντος) ή
`resilienceSettings.requestQueue.maxQueueDepth` (τροποποίηση μέσω πίνακα ελέγχου/API).

Ο ίδιος ο έλεγχος αποδοχής είναι μια αμιγής συνάρτηση
(`open-sse/services/rateLimitManager/admission.ts::checkQueueAdmission`), ώστε
να μπορεί να ελεγχθεί με δοκιμές μονάδας χωρίς πραγματικό περιοριστή Bottleneck.

> Το RFC που άνοιξε το #6593 πρότεινε επίσης μια σημαία `bypassCompressionOnRateLimit`.
> Η διοχέτευση `open-sse/services/compression/` αυτού του αποθετηρίου αφορά τη
> συμπίεση προτροπής/περιβάλλοντος στο εξερχόμενο αίτημα LLM (`chatCore.ts`,
> γύρω από το τμήμα `resolveCompressionSettings`/`selectCompressionStrategy`)
> και όχι τη συμπίεση απόκρισης HTTP σε παραγόμενα σώματα 429 — δεν υπάρχει
> αντίστοιχη διαδρομή κώδικα για μια κυριολεκτική σημαία παράκαμψης. Αυτό το βήμα συμπίεσης προτροπής
> εκτελείται επίσης επί του παρόντος _πριν_ από το `withRateLimit()` στη διοχέτευση αιτημάτων, επομένως
> η αναδιάταξη ώστε να παραλείπεται σε περίπτωση απόρριψης λόγω πλήρους ουράς αποτελεί μια ξεχωριστή και μεγαλύτερη
> αλλαγή από το πεδίο εφαρμογής αυτού του ζητήματος· **δεν** υλοποιήθηκε σκόπιμα
> εδώ και παραμένει ως μελλοντική εργασία, εφόσον το όφελος εξοικονόμησης CPU αξίζει τον
> κίνδυνο της αναδιάταξης.

## 6. Μηχανισμός επιτήρησης ρυθμαπόδοσης αργής ροής (#9709)

Ο προαιρετικός μηχανισμός προστασίας `resilienceSettings.streamRecovery.throughputWatchdog` εντοπίζει
μια upstream υπηρεσία που εξακολουθεί να στέλνει τμήματα δεδομένων, αλλά παράγει έξοδο βοηθού κάτω από τον
διαμορφωμένο ρυθμό χρήσιμης εξόδου. Είναι σκόπιμα διακριτός από το χρονικό όριο αδράνειας:
τα heartbeat και τα μεταδεδομένα δεν επαναφέρουν κανέναν από τους δύο χρονομετρητές και δεν υπολογίζονται ως πρόοδος. Είναι επίσης
διακριτός από την ανελαστική προθεσμία προσπάθειας (#9153), η οποία παραμένει ένα απόλυτο ανώτατο όριο
ασφαλείας ανεξάρτητα από την ποιότητα της εξόδου.

Ο μηχανισμός επιτήρησης απαιτεί μια περίοδο προθέρμανσης, ακολουθούμενη από ένα πλήρες κυλιόμενο παράθυρο, προτού
μπορέσει να διακόψει. Μετρά τις διαφορές κειμένου από συμβάντα εξόδου των Chat Completions και Responses API
(μια συντηρητική προσέγγιση βάσει byte UTF-8), αγνοεί συμβάντα που περιέχουν μόνο στοιχεία χρήσης ή είναι κενά και
αναστέλλει την αξιολόγηση όσο βρίσκονται σε εξέλιξη συμβάντα κλήσης εργαλείων ή συλλογισμού. Είναι απενεργοποιημένος
από προεπιλογή και μπορεί να ενεργοποιηθεί με `STREAM_THROUGHPUT_WATCHDOG_ENABLED=true`· το
παράθυρο, η προθέρμανση, ο ελάχιστος ρυθμός και η ελάχιστη μετρήσιμη έξοδος οριοθετούνται από το
κανονικό επίπεδο κανονικοποίησης των ρυθμίσεων ανθεκτικότητας.

Όταν είναι ενεργοποιημένη, μια διακοπή από τον μηχανισμό επιτήρησης εφαρμόζεται μόνο στην ενεργή upstream προσπάθεια. Πριν
από οποιαδήποτε byte ορατά στον πελάτη, η υπάρχουσα διαδρομή έγκαιρης ανάκτησης στον ίδιο λογαριασμό μπορεί να ανοίξει ξανά
την προσπάθεια. Μετά την οριστικοποίηση, η ροή δεν αναπαράγεται ποτέ στα τυφλά· μόνο η υπάρχουσα
σύμβαση ασφαλούς συνέχισης στο μέσο της ροής μπορεί να συρράψει ένα επίθημα. Η ολοκλήρωση παραμένει
μίας εκτέλεσης, ώστε η λογιστική χρήσης και η αποδέσμευση του semaphore να μην επαναλαμβάνονται.

## 7. Επαναδιατύπωση Upstream Κατάστασης (εσφαλμένα διατυπωμένα σφάλματα ορίου χρήσης)

**Πεδίο εφαρμογής:** μία upstream πύλη που αναφέρει προσωρινή εξάντληση ορίου χρήσης με εσφαλμένη HTTP κατάσταση.

**Σκοπός:** διόρθωση μιας παραπλανητικής κατάστασης ΠΡΙΝ από την ταξινόμηση, ώστε οι downstream καταναλωτές (μηχανισμός fallback, συγκέντρωση combo, απόκριση προς τον πελάτη) να βλέπουν την πραγματική, επαναλήψιμη φύση της αποτυχίας.

Ορισμένες πύλες σηματοδοτούν την ΠΡΟΣΩΡΙΝΗ εξάντληση ορίου χρήσης με μια μη επαναλήψιμη HTTP
κατάσταση. Το `agentrouter.org` επιστρέφει `403` (μερικές φορές `400`) με κινεζικό σώμα
(`用户额度不足` / `额度不足`) αντί για το τυπικό `429`. Πελάτες όπως το Claude
Code αντιμετωπίζουν το `403` ως μόνιμο και διακόπτουν τη συνεδρία, ενώ χωρίς διόρθωση
ο μηχανισμός fallback θα το ταξινομούσε ως `AUTH_ERROR` αντί για συμβάν ορίου
χρήσης.

**Υλοποίηση:**

- Μητρώο + αντιστοιχιστής: `open-sse/config/upstreamStatusRestatement.ts` — μια
  λίστα κανόνων ανά πάροχο (`{id, fromStatuses, toStatus, textMarkers,
excludeMarkers, defaultRetryAfterMs}`), οι οποίοι αντιστοιχίζονται μέσω του `applyStatusRestatement()`.
- Σημείο κλήσης: το μπλοκ `providerFailure:` στο `open-sse/handlers/chatCore.ts`
  (περίπου στη γραμμή 3654), αμέσως αφού το `parseUpstreamError()` αναλύσει μια upstream
  απόκριση με κατάσταση σφάλματος HTTP (`!providerResponse.ok`) και πριν εκτελεστεί οποιαδήποτε
  ταξινόμηση, ώστε κάθε downstream καταναλωτής να βλέπει τη διορθωμένη
  κατάσταση. Τα σφάλματα που είναι ενσωματωμένα σε μια ροή SSE με `200` ακολουθούν μια ξεχωριστή,
  μεταγενέστερη διαδρομή ανάλυσης ροής και **δεν** καλύπτονται επί του παρόντος από αυτό το hook — ένας
  γνωστός περιορισμός, ο οποίος δεν είναι ακόμη απαραίτητος για την εσφαλμένη κατάσταση του agentrouter (η οποία
  εμφανίζεται ως κατάσταση σφάλματος HTTP).
- Καταλληλότητα για επανάληψη: το `429` περιλαμβάνεται στο `RETRY_AFTER_ELIGIBLE_STATUSES`
  (`open-sse/services/combo/unavailableRetryGate.ts`), επομένως ένα επαναδιατυπωμένο σφάλμα
  φέρει ένα πραγματικό παράθυρο επανάληψης αντί να εμφανίζεται ως ανενεργό `403`.
- Το συνθετικό `60s` του `defaultRetryAfterMs` (`upstreamStatusRestatement.ts`)
  είναι μόνο αυτό που γνωστοποιεί η επαναδιατυπωμένη απόκριση στον **πελάτη**· δεν αποτελεί το ίδιο
  την εσωτερική διάρκεια cooldown/αποκλεισμού της σύνδεσης — αυτή διέπεται
  ξεχωριστά από τον εκάστοτε μηχανισμό που χειρίζεται πραγματικά το επαναδιατυπωμένο σφάλμα
  (το κλιμακούμενο backoff του Connection Cooldown, §2, με βάση `3s` για παρόχους
  API key· ή το Model Lockout, §3, για παρόχους ορίου χρήσης ανά μοντέλο όπως ο
  agentrouter). Ο δρομολογητής μπορεί να καταστεί κατάλληλος για εσωτερική επανάληψη νωρίτερα
  από το παράθυρο των 60s που γνωστοποιεί στον πελάτη — πρόκειται για σκόπιμο περιθώριο,
  όχι για σφάλμα.

Τα μόνιμα σφάλματα (το `无权访问模型` του agentrouter — απουσία πρόσβασης σε αυτό το μοντέλο)
ΔΕΝ επαναδιατυπώνονται ΠΟΤΕ: το `excludeMarkers` ακυρώνει τον κανόνα ακόμη και όταν υπάρχει αντιστοιχία με το `textMarkers`,
ώστε το σφάλμα να διατηρεί την αρχική του κατάσταση και τίποτα να μην το επαναλαμβάνει επ' αόριστον. Ο
αντίστοιχος κανόνας ταξινόμησης παρόχου
(`agentrouter-model-access-denied` στο `open-sse/config/providerErrorRules.ts`:
`reason: "auth_error"`, `scope: "model"`, δηλωμένο βασικό cooldown `6h`) εξετάζεται
από το `checkFallbackError` (`open-sse/services/accountFallback.ts`)
_πριν_ από τη γενική πρόωρη επιστροφή `FORBIDDEN` της κατηγορίας apikey, με έλεγχο μέσω του
`honorsRuleLockScope(provider)` (#10334 — προς το παρόν αποκλειστικά για τον agentrouter μέσω
της λίστας επιτρεπόμενων `HONORS_RULE_LOCK_SCOPE_PROVIDERS` στο
`providerErrorRules.ts`). Το δηλωμένο cooldown 6h του κανόνα μεταβιβάζεται ως
`fallbackResult.baseCooldownMs`, αλλά εξακολουθεί να τροφοδοτεί την προϋπάρχουσα
διαδρομή αποκλεισμού ορίου χρήσης ανά μοντέλο (`lockModelIfPerModelQuota()` /
`recordModelLockoutFailure()`, αμετάβλητη από το #10334 εκτός από την πηγή του cooldown):
περιορίζεται προς τα κάτω στο `mlSettings.maxCooldownMs` του διαχειριστή
(προεπιλογή `1_800_000ms` / 30min), όπως κάθε άλλος αποκλεισμός μοντέλου, και η
_αποθηκευμένη αιτία αποκλεισμού_ παραμένει η προϋπάρχουσα, ενσωματωμένη τιμή `"forbidden"`,
όχι η τιμή `"auth_error"` του κανόνα — μόνο η διάρκεια του cooldown τηρείται
από άκρο σε άκρο, όχι η συμβολοσειρά της αιτίας. Η ίδια η σύνδεση παραμένει ενεργή·
τα συγγενικά μοντέλα στην ίδια σύνδεση δεν επηρεάζονται.

Τα σφάλματα ορίου χρήσης που επαναδιατυπώνονται (`额度不足`) αντιστοιχούν σε έναν κανόνα παρόχου στην παραγωγή
(`agentrouter-user-quota-exhausted`: `reason: "quota_exhausted"`, `scope:
"connection"`, χωρίς δικό του δηλωμένο χρόνο αναμονής — εφαρμόζεται η
προεπιλεγμένη κλιμακούμενη καθυστέρηση επανάληψης του επιπέδου διατήρησης).
Από το #10334 και μετά, το `scope` στο
`ProviderErrorRuleMatch` χρησιμοποιείται από άκρο σε άκρο, αλλά **μόνο** για παρόχους στη
λίστα επιτρεπόμενων `HONORS_RULE_LOCK_SCOPE_PROVIDERS` (`providerErrorRules.ts` —
προς το παρόν μόνο ο `"agentrouter"`, με έλεγχο μέσω `honorsRuleLockScope()`).
Για κάθε άλλο πάροχο, το `scope` παραμένει πληροφοριακό, ακριβώς όπως πριν από το #10334.
Το `checkFallbackError` εκθέτει το scope του κανόνα που αντιστοιχίστηκε ως
`fallbackResult.ruleScope`· το `isAgentrouterConnectionQuotaScope()`
(`src/sse/services/auth.ts`) είναι ο κοινόχρηστος έλεγχος που επιβεβαιώνει ότι ένα
`ruleScope` είναι πράγματι ασφαλές να αντιμετωπιστεί ως σήμα που αφορά ολόκληρη τη σύνδεση και
αποκαθίσταται αυτόματα (scope `"connection"`, reason `quota_exhausted`, ποτέ
`permanent`, ποτέ `creditsExhausted` — μια άμυνα απέναντι σε έναν μελλοντικό κανόνα που θα συνδυάζει το scope
`"connection"` με μια μόνιμη κατάσταση λογαριασμού). Δύο καταναλωτές τον καλούν:

- **Διατήρηση** (`markAccountUnavailable()`, `src/sse/services/auth.ts`):
  αντί να καταλήξει στον κλάδο αποκλεισμού **ανά μοντέλο** του παρόχου διέλευσης
  (το agentrouter έχει `passthroughModels: true` → το `hasPerModelQuota()`
  επιστρέφει `true`), εφαρμόζει έναν **προσωρινό χρόνο αναμονής σύνδεσης** —
  `testStatus: "unavailable"` + `rateLimitedUntil`, ποτέ μια τελική κατάσταση
  (`credits_exhausted`/`banned`/`expired`) — ώστε η σύνδεση να αποκαθίσταται αυτόματα
  μόλις λήξει ο χρόνος αναμονής, αντί να απαιτεί μη αυτόματη επαναφορά των διαπιστευτηρίων.
  Παραλείπεται για συνδέσεις με `disableCooling: true` (#2997): αυτή η εξαίρεση
  καταλήγει στον αποκλεισμό ανά μοντέλο (ένας τεκμηριωμένος συμβιβασμός —
  δείτε το σχόλιο κώδικα πάνω από τον κλάδο).
- **Συνδυαστική δρομολόγηση στο ίδιο αίτημα** (`applyComboTargetExhaustion()`,
  `open-sse/services/combo/targetExhaustion.ts`): ο ίδιος έλεγχος επισημαίνει τη
  σύνδεση στο σύνολο `exhaustedConnections` στη μνήμη, με κλειδί
  `${provider}:${connectionId}`. Αυτό παραλείπει μόνο έναν εναπομείναντα στόχο ΤΟΥ ΙΔΙΟΥ ΑΙΤΗΜΑΤΟΣ
  που _φέρει ήδη ο ίδιος ακριβώς αυτό το `connectionId`_ στο δικό του
  αντικείμενο στόχου (`getExhaustedTargetSkipReason()`,
  `open-sse/services/combo/comboPredicates.ts`, `if (provider &&
connectionId)` πριν από την αναζήτηση στο `exhaustedConnections`) — ένας απλός
  συνδυασμός λίστας μοντέλων, όπου οι συγγενικοί στόχοι δεν φέρουν δικό τους καρφιτσωμένο `connectionId`
  και ένα τέτοιο αναγνωριστικό επιλύεται μόνο ανά αποστολή από την κεφαλίδα
  `X-OmniRoute-Selected-Connection-Id` της απόκρισης, δεν αντιστοιχεί ποτέ σε αυτό το κλειδί. Για
  αυτήν τη συνηθισμένη περίπτωση, η πραγματική προστασία από την επαναχρησιμοποίηση του λογαριασμού
  που μόλις εξάντλησε το όριό του από ένα εναπομείναν σκέλος ΔΕΝ είναι αυτό το Set — είναι το παραπάνω επίπεδο
  διατήρησης (το `rateLimitedUntil` της σύνδεσης βρίσκεται πλέον στο μέλλον) σε συνδυασμό με
  τον ίδιο αυτό έλεγχο που καταστέλλει το `transientRateLimitedProviders` για την
  αποτυχία (δείτε «Σχεδιασμός δύο σταδίων» και το σχόλιο κώδικα στον κλάδο
  `isAgentrouterConnectionQuotaScope` στο `targetExhaustion.ts`): καθώς
  αυτό το Set παραμένει χωρίς επισήμανση, η εξαναγκασμένη αποδοχή του `allowRateLimitedConnection` στο `combo.ts`
  (`open-sse/services/combo.ts:1005-1013`, `:2734-2738`) ΔΕΝ ενεργοποιείται για
  τα εναπομείναντα σκέλη του παρόχου, επομένως το φίλτρο `rateLimitedUntil` της επιλογής
  διαπιστευτηρίων (`src/sse/services/auth.ts:1238`) τηρείται κανονικά και ένα
  εναπομείναν σκέλος είτε επιλέγει μια διαφορετική, ακόμη κατάλληλη σύνδεση agentrouter
  είτε αποτυγχάνει επειδή δεν υπάρχουν διαθέσιμα διαπιστευτήρια — δεν επιστρέφει
  εξαναγκαστικά στη σύνδεση για την οποία αυτός ο κλάδος μόλις εφάρμοσε χρόνο αναμονής.

### Σχεδιασμός δύο σταδίων: επαναδιατύπωση κατάστασης και, στη συνέχεια, ταξινόμηση

Η επαναδιατύπωση κατάστασης (`upstreamStatusRestatement.ts`) και οι κανόνες
ταξινόμησης παρόχων (`open-sse/config/providerErrorRules.ts`,
`providerRuleRegistry`) είναι ξεχωριστά μητρώα που χρησιμοποιούν και τα δύο ως κλειδιά το αναγνωριστικό
παρόχου και δείκτες κειμένου, αλλά εκτελούνται σε διαφορετικά σημεία και εξυπηρετούν διαφορετικούς
σκοπούς: η επαναδιατύπωση ξαναγράφει την κατάσταση HTTP νωρίς στο `chatCore.ts`·
οι κανόνες ταξινόμησης επιλέγουν το εναλλακτικό `reason` και το `scope` κλειδώματος
(`model` / `provider` / `connection`) μέσα στο `checkFallbackError()`
(`open-sse/services/accountFallback.ts`).

Οι κανόνες ταξινόμησης βλέπουν το πλήρες **κείμενο** του σφάλματος (απαραίτητο για την αντιστοίχιση
δεικτών σώματος όπως το `额度不足`) μόνο για παρόχους που περιλαμβάνονται στη λίστα επιτρεπόμενων
`FULL_TEXT_RULE_PROVIDERS` στο `providerErrorRules.ts` — προς το παρόν μόνο ο `"agentrouter"`.
Για κάθε άλλο πάροχο του **ενσωματωμένου καταλόγου**, το `checkFallbackError` παραδίδει
στο `getProviderErrorRuleMatch` μόνο το δομημένο σφάλμα (`{code, type}`), το οποίο
επαρκεί για κανόνες που βασίζονται σε κεφαλίδες/κατάσταση/κωδικό, αλλά δεν μπορεί να εντοπίσει δείκτες στο κείμενο του σώματος.
Η βοηθητική συνάρτηση `resolveRuleMatchBody()` εκτελεί αυτήν την επιλογή: πλήρες κείμενο σφάλματος
για τους παρόχους της λίστας επιτρεπόμενων και το δομημένο σφάλμα για τους υπόλοιπους. Η προσθήκη ενός
**ενσωματωμένου** παρόχου στο `FULL_TEXT_RULE_PROVIDERS` αποτελεί ρητή ενεργοποίηση ανά πάροχο
— υπάρχει ώστε η προεπιλεγμένη διαδρομή για κάθε πάροχο που δεν περιλαμβάνεται στη
λίστα να παραμένει αμετάβλητη, byte προς byte.

Το `scope` ενός κανόνα (`model` / `provider` / `connection`) αποτελεί ξεχωριστή ρητή ενεργοποίηση
από το `FULL_TEXT_RULE_PROVIDERS`: το `checkFallbackError` το εκθέτει μόνο ως
`fallbackResult.ruleScope`, και οι μεταγενέστεροι καταναλωτές το αντιμετωπίζουν ως
οτιδήποτε άλλο πέρα από μια πληροφοριακή ετικέτα μόνο για παρόχους στη λίστα επιτρεπόμενων
`HONORS_RULE_LOCK_SCOPE_PROVIDERS` στο ίδιο αρχείο (`με έλεγχο μέσω
honorsRuleLockScope()` — προς το παρόν μόνο ο `"agentrouter"`). Δείτε την ενότητα «Επαναδιατυπωμένα σφάλματα
ορίου χρήσης» παραπάνω για το τι κάνει πραγματικά μια αντιστοίχιση `scope: "connection"` όταν ένας
πάροχος περιλαμβάνεται σε αυτήν τη λίστα επιτρεπόμενων.

**#11104 — οι κανόνες που δηλώνονται από τον διαχειριστή παρακάμπτουν και τις δύο λίστες επιτρεπόμενων.** Ένας διαχειριστής μπορεί να
δηλώσει κατά την εκτέλεση έναν κανόνα ανά πάροχο μέσω του `settings.providerErrorRules`
(`open-sse/config/providerErrorRules.ts::setOperatorProviderErrorRules`)
χωρίς να επεξεργαστεί αυτό το αρχείο. Η εξάρτηση ενός κανόνα διαχειριστή από τα
`FULL_TEXT_RULE_PROVIDERS`/`HONORS_RULE_LOCK_SCOPE_PROVIDERS` — λίστες επιτρεπόμενων
που προορίζονται για την προστασία της **προεπιλεγμένης** συμπεριφοράς των ενσωματωμένων κανόνων καταλόγου — θα
καθιστούσε τον μηχανισμό ρυθμίσεων ανενεργό για κάθε πάροχο εκτός από όσους είναι ήδη
καταχωρισμένοι εκεί, αφού η δήλωση του κανόνα αποτελεί ήδη ρητή επιλογή συμμετοχής
από τον διαχειριστή. Τα `resolveRuleMatchBody()` και `honorsRuleLockScope()` ελέγχουν
πρώτα το `hasOperatorRuleForProvider()`: ένας πάροχος με κανόνα διαχειριστή λαμβάνει
το ανεπεξέργαστο κείμενο σφάλματος και το δηλωμένο `scope` του εφαρμόζεται, ανεξάρτητα
από το αν εμφανίζεται επίσης σε κάποια από τις δύο λίστες επιτρεπόμενων.

**Γνωστό κενό — δεν γίνεται ποτέ αναζήτηση στο `providerRuleRegistry` για HTTP 400.**
Ο κλάδος `BAD_REQUEST` του `checkFallbackError` ταξινομεί την κατάσταση 400 εξ ολοκλήρου
μέσω των δικών του πινάκων μοτίβων (`MODEL_ACCESS_DENIED_PATTERNS`,
`CONTEXT_OVERFLOW_PATTERNS` κ.λπ. στο `accountFallback.ts`) και επιστρέφει πριν
προσεγγιστεί ο κλάδος `configuredRule`/`getProviderErrorRuleMatch` που βρίσκεται παραπάνω.
Ένας ενσωματωμένος κανόνας καταλόγου (ή ένας κανόνας διαχειριστή) με `status: 400` είναι
συντακτικά έγκυρος, αλλά δεν θα ενεργοποιηθεί ποτέ. Κανένας υπάρχων κανόνας δεν στοχεύει
σήμερα το 400, επομένως τίποτα στην παραγωγή δεν επηρεάζεται — αλλά ένας μελλοντικός
κανόνας για το 400 απαιτεί πρώτα τροποποίηση αυτού του κλάδου, κάτι που αποτελεί μεγαλύτερη
αλλαγή από την προσθήκη ενός κανόνα (επαναταξινομεί το 400 για κάθε πάροχο που βασίζεται
ήδη στη συμπεριφορά των πινάκων μοτίβων) και βρίσκεται εκτός του πεδίου εφαρμογής μιας
προσθήκης κανόνα για έναν μόνο πάροχο.

### Προσθήκη μιας νέας πύλης που δηλώνει εσφαλμένα το quota

1. Καταχωρίστε έναν πίνακα κανόνων στο `statusRestatementRegistry`
   (`open-sse/config/upstreamStatusRestatement.ts`). Διατηρήστε τα `textMarkers`
   ειδικά για τον πάροχο· μην επαναχρησιμοποιείτε γενικές αγγλικές φράσεις που
   συγκρούονται με τα `CREDITS_EXHAUSTED_SIGNALS`
   (`open-sse/services/accountFallback.ts`).
2. Προαιρετικά, καταχωρίστε κανόνες ταξινόμησης στο
   `open-sse/config/providerErrorRules.ts` (`providerRuleRegistry`) για να επιλέξετε
   το σωστό εύρος κλειδώματος (`connection` για quota σε επίπεδο λογαριασμού, `model`
   για σφάλματα ανά μοντέλο). Αυτό το βήμα τίθεται σε ισχύ στην παραγωγή μόνο για
   παρόχους των οποίων οι κανόνες χρειάζονται το πλήρες κείμενο σφάλματος (δείκτες σώματος):
   προσθέστε το αναγνωριστικό παρόχου στο `FULL_TEXT_RULE_PROVIDERS` στο ίδιο αρχείο —
   διαφορετικά, το `checkFallbackError` παρέχει στον κανόνα μόνο το δομημένο σφάλμα
   `{code, type}` και ένας κανόνας κειμένου σώματος δεν θα αντιστοιχιστεί ποτέ σε πραγματική
   κίνηση. Οι κανόνες που αντιστοιχίζονται αποκλειστικά βάσει `status`/`headers` (όπως
   εκείνοι του Opencode ή του Minimax) δεν χρειάζονται αυτήν τη ρητή ενεργοποίηση. Ξεχωριστά,
   εάν ο κανόνας δηλώνει `scope: "connection"` και η πρόθεση είναι μια πραγματική περίοδος
   αναμονής σε επίπεδο σύνδεσης μαζί με παράλειψη του συνδυασμού στο ίδιο αίτημα (και όχι
   απλώς μια ενημερωτική ετικέτα), προσθέστε το αναγνωριστικό παρόχου στο
   `HONORS_RULE_LOCK_SCOPE_PROVIDERS` στο ίδιο αρχείο — αυτό ελέγχει τη χρήση τύπου
   `isAgentrouterConnectionQuotaScope()` στο `markAccountUnavailable()`
   (`src/sse/services/auth.ts`) και στο `applyComboTargetExhaustion()`
   (`open-sse/services/combo/targetExhaustion.ts`)· χωρίς αυτό, το `scope`
   εξακολουθεί να μεταφέρεται μέσω του `fallbackResult.ruleScope`, αλλά τίποτα δεν
   ενεργεί βάσει αυτού.
3. Προσθέστε δοκιμές μονάδας κατά τα πρότυπα των
   `tests/unit/upstream-status-restatement.test.ts` και
   `tests/unit/agentrouter-error-rules.test.ts` (συμπεριλαμβανομένων των ελέγχων
   not-permanent / not-creditsExhausted και — εάν ο πάροχος χρειάζεται τη λίστα
   επιτρεπόμενων — μιας δοκιμής που επιβεβαιώνει ότι το `resolveRuleMatchBody()`
   επιστρέφει το πλήρες κείμενο μόνο για τον συγκεκριμένο πάροχο).

Δεν απαιτούνται αλλαγές στα `chatCore.ts`, `classifyError` ή combo.

#### Κλείδωμα ανά ομάδα εξόδου (#10880)

Οι πάροχοι στο `EGRESS_BUCKETED_LOCK_PROVIDERS` (οικογένεια opencode) αντιμετωπίζονται
ως upstream ομαδοποιημένοι ανά IP (το δωρεάν επίπεδο του opencode ομαδοποιείται ανά IP,
όχι ανά λογαριασμό — βλ. #9611): μια κατάσταση 429 ταξινομημένη ως `quota_exhausted`
**ή** `rate_limit_exceeded` θέτει σε περίοδο αναμονής κάθε σύνδεση της οικογένειας της
λίστας επιτρεπόμενων της οποίας η τελευταία γνωστή IP εξόδου αντιστοιχεί σε εκείνη της
σύνδεσης που απέτυχε, πριν η εναλλαγή προλάβει να τις δοκιμάσει
— αποφεύγοντας N-1 upstream κλήσεις με εγγυημένη αποτυχία (ίδιο μοτίβο με τα
#10460/#10525). Το `rate_limit_exceeded` συμπεριλαμβάνεται σκόπιμα: στη διαδρομή
`markAccountUnavailable` οι ειδικοί κανόνες του opencode δεν αντιστοιχίζονται ποτέ
(δεν παραδίδονται headers/σώμα στο `checkFallbackError`, το opencode δεν βρίσκεται στο
`FULL_TEXT_RULE_PROVIDERS`), επομένως ένα 429 του οποίου το σώμα περιέχει το κείμενο
quota συνδρομής ("επιτεύχθηκε το μηνιαίο όριο χρήσης") ταξινομείται ως `quota_exhausted`
από τον εφεδρικό μηχανισμό κειμένου quota (`buildSubscriptionQuotaFallback`,
`accountFallback.ts`· περίοδος αναμονής 1 ώρας) πριν προσεγγιστεί ποτέ ο κανόνας
`status_429` — ενώ ένα 429 χωρίς κείμενο quota (απλός περιορισμός ρυθμού) ταξινομείται
μέσω του κανόνα `status_429` ως `rate_limit_exceeded` και εξακολουθεί να θέτει την
οικογένεια IP σε περίοδο αναμονής. Για έναν πάροχο της λίστας επιτρεπόμενων, ένας
περιορισμός ρυθμού ομαδοποιημένος ανά IP αποτελεί το ίδιο σήμα με ένα εξαντλημένο quota.
Πραγματικοί περιορισμοί:

- **Βέλτιστη δυνατή προσπάθεια**: το κλείδωμα επιλύει την τελευταία γνωστή `egress_ip`
  της σύνδεσης από το `proxy_logs` (παράθυρο 24 ωρών, σύγχρονα, χωρίς cache). Ψυχρό cache (το egress
  IP δεν έχει ανιχνευθεί ποτέ) ή απουσία γραμμής → η σύνδεση που αποτυγχάνει εξακολουθεί να τίθεται σε cooldown από τον
  κλάδο (καταγράφεται όπως σήμερα), απλώς δεν κλειδώνεται καμία συγγενική σύνδεση.
- **Ποτέ οριστικό**: το cooldown είναι ένα ανανεούμενο παράθυρο ορίου
  (`testStatus: "unavailable"`)· μια μόνιμη κατάσταση δεν συνάγεται ποτέ από ένα
  σήμα σε επίπεδο IP. Οι συνδέσεις `disableCooling` παρακάμπτουν πλήρως τον κλάδο.
- **Αλλάζει η λεπτομέρεια κλειδώματος για την οικογένεια της λίστας επιτρεπόμενων**: πρόκειται για αλλαγή εμβέλειας
  και όχι μόνο για βελτιστοποίηση συγγενικών συνδέσεων. Το opencode είναι πάροχος `passthroughModels`,
  επομένως πριν από αυτόν τον κλάδο ένα 429 προκαλούσε κλείδωμα ανά MODEL· τώρα
  προκαλεί cooldown σύνδεσης — ακόμη και για διαχειριστή που εκτελεί μία μόνο
  σύνδεση χωρίς καμία συγγενική σύνδεση. Αυτή είναι η λεπτομέρεια που ο πίνακας κανόνων του opencode
  δηλώνει ήδη ως σωστή (`scope: "connection"`,
  `providerErrorRules.ts`), αλλά μέχρι τώρα δεν τηρούνταν ποτέ, επειδή το opencode δεν βρίσκεται στο
  `HONORS_RULE_LOCK_SCOPE_PROVIDERS`. Ο κλάδος εγγράφει ο ίδιος το cooldown
  - `backoffLevel` της σύνδεσης που αποτυγχάνει, αντικατοπτρίζοντας τον
    κλάδο agentrouter με εμβέλεια σύνδεσης, και επιστρέφει — το μπλοκάρισμα ανά μοντέλο και
    η γενική διαδρομή παρακάτω δεν εκτελούνται ποτέ.
- **Περιλαμβάνεται το combo**: όπως και ο κλάδος agentrouter, η εμβέλεια αγνοεί σκόπιμα
  την υποβάθμιση `persistUnavailableState`/`isCombo` που εφαρμόζει ένας καλών combo
  σε ένα 429. Ένα κλείδωμα ανά μοντέλο δεν αποτελεί ασθενέστερη μορφή αυτής της εμβέλειας· είναι
  η λανθασμένη μονάδα: δεν λέει τίποτα για το εξαντλημένο IP, οπότε η εναλλαγή
  combo θα συνέχιζε να σπαταλά μία εγγυημένα αποτυχημένη κλήση ανά συγγενική σύνδεση.
- **Ασφάλεια συγγενικών συνδέσεων**: μια συγγενική σύνδεση που βρίσκεται ήδη σε οριστική κατάσταση (banned/credits_exhausted)
  ή ήδη σε μεγαλύτερο cooldown δεν αντικαθίσταται ποτέ.
- **Αποκλειστική λίστα επιτρεπόμενων**: η διεύρυνση του `EGRESS_BUCKETED_LOCK_PROVIDERS` αποτελεί
  ρητή απόφαση του κατόχου· δεν υπάρχει γενική καλωδίωση (μοτίβο #10334/#10419). Το
  ερώτημα συγγενικών συνδέσεων δεσμεύει την ίδια λίστα επιτρεπόμενων αντί να την επαναλαμβάνει ως SQL
  literal, ώστε η διεύρυνσή της να παραμένει αλλαγή μίας γραμμής.
- **Εναλλαγή egress IP, και προς τις δύο κατευθύνσεις**: το παράθυρο αναζήτησης (24h) είναι πολύ
  μεγαλύτερο από το TTL του cache egress-IP (5 min), επομένως το «τελευταίο γνωστό IP» είναι ιστορικό,
  όχι τρέχουσα κατάσταση. Αν ο proxy μιας σύνδεσης άλλαξε μέσα στο παράθυρο, το
  κλείδωμα ενδέχεται να **μην εντοπίσει** ένα πραγματικά κοινόχρηστο IP (το καταγεγραμμένο IP είναι το νέο,
  μη εξαντλημένο) — και, συμμετρικά, ενδέχεται να **θέσει σε cooldown μια συγγενική σύνδεση που έκτοτε
  έχει μετακινηθεί** από το εξαντλημένο IP. Η δεύτερη περίπτωση κοστίζει σε εκείνη τη συγγενική σύνδεση ένα
  παράθυρο cooldown· και οι δύο γίνονται αποδεκτές ως περιορισμοί βέλτιστης δυνατής προσπάθειας μιας αναζήτησης
  βάσει ιστορικού.
- **Κόστος**: δύο οριοθετημένες σαρώσεις του `proxy_logs` (με φιλτράρισμα παραθύρου μέσω
  `idx_pl_timestamp`), μόνο με τη συχνότητα εμφάνισης 429. Κανένα νέο index (migration 134
  YAGNI). Μετρήθηκε σε αντίγραφο DB πραγματικής κίνησης μεσαίου μεγέθους· ένα
  instance υψηλού throughput διατηρεί αναλογικά περισσότερες γραμμές στο ίδιο παράθυρο.

## Εντοπισμός σφαλμάτων

- Το σταθμισμένο combo απαντά με `503 all_targets_cooling_down` (έχει οριστεί το `Retry-After`, ενώ το `diagnostics.excluded` παραθέτει κάθε προορισμό με `model_lockout` / `circuit_open` / `provider_cooldown` / `unavailable`) → το pool έχει ρυθμιστεί και συνδεθεί, αλλά κάθε προορισμός αποκλείεται απλώς από έναν χρονοδιακόπτη ανθεκτικότητας· η προειδοποίηση `[COMBO] Weighted selection: every target excluded before dispatch — …` αναφέρει τους λόγους και τα δευτερόλεπτα που απομένουν. Ένα `404 no_executable_targets` από το ίδιο combo σημαίνει ότι δεν εμπλέκεται κανένας χρονοδιακόπτης ανθεκτικότητας (δεν υπάρχει τίποτα προς εκτέλεση ή κάθε λογαριασμός απέτυχε στον έλεγχο διαθεσιμότητας). Υλοποιείται στο `open-sse/services/combo/pinRecovery.ts` από τους αποκλεισμούς που συλλέγονται στο `targetResolution.ts`.
- Παραλείπονται όλα τα κλειδιά για έναν πάροχο → ελέγξτε τόσο την κατάσταση του circuit breaker ΟΣΟ ΚΑΙ τα `rateLimitedUntil`/`testStatus` κάθε σύνδεσης.
- Ο πάροχος αποκλείεται μόνιμα μετά το παράθυρο επαναφοράς → ο κώδικας διαβάζει απευθείας το `state` αντί για τα `getStatus()`/`canExecute()`.
- Ένα κλειδί αποτυγχάνει, ενώ τα υπόλοιπα θα πρέπει να λειτουργούν → προτιμήστε το cooldown σύνδεσης αντί για το circuit breaker.
- Αποτυγχάνει μόνο ένα μοντέλο → προτιμήστε το κλείδωμα μοντέλου αντί για το cooldown σύνδεσης.
- Η κατάσταση θα έπρεπε να ανακάμπτει αυτόματα, αλλά δεν το κάνει → ελέγξτε για μελλοντική χρονική σήμανση και για διαδρομή ανάγνωσης που ανανεώνει την κατάσταση που έχει λήξει. Οι μόνιμες καταστάσεις απαιτούν μη αυτόματες αλλαγές.

## Δοκιμές ανθεκτικότητας (Φάση 8 · Μπλοκ C)

Πέρα από τις δοκιμές μονάδας για τη λογική ανθεκτικότητας, τρεις δοκιμές ελέγχουν το περιβάλλον εκτέλεσης υπό
πραγματικές συνθήκες έντονου φόρτου/αστοχίας (όλες είναι δοκιμές ενσωμάτωσης/νυχτερινές — καμία δεν εμποδίζει τα PR):

| Δοκιμή                 | Τι ελέγχει                                                                                                                                                                                                                                | Εκτέλεση                                   |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| Χάος                   | Ένας ψευδής κόμβος upstream εισάγει πραγματική καθυστέρηση/επαναφορά/λήξη χρονικού ορίου/503· επαληθεύει ότι ο διακόπτης κυκλώματος ανοίγει/ανακάμπτει και ότι το `checkFallbackError` ταξινομεί το 503 ως ανακτήσιμη εφεδρική περίπτωση. | `RUN_CHAOS_INT=1 npm run test:chaos`       |
| Αύξηση σωρού           | ~500 ροές ανά `createSSEStream` με `--expose-gc`· αποτυγχάνει αν ο σωρός αυξηθεί πέρα από το ανώτατο όριο (προστασία OOM #3069).                                                                                                          | `npm run test:heap`                        |
| Παρατεταμένο φορτίο k6 | Διαρκές φορτίο στο `/api/monitoring/health`· κατώφλια p95/σφαλμάτων.                                                                                                                                                                      | `k6 run tests/load/k6-soak.js` (νυχτερινά) |

Ενορχηστρώνονται από το `.github/workflows/nightly-resilience.yml` (cron + χειροκίνητη ενεργοποίηση). Στο
προεπιλεγμένο `test:integration`, οι δοκιμές χάους και σωρού παραλείπονται αυτόματα (χωρίς `RUN_CHAOS_INT`/`--expose-gc`).
