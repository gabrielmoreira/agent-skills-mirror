# Agent Note: 起点、七猫扫榜加书库新书翻页，聚合不让没热度的列表拖掉平台口径

Status: implemented
Date: 2026-10-10
Related: [扫榜聚合与交接](2026-09-26-scan-aggregate-and-handoff.md)、[扫榜与安装审查修复](../bug-fix/2026-09-26-scan-setup-review-fixes.md)

## Problem

作者要看「最近冒头的新书」：七猫只有排行榜，起点的各新书榜满 20 万字、签约满 30 天或断更超 3 天就下榜，还在更新、刚起量的新书两边都看不全。作者点名要两个书库筛选页，并且要翻页取前几页：七猫 https://www.qimao.com/shuku/a-a-a-1-1-a-0-click-1/（全部频道、30 万字以下、3 天内更新、连载中、按点击量），起点 https://www.qidian.com/all/action0-size1-update1/（男生、连载、30 万字以下、三日内、人气排序）。

两页的取数条件不同：七猫书库服务端渲染，普通 HTTPS 就能拿到，但只给子分类、没有热度；起点 PC 页直接请求会被风控拦下，只能走 Chrome，字数用每次刷新都换的反爬字体加密，也没有总推荐。另外聚合器选热度口径时以全平台去重后的书为分母，没有热度的书库书一多（超过带热度书的 2.33 倍），整个平台会悄悄退成「按榜单名次」，排行榜的真实热度也跟着丢掉。

## Decision

- 七猫：`qimao-rank-scraper.js --source library --pages N`（默认 3，1–10），走 Node https，不需要 Chrome；第 1 页核对标题里的三个筛选与「按点击量」排序；主类按子分类链接里的主类 id 请求一次分类页、读标题补出（同次运行缓存），和排行榜题材写法逐字一致；七猫响应头有折行，这一处请求开 `insecureHTTPParser`。
- 起点：`qidian-rank-scraper.js --type library --pages N`（默认 3，1–10），只走 CDP，不进 `--type all`；逐页核对可见筛选面板、男生频道、人气排序与当前页码；下载 `qd_anti_spider` 字体（只允许 qdfepccdn.qidian.com），纯 Node 解析 cmap 与 post 字形名解码字数，私用区字符一律不写进输出；签约、收费、更新时间与兜底字数从移动端作品页补，失败写 `[待补]`。作品页的总推荐单列为「新书总推荐」：新书只有几千到几万，按聚合认的「总推荐」行名写会和月票、畅销榜的老书混算，把题材热度中位拉低两个数量级，所以这份和七猫书库一样按名次（人气排名）进聚合。判断页面是否被验证码拦，先看页面上有没有成片的作品链接，书目简介、章节名里出现「验证」「拖动」等字不再误判。
- 两边都是所有页写一份文件，首行「平台 · …新书」进聚合的「新书榜」列，名次跨页连续、按 bookId 去重、某页无新书即停；第 1 页失败或 0 本不写文件（exit 1），后续页失败保留已采部分（exit 2）；文件名走各脚本唯一那处带日期的赋值。
- 聚合器（长篇、短篇共用一份）：热度口径门槛的分母只算出现在至少一份带指标值列表里的书，整份没有指标值的列表视为名次榜；题材热度中位在部分书有值时标「（n 本有值）」，少于 3 本有值不显示；出现名次榜时列一行说明热度中位只算有热度的书。字数中位不改，平台参考里写明书库只收 30 万字以下会拉低字数中位。
- 两个来源都不进默认组合，作者说「新书」「最近冒头」「什么在起量」时再加；起点平台参考写明这份要开 Chrome。入口把六行「用法见某参考」的脚本说明合成一行，腾出的字给起点那节，番茄、晋江锁住余量，七猫补登记预算分支；描述与路由表补「七猫」「新书」触发。

## Alternatives considered

- **起点只解字体、不补移动端详情**：最强理由是每页只开一次浏览器、不多发 20 次请求。不采用：签约、收费是起点条目的必填行，字体解不出时字数也要兜底；移动端作品页实测可用，3 页约多 30–40 秒。
- **新书的总推荐照常写成「总推荐」进热度口径**：最强理由是数字现成、口径统一。不采用：审查用真实输出实测，混入书库后起点「轻小说」题材热度中位从 135 万掉到 5455、「都市」从 195 万掉到 5.5 万，题材冷热变成「哪个题材书库书多」；起点默认组合里新书榜本来也混算，那是旧行为，这次不扩大。
- **起点只用移动端详情、不解字体**：最强理由是少写一个字体解析器。不采用：详情请求可能被限流或失败，字数是这份最核心的字段，列表页上的字体解码不依赖额外请求，详情只作兜底。
- **七猫题材直接用子分类**：最强理由是不多发分类页请求。不采用：排行榜题材是主类，子分类当题材会把七猫题材表拆成两层（调查已用夹具实测）。
- **执行页面里的 `__NUXT__` 还原分类树**：最强理由是一次拿全映射。不采用：名字被压成变量，要执行站点脚本才能还原，不安全也不稳；分类页标题一次请求就给出主类名。
- **限制页数而不改聚合器**：最强理由是不碰共享文件。不采用：作者说「取前几页」，页数一多口径就丢，而且是静默的；改分母是最小、可解释的修法。

## Consequences

- 收益：作者能直接看到两站「最近三天还在更新的 30 万字以内新书」，名次就是点击或人气排名，并和排行榜一起进聚合的新书榜列；七猫这份不需要 Chrome，Chrome 起不来时也能采。
- 代价：七猫每次多 5–8 个分类页请求，主类名依赖分类页标题格式；起点每次多约 60 个移动端请求，字体每次刷新都换；筛选条件固定（七猫全站、起点男生），不提供改频道或排序。`test-scan-runtime.js` 从约 6 秒变成约 45 秒。聚合器的「（n 本有值）」也会出现在旧数据上（番茄个别未解析书名、点众评分只有 1 本时）。
- 未验证：起点这份没有在真实 CDP Chrome 上整链跑过；页面读取脚本在 app 内置浏览器里对真实第 1、2 页验证过，字数解码对照页面渲染逐条核对过 40 本。
