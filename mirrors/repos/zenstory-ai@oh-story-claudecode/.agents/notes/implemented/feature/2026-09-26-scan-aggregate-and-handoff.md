# Agent Note: 扫榜先聚合再读，结论落盘交给写作

Status: implemented

## Problem

按「作者时间线上每个时刻只注入此刻需要的信息」审计扫榜两个 skill，发现三处浪费和一处断链：

- **原始榜单整份进主会话**：番茄默认 37 个题材、每题材约 20 本，一份阅读榜七百多条，每条带作者、在读、字数、标签、bookId、链接和百字简介。按采集脚本的输出格式造同量样例，一份约 18.6 万字符（去空白 16.7 万），主会话读完超过 10 万 token；男女频加新书榜再翻几倍。分析真正要的是分布和代表作，逐条原文只在看开篇卖点、新人设时才需要几本。
- **平台细则常驻入口**：story-long-scan 的 SKILL.md 放着起点、番茄、七猫、晋江四张榜单网址表、命令和人工清洗规则（约 3.4K 去空白字），另有 `scan-output-format.md` 汇总五个平台的字段与模板（3.6K）。作者一次只选一个平台，清洗和质量标注脚本也已经做了。
- **扫榜报告不落盘**：长篇 Phase 4 报告只在对话里，Phase 5 选题只能靠对话记忆接上；作者扫完榜隔天再选题，结论就没了。短篇扫榜整个产出都不落盘，story-short-write 也不读。
- **短篇开头问的平台和脚本对不上**：Phase 1 问「知乎盐言/番茄短篇/七猫短篇」，脚本却只支持点众和黑岩；作者选了前三个，流程才发现抓不了。

## Decision

- **确定性聚合脚本**：`skills/story-long-scan/scripts/aggregate-rank.js`（零依赖 node，与采集脚本同一运行时），经 `scripts/shared-assets.json` 的 `scan-rank-aggregator` 组字节同步到 `skills/story-short-scan/scripts/`。输入是输出目录里的榜单文件（首行 `# 平台 · 榜单名`、条目 `### #排名 书名`、`*作者 · 题材 · …*` 元信息行），自动跳过 `扫榜聚合.md`、`选题决策.md`、`短篇扫榜结论.md` 和非榜单笔记。输出：采集情况（数据质量、问题摘要、书名待解析数、没采到的题材），每平台一张题材表（本数、占比、新书榜本数、热度中位、字数中位、高频标签、样本够不够），热度与字数分布，标签热词，书名常见词，多榜重合，每题材前 3 本代表作（简介截 30 字）。同平台书名+作者相同只计一次，热度取各榜最大值。热度口径按平台自动选：番茄在读、七猫热度、晋江收藏、起点总推荐、刺猬猫榜单值、点众评分，手动榜单认「数字+口径」（如 `2.3万收藏`）。`--out` 落盘并同时打到标准输出，`--sample {题材/标签/书名词} --n 5` 取回原始条目，`--json` 供测试与机读，`--sparse` 调样本门槛（默认 15，小平台 10）。
- **入口只留流程**：story-long-scan Phase 2 改成五步——读所选平台参考、写进同一输出目录、跑聚合、看采集情况、按需抽样。平台细则拆到 `references/platform-{qidian,fanqie,qimao,jjwxc,ciweimao}.md`（网址、命令、字段、默认组合、故障排查、该平台分析维度），`scan-output-format.md` 删除，内容分进这五份。story-short-scan 同样拆出 `platform-dianzhong.md`、`platform-heiyan.md` 和 `manual-rank-input.md`（没有脚本的平台怎么向作者要榜单、整理成可聚合的格式、知乎盐言分析维度）。
- **结论落盘**：长篇沿用 `选题决策.md`。Phase 4 报告展示给作者的同时写进 `{outdir}/选题决策.md` 的「扫榜结论」一节（文件不存在先写文件头），Phase 5 先从文件读「扫榜结论」和 `扫榜聚合.md`，再写「推荐选题」；重跑整节替换。`topic-decision.md` 模板加了「聚合表」字段和「扫榜结论」一节，「推荐选题」及其字段不变。只扫榜不选题时文件只有「扫榜结论」没有「推荐选题」，两个消费方按此容忍：story-long-write 开书当作还没选题、走常规提问，story-long-analyze 跳过回填、不判文件无效。短篇新增 `{outdir}/短篇扫榜结论.md`，模板在 `references/topic-match.md`：文件头有扫榜日期、复扫日期、数据来源、聚合表；「扫榜结论」一节是 Phase 4 报告；「选题匹配」每个方向写目标情绪、题材与设定、开头钩子、传播引擎、复杂度、可行性、篇幅/平台、验证动作。story-short-write Phase 1 发现项目根或上一级目录有这个文件时，先读「选题匹配」，把排第一的方向带着目标情绪当候选问作者，过了复扫日期就提醒。
- **平台选项对齐**：short-scan Phase 1 直接说明点众、黑岩能抓（黑岩要先登录作者后台），知乎盐言、番茄短篇、七猫短篇需要作者发截图或文字；长篇 Phase 1 补上已有脚本的七猫、刺猬猫。
- **测试**：`scripts/test-scan-aggregate.py` 用逐平台模仿采集脚本渲染格式的夹具（外加一份手动榜单）经公开 CLI 断言解析、去重、口径、分桶、问题上浮、抽样、跳过非榜单文件和压缩比，在 Linux / Windows / macOS CI 运行。

## Alternatives considered

- **聚合脚本写成 Python**——最强理由：仓库多数确定性工具是 Python，测试也是 Python。不用：扫榜两个 skill 的运行时只要求 node，skill 文档里调 Python 还得写 python3 → python → py 探测；用 node 不给作者多加一个运行时依赖。
- **让采集脚本直接输出聚合表**——最强理由：少一步命令，主会话一跑就拿到短表。不用：七个采集脚本各改一遍会把聚合逻辑复制七份；作者手动提供的榜单、跨平台对比、多份榜单合并去重都只能在采集之后做。原始榜单仍保留在盘上，抽样和重新聚合都靠它。
- **保留 `scan-output-format.md` 作为一份平台总表，只在入口说「读对应小节」**——最强理由：文件少，改动小。不用：模型读 reference 通常整份读，按小节读约束不住；拆成每平台一份，选了哪个平台读哪份最直接。
- **长篇另写一份 `扫榜报告.md`**——最强理由：报告和选题各自一份文件，职责清楚。不用：写作开书与拆文回填已经围绕 `选题决策.md` 建了查找和确认流程，多一份文件就多一个要找、要复制的产物；把报告作为「扫榜结论」一节放进同一文件，交接只有一个文件。
- **短篇把结论直接写进小说项目**——最强理由：写作一定能找到。不用：扫榜常在还没建项目时做，和长篇一样落在扫榜输出目录，由写作按「项目根或上一级目录」去发现。

## Consequences

- 收益：番茄一份全题材阅读榜（740 条）主会话读入从约 18.6 万字符降到聚合表约 1.3 万字符（按采集格式造的同量样例实测，去空白 16.7 万 → 1.1 万）；抽样一次 5 条约 1.5K 字符。long-scan 入口去空白字数 7807 → 4940，short-scan 4131 → 4095（平台细则移出、脚本说明改指向平台参考，新增聚合与落盘步骤）；选了某平台再多读一份 0.4K–1.4K 的平台参考。扫榜结论与选题都有文件可接，隔天续做、换会话选题不再依赖对话记忆；短篇写作第一次能用上扫榜结论。
- 代价：聚合按采集脚本当前的 Markdown 格式解析，采集脚本改输出格式时要同步改聚合与测试夹具；各平台热度口径不同，题材表按平台分开，不做跨平台热度比较。长篇报告里原有的「更新频率」一项榜单数据从来给不出，这次去掉；「新元素提取」三小节合成三行。story-short-write 为放下读取结论的一句，删了「核心方法」里与「写前必读」、Phase 2 对标加载重复的一条（有对标先拆、无对标读题材参考），入口净减 37 字。
- 行为变化：长篇 Phase 4 现在会写文件（之前只展示）；短篇 Phase 4/5 新增落盘；短篇写作 Phase 1 多一次文件发现。聚合脚本只读输入，除 `--out` 外不写文件。
