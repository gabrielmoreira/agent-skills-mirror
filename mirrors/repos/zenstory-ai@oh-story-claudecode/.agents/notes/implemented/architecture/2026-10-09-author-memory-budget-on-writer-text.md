# Agent Note: 作者记忆注入预算改量写手读到的那几行，装不下的用原话告诉作者

Status: implemented
Date: 2026-10-09
Related: [注入预算：读时截断改写时预警](../bug-fix/2026-09-18-author-memory-query-budget.md)、[v0.8 瘦身写作回路](2026-09-24-v0-8-lean-writing-loop.md)、[作者记忆按时刻拆分](2026-09-26-author-memory-by-moment.md)；下游 zenstory-ai/oh-story-dsh#61

## Problem

dsh#61：作者记下的写作习惯写正文时只带上一部分，他那本书固定有 9 条被略过，章末也没人告诉他。三路本地复现（19–22 条适用习惯）都正好漏 9 条。

- 2048 字节是 #368 定的注意力预算，#429 维持不放大，前提是「query 输出原样贴进 prompt」。v0.8.0 起长篇写章由组装脚本代查，只把「- 断言（编号）」渲染进写手 prompt，id、kind、scope、JSON 引号与分隔符都不进去。预算量的却还是 JSON 外壳：每条约 100 字节固定开销，写手实际读到的只有 2048 字节的 35–46%。40 字断言装 8 条、20 字装 11 条就开始漏。
- 漏项只写进核对报告给主会话，单章与日更批末的作者汇报模板都没有对应一行，模板还写着「其余内部结论不说给作者」。漏超过 20 条时组装脚本只数被封顶的编号列表，少报。
- 协议里给作者的话术是「这几条可能顾不上」，脚本回执却写「不会进入 prompt」，作者听到的比实际更含糊。

## Decision

- `query` 输出新增 `lines`：每条一行「- 断言（编号）」，就是交给执行者的原文。2048 字节量 `lines`（每行含换行），数值不变；`items`、漏项清单与 `book_revision` 等只给主会话和脚本判断用，不计入预算。写入端最坏估算的切片轻重与真实装填共用同一个按行计量函数，「回执没提醒 ⟹ 真实查询不漏条」的属性测试照旧穷举。
- 漏项不进 prompt，所以 `omitted_ids` 取消 20 条封顶、全数按候选优先级列出；新增 `omitted_summaries`（编号 → 断言首句，14 字截断），供主会话用原话告诉作者；新增 `omitted_importance`（编号 → 重要度），供组装脚本合并多次查询后重排。
- 组装脚本原样拼 `lines`；本书多个题材或流程各查一次时，合并后某次漏、另一次带上的不算没带上，漏项按重要度重排（同重要度保持先后）。有装不下的条目时，在核对报告里点名全部编号，并拼好给作者的那句话（最多点名 8 条，其余「等」带过，完整清单走「整理作者记忆」）；脚本查询失败或有限定范围要主会话补查时，核对报告提醒补查到的漏项同样章末用原话说。单章作者汇报模板与日更批末模板各加一行条件句：有习惯没带上就用原话说（单章模板注明核对报告拼好了就照说），没有就删掉。
- 各入口把「总输出 ≤2KB」改成「交执行者的是 `lines`」：长篇、短篇、去味、审稿的入口与派写手 prompt 的「作者偏好」槽一并改；短篇入口加「没装下的交稿时用原话告诉作者」；脚本跑不起来时的手动组装说明同步，并写明本书题材、长篇写作流程有限定条目时各带 `--genre`／`--workflow` 再查、合并去重。`author-memory.md` 话术分开说：真实查询的漏项说「写正文时这几条会带不上」，写入回执的预警是按最坏情况估的（全局＋最重的题材、流程切片＋本书），说「可能带不上」。仓库文档（宿主说明中英文、脚本索引）里「输出硬上限 2KB」改为交给写手的习惯原文每次查询不超过 2KB。
- 容量（2048 字节，每行固定开销 14 字节）：40 字断言 8 → 15 条，20 字断言 11 → 27 条。
- 预算：没有调高任何文件或路径预算。日更批末模板那一行靠删掉日更开头与 Step 2 重复的「单轮最多 3 章」腾出（Step 2 的上限与守卫锚点保留），短篇入口改写措辞腾出。

## Alternatives considered

- **容量做成项目级可配置（dsh#61 原方案）**：最强理由是作者自己最清楚要带多少条，书大了可以自己调。不采用：等于把「偏好在写手那里占多少注意力」交给作者判断，而作者没有判断依据；还要多一个配置入口，写入预警与真实读取都得读同一个配置，跨宿主兼容成本高。改计量对象后，报告人那种规模的库已经能装下。
- **装不下就暂停组装（dsh#61 原方案）**：最强理由是绝不悄悄开写。不采用：暂停不增加容量，超编后每章都会停下，逼作者删掉仍然有效的习惯，正是报告人反对的结果；也和「作者记忆是低优先级倾向，不为它中断任务」冲突。用「章末用原话点名」达到「不悄悄」。
- **直接放大到 4096**：最强理由是改一个常量最简单。不采用：这才是真正放大写手读到的量，推翻 #429「不放大」的判断；按行计量后在同样 2048 下已多装一倍，先看这一步够不够。
- **只给写正文那组查询加按行计量的开关，其余路径维持 JSON 外壳**：最强理由是改动面小，去味、审稿的输出不变。不采用：同一组 kind（文风＋故事设计）还被改稿路径查，写入预警只能按一种口径估算，两种口径并存会让「回执没提醒就不漏」失效；各路径交给执行者的本来就该是渲染后的原话，统一口径更简单。
- **压缩 JSON 信封（#429 留下的待办）**：最强理由是改动约 15 行、所有路径受益。不采用：信封不再计入预算，压缩它不再增加容量；单独做时，报告人那种规模的库仍会漏。
- **按本章相关性筛选条目**：最强理由是更省注意力。不采用：每章漏什么变得不可预测，违背 #429「漏掉的是什么要可预测、可核对」，还要升 state 版本、写匹配器。

## Consequences

- 收益：同样 2048 字节，写手读到的习惯约多一倍，报告人那种规模的库基本能装全；装不下时作者在章末汇报里听到具体是哪几条，不再只有主会话知道；漏超过 20 条时计数准确。
- 代价：写手读到的偏好块变长，最多约 680 字（以前约 300 字），对正文质量与偏好遵从有没有影响没有数据。查询输出给主会话的 JSON 变大（`items` 与 `lines` 重复一份，漏项不封顶），最坏约几 KB，只进主会话。作者记忆多的书，每章汇报都会重复那一句，直到作者整理。
- 未变：书带多个题材时，组装脚本按「题材 × 流程」分别查询再合并，合并后的注入块仍可能超过 2048 字节，这是 v0.8.0 起就有的行为；按行计量后每次查询能装的翻倍，超出的绝对量也跟着变大。没有在合并后再按 2048 截一次：写入回执的预警只按单次查询估算，合并后再截会冒出回执没预告过的漏项。文档写作「单次查询 ≤2048 字节」。
- 守卫：单章、日更批末模板的那一行与短篇入口那一句由作者记忆测试的注入契约锚住；组装脚本的多题材合并（累加、去重、按重要度排、不到 8 条不加「等」）、正好 2048 字节的边界、「少而长对多而短」的切片轻重都有回归测试，并对每处做过变异验证。
