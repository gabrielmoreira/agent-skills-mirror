# Provider discovery and setup

Read for a new generation plan, provider setup or the MCP handbook handoff. Apply the entry's provider preference and spend authorization before submission.

## Media handbook handoff

The MCP handbook media-generation example is an explicit request for multimodal guidance. Start with read-only `inspect` even when the user has yet to supply a concrete asset brief. When a provider is usable under the entitlement guidance below, continue the existing request or ask what they want to generate or which reference they want to recreate. Preserve any reference, brief and project context already supplied.

Follow the setup below and the [job procedure](jobs.md) when generation is needed. Read-only onboarding can proceed without creating a project or starting generation.

## Inspect providers and resolve setup

1. Call `openmotion_media_use` with `action: "inspect"`. It lists each provider with `configured`, `available`, `verification` and `reason`, plus `defaults` (the model selected for each modality) and `settings` (where keys are managed). Saving a key in Studio's **Model providers** settings (Chinese UI: **模型供应商**, in the left rail or Settings) enables that provider, and signing in to an OpenDesign account adds its entitled models; configuration alone does not prove entitlement, quota or balance. Handle these setup cases in plain, concise user language, folded into the workflow's single upfront question when it has one. Lead directly with what the user should do next (for example, "I've opened Settings — sign in to OpenDesign under Account first" or "Upgrade to OpenDesign Plus or above under Subscription & usage → Manage subscription"); never use technical or internal phrasing such as "connect the generation service", "verify entitlement", field/tool names, or unconfirmed "opened" claims before presentation succeeds:
   - **No usable provider** (no provider has `available: true`): call `openmotion_open_preview` with `{ target: "providers", entry: "agent_media_signed_out" }` (or `entry: "agent_media_key_rejected"` when a saved key has `verification: "rejected"`) and follow its page handoff. Guide the user to **Settings → Account → Sign in with OpenDesign** (**设置 → 账户 → 使用 OpenDesign 登录**). Free and Go do not include multimodal generation; **OpenDesign Plus or above (Plus / Pro / Max)** includes image, video, speech and music generation, managed under **Subscription & usage → Manage subscription** (**订阅与用量 → 管理订阅**). An OpenDesign Cloud or other supported provider API key can instead be saved under **Model providers** (**模型供应商**), or the user can supply local files. Cloud keys still follow their account's model access and credits. Ask them to tell you once done, then run `inspect` again and continue the original request. For `configured: true` with `verification: "rejected"`, explain that the saved key was rejected and ask them to replace it in the same settings before reinspection.
   - **Signed in, but account `mediaEntitlement: "not-included"`**: the current Free or Go plan does not include multimodal generation; images, video, speech and music start at **OpenDesign Plus or above**. If no other usable provider is available, or the user prefers the account route, call `openmotion_open_preview` with `{ target: "providers", entry: "agent_media_upgrade_free" }` for `plan: "free"` or `entry: "agent_media_upgrade_go"` for `plan: "go"` (falling back to `"agent_providers"` if unknown) and follow its page handoff, then guide them to **Settings → Subscription & usage → Manage subscription** (**设置 → 订阅与用量 → 管理订阅**) to upgrade. Alternatively, they can save an OpenDesign Cloud or other supported provider key under **Model providers**, or provide local media. Wait for confirmation, run `inspect` again and resume the same request. If another usable BYOK provider is already configured, offer/use it under the existing preference and spend-consent rules instead of blocking the task; never silently override an explicit provider choice.
   - **Signed-in account (`available: true`) with `mediaEntitlement: "unknown"`**: the hint is omitted when signed out or reauthentication is required; those states follow sign-in setup instead. For the signed-in unknown case, proceed with model discovery and let live execution check entitlement and balance. Billing refusal or failure is not evidence that a signed-in account cannot generate. `included` is also only a plan hint, not a guarantee of model access or enough credits for this request. `plan` is normalized and `hasBalance` is a boolean when known; inspect never exposes raw dollar balances. Follow the entry's priority: account, OpenDesign Cloud, then other configured providers, unless the user explicitly chose otherwise.
   - **Key works but a needed kind is missing**: check each needed kind with `action: "models", provider, modality, refresh: true` (`image`, `video` or `audio`; among audio models, the discovered `mode` follows the model's operation: speech uses `text-to-speech`, music and sound effects use `text-to-audio`; an input named `text` does not by itself mean speech). If no usable provider offers it, tell the user what their key can and cannot make, explain both supported and missing parts in the consent question, including the proposed alternative (for example locally synthesized BGM if available, user-supplied music or no music). Generate supported parts after consent. Do not silently downgrade a requested capability; if existing authorization does not cover an alternative, keep that part pending and continue independent work.
   - Never silently switch to an unapproved paid provider.
