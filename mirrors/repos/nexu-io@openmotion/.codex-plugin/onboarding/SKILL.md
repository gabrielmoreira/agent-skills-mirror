# OpenMotion onboarding

Complete the welcome, three full-video cards and right-hand template library in the same installation turn. Read [the installation-success contract](../../docs/install-onboarding.md#installation-success-reply) before showing either surface. Reuse the installed application, connection and workspace; setup is complete. Never inject internal instructions through `codex queue` or end the turn to await another onboarding message.

**Curated references require native inline cards.** Default onboarding selects three distinct templates at random from the nine-entry pool once per preparation. Preserve the exact prepared IDs/order and reuse them during recovery. For `inlinePresentation.status=native_required`, do not publish a visualization fragment: its fixed CSP blocks remote posters and videos. Keep the returned welcomeMarkdown for ordinary final-reply streaming, outside the App. Native Tool arguments use onboarding:false so the component contains cards only; after it mounts, stream the welcome once in the final reply. Native cards precede that text; use its above-card pointers. Use the prepared native Tool arguments after confirming the current discovered schema accepts all three IDs. The MCP result binds its immutable resource URI and a recommendation-specific widget session, preventing reuse of an older builtin-only card. Refresh stale discovery through the supported host action; an old three-builtin schema is not compatible with the nine-reference pool. Verify actual image decoding and advancing full-video playback in the mounted native cards. If the current host cannot mount them, report the precise blocker and leave inline delivery incomplete. Do not substitute a right-hand webpage, resample, switch to builtins, download/embed remote media or weaken host security. Inline fragment publication below applies only to self-contained builtin media with `status=prepared`.

1. **Use the prepared result.** Source setup returns `onboardingStatus`, `inlinePresentation`, `preview` and `detailsFile`; read details only if needed. Retained legacy npm setup wraps the result in `onboarding`. Preserve `applicationRoot`, `dataDirectory`, `directAccess` and its environment. If desktop plugin setup supplied no result, run the installed `node --experimental-strip-types scripts/install-onboarding.mjs` once, using the connection's `MOTION_DATA_DIR` and the latest user request's `OPENMOTION_ONBOARDING_LANGUAGE`. This prepares content without reinstalling or creating a project.

2. **Get the chat presentation ready before opening the library.** Finish required file reads, checks and host-route discovery now. During preparation, initialize IAB, create/reuse the exact preview.previewUrl in a hidden tab (visible:false), finish loading the real template list, mark the tab as a deliverable and read the visibility capability documentation. Prefer the prepared inline route for Codex so the welcome can stream as normal reply text. When inline rendering is unavailable and a native presentation tool is already discovered, prepare its arguments: `templateIds: onboarding.catalog.templates.map(item => item.templateId), onboarding: false` and the request's `language`. For a supported inline renderer, publish the prepared path/hash with `node scripts/inline-onboarding.mjs --publish-from PATH --sha256 SHA256 --host-directory DIRECTORY` into this chat's explicitly permitted visualization directory and retain the exact returned `contentReference` and the separate `inlinePresentation.welcomeMarkdown`. The document contains cards only. A runtime/data path is not a readable reference. Preserve the production component and complete videos; choose only one presentation route.

3. **Show both surfaces consecutively.** Prefer the contract's direct IAB route when available; avoid `open_in_codex` followed by another CUA opening. Reveal the already loaded tab with the browser visibility capability and obtain its page state in that same call. This is the one visible check; keep all loading and preparation before it and do not reopen or inspect the page afterward. Complete mandatory browser-tool completion bookkeeping next, then immediately write welcomeMarkdown as ordinary final-reply text followed by the ready content reference on its own line. The welcome streams normally and the cards follow in the same reply; never put welcome text inside the document or imitate streaming with animation. For native cards, call the presentation tool once with onboarding:false, then stream inlinePresentation.welcomeMarkdown (or hostHandoff.welcomeMarkdown) as ordinary final-reply text. The cards precede the final welcome; do not put welcome text inside the App or collapsed commentary. Keep publication, probes and unrelated work before this step. Send the welcome once in the final reply, without duplicated template descriptions or a trailing status paragraph. The host controls final render timing; this sequence minimizes the gap without claiming atomic display.

If either surface cannot be shown, report the actual limitation with the usable library link and preserve this installation. `awaiting_host_delivery`, publication, registration and queued host actions are not display evidence. Resolve `hostHandoff` only when required for the native route; a working inline route needs no restart or MCP refresh. Without a renderer or host-readable directory, do not emit runtime paths or claim complete onboarding.

Use the request's language (or explicit preference): `zh`, `en`, `ja`, `ko`, `fr`, `es`, `pt`, otherwise `en`. Recreate fills an unsent draft only with an explicitly negotiated native composer extension. Otherwise it copies the brief to the clipboard with a floating copied/paste Toast, without a second textbox or task submission. Project creation and export require an explicit user request; browsing alone authorizes neither.

For a user reply accepting a recommendation, continue through [accepted template selection](../../docs/install-onboarding.md#accepted-template-selection) with the accepted ID and scope.

For an explicitly supplied event from an older installation, read that exact file, verify its thread matches this chat and resume `event.onboarding` with its recorded application/workspace. It is recovery input, not permission to enqueue another event or rerun setup.
