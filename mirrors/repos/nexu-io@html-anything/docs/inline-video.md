# Final video playback and editor delivery

Video generation and editing do not mount chat progress or video components. Intermediate saves do not pull up the right-hand editor. Once the final authored HTML and assets are complete and ready for preview, the Agent presents the editable Studio on the right. After the final MP4 export completes and passes technical verification, the chat displays only that final video.

## Contract

1. Create or read the intended project. Use `openmotion_open_preview(action=begin)` silently to establish a work round; this is business state, not UI. Keep its workId through saves and the final export.
2. Author and check the final content without calling a presentation Tool or opening the editor for intermediate saves. Production saves return a deferred preview handoff. An explicit editor-only, show-now or background request retains its scope.
3. When the final video is ready to preview, call `openmotion_open_preview` for the current revision/version and complete its right-hand editable Studio handoff. This does not mount any chat component. A saved empty carrier is not a ready video.
4. Request the final MP4, then wait for the owned job to complete and pass automatic technical verification. Saving or queueing does not mean a video is available.
5. Follow the [shared final-video selection rule](../skills/openmotion-production/references/production.md#choose-one-final-video-preview): prefer the host-native player. Codex defaults to a single final-reply MP4 embed without calling `openmotion_show_video`. Other hosts use native playback when available, otherwise the discovered MCP Apps player; without either capability provide a verified file/link and disclose the limitation. Never display the same export through both routes, including after an uncertain or pending presentation.

The optional `openmotion_show_video({projectId,workId})` is read-only. When needed, it rejects unfinished, failed, missing or changed media, and a large film for which no bounded preview fits; it never creates a project, work round or export. A native preview uses the same completed job’s verified file or a hash-matching, version-specific copy. Requested HTML/project/download links are supplementary deliverables, not a reason to add another player.

Existing domain Tools keep their names and non-App contract; the preferred openmotion_assets_use name is additive alongside its openmotion_assets compatibility name. An MCP Apps connection additionally discovers the final-video presentation Tool; the independent template-card extension remains optional. Ordinary preview/open, save, review and display-receipt operations have no video UI binding. The legacy begin action remains available without presenting progress UI.

## Codex native-preview acceptance

On 2026-11-17, the real macOS Codex desktop conversation (app version `26.1106.51428`, build `26605`) rendered `![Dia 模板视频](/absolute/path/to/Dia.mp4)` as its native video player, with a 24-second duration, playback position, sound, seeking and fullscreen controls visible in user-provided screenshots. The delivery log bound that file to the same SHA-256 as the verified Dia export. This was an actual host rendering observation, not an HTML mock or an inference from Markdown syntax. The duplicate shown above it came from an additional `openmotion_show_video` call.

This MP4 image-reference syntax is a Codex host feature, not standard Markdown video support or a guarantee for every Codex client/version. Use the native route where the installed host supports it; other clients must be checked before selection. A regular file link is the truthful fallback when neither player is available. A pending or unconfirmed presentation must not trigger a second preview.

## Playback and identity

On the plugin-player route, the presentation Tool returns only the completed work identity and `inlineVideoTransport: server-tool`. The App then reads MP4/poster metadata directly with `openmotion_get_project({projectId,workId,includeVideo:true})`; large data URLs never pass through the Agent execution-result envelope. The Tool still validates the completed export and playback availability before presentation. The v2 resource and result binding select this loading protocol; the v1 resource remains readable for existing chats. It supports the observed canonical and bounded wrapped MCP result shapes while keeping media out of visible content. A malformed or conflicting result shows a compact recoverable error rather than silently retaining an obsolete state.

Execution wrappers may include status text alongside one serialized result JSON. The normalizer selects that one result, retains private media from its envelopes and rejects multiple result candidates. The component pins the project/work from the presentation Tool input before parsing results, so even an initial format failure can offer Reload. Initial loading and Reload call only `openmotion_get_project` for that work with `includeVideo`, preserving the presentation version/job/hash identity. Initial loading starts once, concurrent duplicate presentations share that read, and failures require an explicit Reload rather than an automatic retry loop. Read failures and a 15-second media-loading timeout retain this recovery action. Duplicate delivery of an already loaded result preserves its player and playback position.

The component expands its player only after real video data has decoded and has positive dimensions and duration. Duration comes from the media, not update timestamps or an authoring timer. Playback is manual. Verified local bytes are loaded through a browser-owned Blob URL for seeking and replay; the resource declares both data and blob origins. Teardown releases the Blob, and hidden components pause playback.

Each final frame keeps its immutable work/version/job/hash identity. Later edits start another business round without mounting progress UI; only the next completed final video gets another player. Reopening an old chat reads that round's own result, never the project's latest export. Resource failures retain recovery without starting another render.

## Limits and verification

Playback requires a completed owned export, matching version/revision, passed technical report, regular local file and matching SHA-256. Verified exports up to 8 MiB return their own bytes through the direct App-to-server read. Native Codex acceptance found a 6.8 MB film arriving through the Agent result as an approximately 1 MiB envelope with invalid private media, while a direct App read recovered it; this is why initial presentation carries no media bytes. Codex's MCP stdio transport drops message lines above 16 MiB and base64 grows bytes by 4/3, so a larger export embeds a re-encoded H.264/AAC preview (720p, then 540p, then 360p, within a 45-second budget) that must fit under 8 MiB and decode. The preview is cached per job and verified SHA-256 and is discarded if the source changes while encoding. The verified export itself is unchanged. If no preview fits, the Tool returns `INLINE_MEDIA_UNAVAILABLE` and the Agent reports the playback limitation while retaining the verified export. The native-host route does not use this App media transport or its embedding-size budget; the host’s own file access and limits apply. For a plugin timeout, return a plain file link and keep presentation pending rather than adding another player. Additional downloads follow the requested file scope. Media stays local; no cloud upload is introduced. Technical verification, actual player playback, editor visibility and creative/audio acceptance remain separate checks.

The implementation is covered by protocol discovery, deferred-handoff, final-player DOM, real two-round rendering and distribution checks. A local browser/SDK harness does not establish native Codex acceptance of a newly installed build. Existing host connections must refresh discovery before using the new presentation Tool; source changes do not update a running plugin automatically.
