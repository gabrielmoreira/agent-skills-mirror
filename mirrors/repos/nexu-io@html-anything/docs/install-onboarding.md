## Installation-success reply

### Reference media and native inline delivery

Default onboarding samples three distinct entries from the curated nine-reference pool once and freezes their IDs/order across catalog, handoff, native presentation and recovery. References keep their full remote videos and posters at the approved public media origin. Codex's fixed visualization CSP cannot inherit the native App's `ui.csp.resourceDomains`; preparing those references therefore returns `inlinePresentation.status=native_required`, exact cards-only native Tool arguments (onboarding:false), separate welcomeMarkdown and no broken HTML document. After mounting the native cards, the Agent streams welcomeMarkdown once as its ordinary final reply. The native Tool result precedes that final text, so this version of the welcome points to cards above. Never move the welcome into the App or collapsed commentary, or imitate streaming with an animation. Use a compatible natively discovered Tool in the calling conversation. Each Tool result pins its negotiated immutable resource URI and a separate `openai/widgetSessionId` so an older builtin-only mounted card cannot be reused as the new recommendation. Check the current Tool schema, resource version, actual image decoding and advancing video playback, including enlarged preview. A stale schema needs a supported connection refresh; registration, shell RPC and another process's probe are not native delivery evidence. Preserve the selection and report a real host blocker if unresolved. A right-hand browser page does not satisfy inline cards and must not replace them. Do not bypass host policy with downloaded-media embedding or security changes. The fragment route below remains available only for self-contained builtin examples with `status=prepared`.

Every successful Agent-led OpenMotion installation opens the editor's template library in the current conversation. Do not ask whether to experience a recommended template or wait for a yes/no reply before opening the library. Respect an explicit request not to open it, or a previous refusal/deferment. If the user already explicitly requested creation with an exact template, continue that authorized task directly.

For Codex, complete the normal streamed welcome reply, three full-video cards and visible right-hand library in the same installation turn. Installation is one user request, including onboarding. Use native MCP Apps for the default curated reference cards so their remote images and videos receive the declared media policy. The bounded fragment renderer remains available for self-contained builtin media, returning welcomeMarkdown and a cards-only document. `host_action_required` and `refresh_requested` remain incomplete when neither presentation route works, even if CLI setup exits zero and the library works. Report the concrete host limitation and preserve this installation for recovery.

Keep the returned `contentReference` and `inlinePresentation.welcomeMarkdown` ready. 2. **Present at the end.** Reveal the already loaded IAB library as the last presentation operation: set browser visibility to true and read its page state in that same call. This is the one visible content check; do not reopen the URL, create another tab or request another snapshot afterward. Complete any mandatory browser-tool completion bookkeeping next, then immediately write `inlinePresentation.welcomeMarkdown` as ordinary final-reply text followed by the ready `contentReference` on its own line. This lets the host stream the welcome before mounting the cards in that same reply. Keep welcome text out of the cards-only document; do not simulate streaming with a typewriter animation. For native delivery, call its presentation tool once with onboarding:false and then stream the separate welcomeMarkdown as ordinary final-reply text; cards precede the text in this route. Keep file reads, publication, probes and unrelated investigation out of this interval. The final reply contains the welcome once; the cards stay in the same conversation; add no earlier success message or trailing status reply.

This minimizes the gap between the library and chat content. The host owns their rendering and does not expose an atomic two-surface display operation; do not claim exact simultaneous rendering. Preserve the production component and full videos, use only one presentation route, and distinguish prepared/published content from actual display.

The inline document context has no negotiated unsent-composer extension. Recreate copies the complete brief to the clipboard and shows a floating localized copied/paste Toast, without inserting a second textbox or sending a task. The user pastes/edits and sends the brief before creation. Continue operations through this installation's `directAccess`, including its selected profile environment when supplied. Codex plugin setup reaches this same contract through the packaged `extensions.com.openai.onboardingSkill` entry. ### CLI installation: attach the calling chat before presentation

CLI registration does not run the desktop install callback. Source and npm Codex setup return `onboarding.hostHandoff` after registration. They use an existing Codex app-server control socket to request `config/mcpServer/reload`, then inspect `mcpServerStatus/list` with the calling `CODEX_THREAD_ID` and read `openmotion_get_project` through that same thread. An unrelated daemon is refused before refresh. They never start another app-server to simulate a connected chat. `OPENMOTION_CODEX_SOCKET` may select an explicitly known local control socket; do not guess sockets or change the host's listener/security configuration.

Working native tool discovery and a matching `openmotion_get_project` read in this chat supersede an earlier pending handoff result. When those native tools are already loaded, use them directly; do not require a control socket or repeat setup to clear a historical pending status.

Set `OPENMOTION_ONBOARDING_LANGUAGE` from the latest user request when running setup; supported codes are listed below. The host Agent must still use that request language for the native presentation, regardless of the terminal/UI locale.

- `ready_for_presentation` confirms the calling chat's workspace read and native presentation-tool discovery. Open the library, then call the discovered tool natively. `presentationVerified` remains false until the welcome and all three video cards are actually visible.
- `refresh_requested` means the host queued a refresh. After the current tool step finishes, run the installed `scripts/codex-host-handoff.mjs --verify-only` once (with Node type stripping enabled and the same data-directory environment). That verification does not request another reload or present duplicate cards.
- `host_action_required` keeps onboarding incomplete and supplies the exact host RPC handoff. A desktop host running only over private stdio may not expose a CLI control socket. Use an available supported host reload action; if none is accessible, explain that concrete limit and request the minimum user action to reload the existing chat. Do not report a complete onboarding, silently substitute a library-only welcome when full onboarding was requested, or repeat installation/probes. Never call the presentation through a shell RPC and claim it appeared in the conversation.

This host handoff does not authorize project creation, export, host restart, or changes to unrelated host settings. Independent MCP diagnostics and ordinary non-UI hosts retain the library-only fallback; they do not establish native onboarding acceptance.

### Open the library without creating a project

Do not require a new chat, repeat installation, or create a project to obtain a link. `onboarding.catalog` is compatibility data, not a required recommendation or creation step.
3. Present the exact URL in the calling chat's right panel, preserving embed/query parameters. When CUA exposes this chat's IAB, prepare its real page with `cua.createBrowserTab('iab', previewUrl, {visible:false})` (or reuse the matching tab), finish loading and mark it as a deliverable before the final reveal. After cards/publication and all required checks are ready, show it with the browser visibility capability and obtain its page state in the same call. Complete mandatory browser bookkeeping next. For builtin fragments, immediately stream welcomeMarkdown followed by the ready cards reference. For native references, mount the cards-only Tool and then stream welcomeMarkdown in the final reply. Do not first queue `open_in_codex`, reopen the same URL or inspect it again after the reveal. When direct IAB is unavailable, use `open_in_codex` with `placement: "right"`, the exact browser URL and no other threadId; report an unobserved or queued result accurately. Native Codex app automation is unnecessary. Queue only when the host confirms the chat is inactive; a queued acknowledgment alone does not establish visibility. Do not submit project `record_display` receipts for the library.
4. If the host has no browser/panel, provide the actual library link and explain that it could not be opened automatically. If setup returned `onboarding.preview.status=unavailable`, report the installation result and the concrete preview failure; retry with the templates target when MCP is available. Never claim opening succeeded or silently create a fallback project.

## Maintained recommendation selection

`shared/onboarding-templates.ts` owns a curated pool of nine references: **Bolt Skills｜团队能力展示**, **A New Era of No-Code**, **Magic Share**, **Glean Agents 发布**, **HyperOS 官网界面动效 1**, **Salsa｜音乐主题 Doodle**, **功能更新｜Voice mode**, **Dia 开放给 Arc 会员**, and **免费语音输入**. Each onboarding preparation samples three distinct entries without replacement. Inline cards, native handoff and the fallback catalog share that exact selection and order. The prepared document keeps its selection while playing, returning from detail or changing host context; only a new preparation draws again. Independent preparations may overlap.

Use the three prepared IDs returned in `inlinePresentation.templateIds`, the ordered `catalog.templates`, or the native handoff arguments. Do not draw a separate set for another surface. Every selected entry is a reference video with motion guidance, not a directly copyable builtin project; read its exact ID through `openmotion_get_template` and follow `openmotion-recreate` after the user submits their brief.

Full reference videos and posters load from existing immutable public `r.open-design.ai` URLs, with the same playback controls, visibility pauses and error fallback as bundled previews. Playback requires network access; installation preparation performs no media download or generation. The three previous builtin examples remain available for explicit recommendations and offline preview. Existing chats retain their frozen presentation; source changes do not update an installed host or previously prepared onboarding document.

Cards show the selected reference's localized `original.promotionalUseCases` value in a persistent top-left media badge, without a field-name prefix. This purpose category stays visible while the video plays and at narrow widths; the bottom-right preview action remains separate. Empty/missing values are omitted. The category does not use the separate `visualPresentation` field or infer a value from the title. The shared design-system media-label recipe supplies its translucent surface and typography.
