# 2026-11-15 专题报告：llama.cpp v1.0.0 升级 / MoE 专家缓存 / 驱动「2.2 倍」辨析

> 硬件基线：RTX 5060 Ti 16GB、48 GiB RAM、Windows、NVIDIA 驱动 621.24。
> 被测模型：Qwen3.6-35B-A3B（Q4_K_P，41 层含 MTP 头、`nextn_predict_layers=1`、256 专家/8 激活）+ f16 mmproj。
> 全部测试在隔离端口逐次启动、逐次停止，未改动生产配置。

---

## 1. 一句话结论

**「驱动更新让 MoE 解码快 2.2 倍」在本类 16GB 卡上不成立，且不需要为此新增任何参数。**
2.2× 的前提是「把大量专家留在内存 + 在显存里放十几 GiB 专家缓存」，而本机 262K 配置在加载后只剩 **约 204 MiB** 高于 llama.cpp 自身要求的余量——连 256 MiB 缓存都放不进去。
升级 v1.0.0 的真实收益是 **0–6.5%**（短请求 +6.5%，长上下文 prefill 持平），不是数量级。

### 2.1 上游「2.2 倍」的原始条件（PR #29887）

| GPU | 方案 | 显存内专家 | tg t/s | 倍率 |
|---|---|---:|---:|---:|
| RTX 5090 | 原 `--fit` | 24.5 GB（全部层） | 30.8 | 1.00× |
| RTX 5090 | `--fit --moe-cache-mib 6544` | 17.9 + 6.4 GB | 54.5 | 1.77× |
| RTX 5090 | `-cmoe --moe-cache-mib 19000` | 0 + 18.6 GB | 67.8 | **2.20×** |

条件：Qwen3.8-Flash-Next Q4_0 **93.7 GiB**（专家 65.4 GiB）、无 MTP、EPYC 7742 16 核同 NUMA、PCIe 4.0 x16。
**关键不是参数名，而是「模型远大于显存，且显存能装下十几 GiB 缓存」这两个前提。**

## 3. 生产原参数实测（262K / 单槽 / 34 层 / MTP n-max 4 / q8-q8 / mmproj / cache 0）

### 3.1 短请求（25 token 输入、384 token 输出上限）

| 版本 | 两次稳态 decode t/s | 中点 | 相对旧版 | MTP 接受率 | 最低空闲显存 |
|---|---:|---:|---:|---:|---:|
| b12274 | 56.21 / 55.63 | **55.92** | 基线 | 0.492 | 2333 MiB |
| b12359 | 59.23 / 59.92 | **59.57** | **+6.5%** | 0.497 | 2337 MiB |

两组都 `finish_reason=length`、无可见答案（384 token 全用于思考）⇒ **只可用于固定长度吞吐对照**。

### 3.2 长上下文（12,863 token 输入，贴近真实 Agent 回合）

| 指标 | b12274 | b12359 |
|---|---:|---:|
| 首轮 prefill t/s | 1679.8 | 1685.7 |
| 首轮 prefill 墙钟 | 7.66 s | 7.63 s |
| 首轮 decode t/s | 68.2（79 tok，stop） | 69.7（128 tok，length） |
| 同上下文二次进入 | 12,859/12,863 命中，实测 74 ms | 同，78 ms |
| 续问（新增 2,063 tok）prefill | 1551.6 t/s | 1550.6 t/s |
| 续问 decode | 68.8（347 tok） | 70.6（364 tok） |
| 答案 | `FINAL: 619` ✅ | `FINAL: 619` ✅ |
| 视觉（程序生成图片） | `AX-4719 / 238.75` ✅ 75.7 t/s | 同 ✅ 77.2 t/s |
| MTP 接受率（3 次） | 0.679 / 0.680 / 0.741 | 0.657 / 0.705 / 0.746 |
| 最低空闲显存 | 2153 MiB | 2159 MiB |

**三条可复用结论**：

1. **decode 速度由 MTP 接受率决定，不由上下文长度决定**：同一模型短请求（接受率 0.49）只有 56 t/s，长上下文任务（0.66–0.74）反而 68–77 t/s。用「短 prompt 测速」评估 Agent 体验会**低估**。
2. **prefill 与版本几乎无关**（差 < 1%），升级不会改善首字延迟；12.8K 输入 ≈ **7.6 s** 首字。
3. **Agent 多轮真正的成本优势来自前缀缓存**：同上下文二次进入只重算 4 token（74 ms），续问只重算新增的 2,063 token。

### 3.3 行为差异（单样本，需留意）

同一「只回复序列号」请求：旧版 79 token 收尾并给出正文；新版思考到 128 token 上限仍未进正文（`finish=length`）。Router 模式复测同向（143 vs 197 输出 token，答案都对）。
⇒ **客户端 `max_tokens` 卡得紧时，新版可见答案更容易被思考段吃掉**；升级后建议 Agent 侧输出上限 ≥ 2048。

## 4. 显存余量体检：fit 判决行才是硬指标

`--fit on` 在 MoE 条目上**会运行**（早期 build 的 A/B 只是观察到「结论不变」，不是「没运行」）。b12274 生产原参数实测输出：

```
| CUDA0 (RTX 5060 Ti) | 16283 = 15172 + ( 7325 = 5628 + 512 + 1185) + -6213 |
| Host                | 18261 = 17204 + 1057                              |
projected to use 12236 MiB of device memory vs. 15172 MiB of free device memory
will leave 2935 >= 2129 MiB of free device memory, no changes needed
```

- **程序要求的最低余量**：`2129 MiB`；投影余量 `2935`；**实测**最低 `2333`。
- 真实富余 = 2333 − 2129 ≈ **204 MiB**。
- `Host model 17204 MiB` ≈ 16.8 GiB，就是 34 层专家权重（与 GGUF 张量表直算吻合）。

⇒ 日常体检只需看这一行：`will leave X >= 2129 MiB`。**X 逼近 2129 就不要再加任何显存占用**（缓存 / 并发槽 / 更大的 mmproj / 同机其它 GPU 程序）。
⇒ ⚠️ **未验证**：投影不足时 fit 是否会真的下调（没有 `--no-alloc` 之类零风险探针，强行试会 OOM/不稳定）。**所以 fit 不是安全网，只是体检仪**。

## 5. MoE 专家缓存（`--moe-cache-mib`）的适用边界

### 5.1 8K 上下文（同参数只缩短 ctx）

| 版本 | 缓存 MiB | decode t/s | 相对关闭 | 最低空闲显存 |
|---|---:|---:|---:|---:|
| b12274 | 0 | 57.12 | 基线 | 7429 |
| b12274 | 256 | 37.54 | -34.3% | 7165 |
| b12274 | 512 | 37.89 | -33.7% | 6919 |
| b12274 | 1024 | 36.77 | -35.6% | 6407 |
| b12359 | 0 | 59.95 | 基线 | 7433 |
| b12359 | 256 | 41.36 | -31.0% | 7173 |
| b12359 | 512 | 35.24 | -41.2% | 6915 |
| b12359 | 1024 | 38.40 | -36.0% | 6407 |

两个版本、四个档位方向一致：**在这类「16GB 卡 + 35B-A3B + 34 层 CPU 专家」配置上，缓存是负优化**。日志无命中率，故只报现象不给根因。`--moe-cache-cpu-share` 未扫描（主档位全线下降）。

### 5.2 262K 上下文：**放不下，不是「没测出来」**

按 §4 的余量：`2333 − 256 缓存 − 512 预留 < 2129` ⇒ 加缓存直接跌破程序要求。这也是**不做该实验的原因**。

### 5.3 什么时候才值得考虑缓存

- 模型总专家体量 ≫ 显存，且**显存能空出 ≥ 10% 专家总量**（上游原文建议 `10% of total expert size`）；
- 负载是**小批量解码**（≤ 32 token/批），大 batch prefill 走另一条路径；
- 有办法量到命中率与传输开销（否则「变慢」也无法归因）。

三条只要有一条不满足，就先别开。

## 6. `n-cpu-moe` 34 vs 36 的受控实验（交错重复）

| 场景 | 34 层 | 36 层 | 结论 |
|---|---:|---:|---|
| 短请求 decode（3 组交错、各 2 稳态样本） | 55.65 / 55.95 / 55.32 | 58.03 / 58.96 / 57.69 | 36 层 **+4.7%** |
| 对应 MTP 接受率 | 0.486（三组一致） | 0.532（三组一致） | 配置级差异，非噪声 |
| 12.9K 长上下文 prefill | 1668 / 1498 t/s | 1580 / 1467 t/s | 36 层 **慢 2%–5.3%** |
| 12.9K 长上下文 decode | 66.9 / 68.9 / 69.3 | 68.3 / 69.0 / 66.9 | 基本持平 |
| 最低空闲显存 | 2333 MiB | 3593 MiB | 36 层多 1.26 GiB |
| 最低可用内存 | 12269–12852 MiB | 11409–11983 MiB | 36 层多吃约 1 GiB RAM |

解释：多卸两层把短 prompt 的 MTP 接受率推高（0.486→0.532）带来 +4.7%，但长上下文 prefill 由 CPU 专家主导，多卸载反而变慢，decode 收益消失。
⇒ **不构成普适提速，不作为生产建议**；只有在需要额外显存余量（安全垫）时才当作杠杆，代价是 RAM 与 prefill。

## 7. Router 参数优先级：ini 里的 `parallel` 是死参数

源码（Router 会把命令行参数**覆盖**到每个模型 preset 之上）：

```cpp
// tools/server/server-models.cpp
// overlay router's own CLI args on top of every model preset so that
// e.g. `llama-server --temp 0` is honoured by all child processes
for (auto & [name, preset] : final_presets) { preset.merge(base_preset); }
```

实测（用新二进制 + 原 ini 起 Router，读 `/models` 拿到渲染结果）：

```
--parallel 1 --ctx-size 262144 --n-cpu-moe 34 --n-gpu-layers 99
--spec-type draft-mtp --spec-draft-n-max 4 --cache-type-k q8_0 --cache-type-v q8_0
--batch-size 2048 --ubatch-size 2048 --load-mode none --fit on --fit-ctx 65536 --mmproj ...
```

⇒ **ini 写 `parallel = 3`、启动器写 `-np 1` 时，生效的是 1 槽。**
⚠️ 反向陷阱：把 `parallel` 调大**不会**因为 ini 里写着 3 就生效，但一旦真的把 `-np` 调到 3，同一份 34 层配置实测只剩 **2189 MiB**（越过安全线）——因为每槽都要吃 compute buffer 与 KV。

## 9. 这些数字的边界（不要外推）

- 短请求只有 2 个稳态样本/组；长上下文每个条件 1 次。**没有置信区间**。
- 以下场景没有测：满 262K 输入（最长 12.9K，占 4.9%）、多并发（生产单槽排队）、复杂图片 OCR、多天稳定性、菜单启动器路径（37 层 / 3 槽）。
- 客户端侧墙钟包含轮询开销，**不能**当端到端延迟；一律用服务端 `prompt eval time` / `eval time` 与完整请求墙钟。
- 所有结论都绑定「16GB 卡 + 该 35B-A3B 模型 + 该量化」；换模型/换卡请重测。
