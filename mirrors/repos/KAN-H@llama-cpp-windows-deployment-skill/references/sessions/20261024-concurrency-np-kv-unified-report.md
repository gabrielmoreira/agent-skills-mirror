# 并发（n_parallel）与统一 KV 池（`--kv-unified`）专项报告

**日期**：2026-10-24 ｜ **执行**：GitHub Copilot（llama-cpp-windows-deployment 技能工作流）

> 硬件：单卡 16 GiB（RTX 5060 Ti 级）· 驱动 617.42 · Windows 11
> 构建：llama.cpp 0.6.0-dev (b11571) 为主，Vulkan 侧另用 0.7.0-dev (b11836)
> 模型族：qwen35 dense 27B（内置 MTP head）+ qwen35 MoE 35B-A3B（嫁接 MTP head）+ Gemma4 / 9B 级小模型
> 脱敏说明：一切部署路径写作 `<llama-cpp-dir>` / `<models-dir>`，端口写作 `<port>`，key 用 `sk-local-001` 占位。

## 1. 三条核心结论

1. **`np>1` 与 MTP 在 16 GiB 卡上是耦合的，不是两个独立旋钮。** 把 np 从 1 提到 2 需要约 **318 MiB**，
   而一个 141K 上下文 + MTP 的 27B dense 模型只剩 **313 MiB** —— 差几十 MB 就足够让驱动崩溃。
2. **`--kv-unified` 让并发几乎不花上下文、也几乎不花显存。** 加了它以后 `-c` 是**池子总大小**，
   `n_ctx_slot` 恒等于 `-c`（任何 np 下都实测如此），单次请求可以独占整池。
3. **并发不降单流速度。** MoE 侧 np=1/2/3/4 的单流解码 57.3 / 56.7 / 57.3 / 58.2 t/s，
   差异全在噪声内；代价只出现在「满载时每流分摊」上。

## 2. 事故复盘：一次可预测的绿屏（BugCheck `0x00020001`）

### 现象
- 系统日志：`检测错误: 0x00020001 (0x28, 0x1, ...)` —— `HYPERVISOR_ERROR`，非普通 OOM。
- 崩溃发生在**发出第一个请求之前**，服务端日志无任何推理记录，距上一条测量记录只有 5 秒。

### 证据链
| 时间 | 事件 |
|---|---|
| np=1 三次测量全部正常收尾 | 日志末行 `stop processing`，记录文件已落盘 |
| 记录落盘后 5 秒 | 系统绿屏重启 |
| 崩溃时的显存 | np=1 已占 **16,000 / 16,311 MiB（剩 313）** |

### 机理
用同一台机器、同一个 `--kv-unified` 口径测出**第二个 slot 的显存代价**：

```
MoE 35B-A3B, ctx 260,000, KV q8_0:  np=1 -> 12,572 MiB ; np=2 -> 12,890 MiB   ⇒ +318 MiB
27B dense,   ctx 141,312, MTP off :  np=1 -> 14,550 MiB ; np=2 -> 14,702 MiB   ⇒ +152 MiB
```

⇒ 27B dense 的 `16,000 + 318 = 16,318 > 16,311`。**在分配阶段就失败**，所以来不及报干净的
`out of memory`，而是把驱动带下去了。

> **教训**：这张卡上「剩 300 MiB」不是"还能跑"，是"下一次分配就崩"。
> 多 slot、多上下文、多 MTP 上下文都会在启动期一次性要显存 —— 那是**最容易越界**的时刻，不是推理时。

### 加固（已内置到 `scripts/np_probe.py`）
- `--prior-headroom N`：**np>1 时，若同模型同 ctx 的 np=1 实测余量 < `--min-headroom`（默认 1024 MiB），
  直接拒绝启动**（exit 4），一个字节都不分配。
- `--min-headroom N`：加载完成后若余量不足，**在发出任何请求之前**中止并落盘日志（exit 3）。

## 3. `--kv-unified` 语义（本 build 实测）

| 项 | 不开启（默认） | 开启 |
|---|---|---|
| KV 池 | 每个 slot 独立 `-c / np` | 单一共享池，总量 `-c` |
| `n_ctx_slot` | `-c / np` | **`-c`**（实测 np=1/2/3/4 全部等于 `-c`） |
| 开 2 路对上下文的影响 | **每路砍半** | **无影响**，单请求可独占整池 |
| 额外显存 | — | ~152–318 MiB（视模型与 MTP） |

⚠️ 默认只在 `-np` 为 auto 时启用；**显式给 `-np N` 时必须手动加 `--kv-unified`**，否则每路上下文被静默砍半。

## 4. np 阶梯实测

### 4.1 MoE 35B-A3B（ctx 260,000 / KV q8_0 / 专家卸载 34 层 / b=ub 2048 / MTP nmax 4）

| np | n_ctx_slot | c=1 单流 | c=2 聚合 | c=3 聚合 | c=4 聚合 | 显存余量 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 260,096 | 57.31 | — | — | — | 3,739 |
| 2 | 260,096 | 56.71 | 64.95 | — | — | 3,421 |
| **3** | 260,096 | **57.30** | 64.80 | **75.24** | — | 3,101 |
| 4 | 260,096 | 58.16 | 65.50 | 76.51 | 77.81 | 2,643 |

（聚合为墙钟口径、含 prefill；每档 `cuda_err=0 / assert=0 / 质量对比一致`）

**定档 np=3**：np=4 的 c=4 只比 c=3 多 **+1.7%** 聚合，但每流从 33.9 掉到 26.2 t/s（−23%），余量还少 458 MiB。

### 4.2 dense 27B（ctx 141,312 / KV q4_0 / b=ub 256）

| 配置 | np | 单流 | 双流聚合 | 显存余量 |
|---|---:|---:|---:|---:|
| MTP **开** | 1 | **~55 t/s** | — | **313 MiB** |
| MTP **关** | 1 | 29.8 | — | 1,761 MiB |
| MTP **关** | 2 | 29.8 | **39.9** | **1,609 MiB** |

⇒ 该模型在 141K 下只能二选一：**单请求最快**（MTP 开，无并发）或 **两路并发**（MTP 关，余量 5 倍）。
没有任何办法同时拿到（除非降 ctx）。

### 4.3 小模型（np=2 + MTP 的安全性验证）

| 模型 | 显存占用 | 余量 | 结论 |
|---|---:|---:|---|
| Gemma4 E4B + MTP | 6,326 | 9,985 | ✅ 安全 |
| QwenPaw 9B + MTP | 7,934 | 8,377 | ✅ 安全 |

**⇒ "MTP 与 np 互斥"是显存条件问题，不是规则本身**：小模型余量够就可以同时开。

## 5. 测量陷阱：不要把首请求当稳态

GPU 空闲时 SM 时钟只有 **195 MHz**。同一个配置：

| 第几次请求 | 256 token 用时 | 推算 t/s |
|---|---:|---:|
| 第 1 次（刚加载完） | 12.4 s | ~20.6 |
| 第 2 次 | 4.86 s | 52.7 |
| 第 3 次 | 4.65 s | 55.1 |
| 第 4 次 | 4.66 s | 54.9 |

**⇒ 至少连测 3 次、取后两次**。否则会把"冷时钟"误读成"配置退化"，从而错误地回滚一个其实更优的配置。

## 6. 落地模式：耦合参数必须做成「原子条目」，不能只放进参数面板

一个工作点若由**多个互相依赖的参数**决定（本例：`n_parallel` + `spec-type`），把它拆进"可调参数面板"就是
在生产环境里组装地雷 —— 用户完全可能只把 np 改成 2 而忘了关 MTP。

因此本仓库采用两层：

1. **模型级条目（首选路径）**：每个工作点是一个独立条目，参数组合预验证、原子生效。
   生成器支持 `variants`：一条主条目可派生若干变体，`drop` 先摘除继承键，`params` 再覆盖，
   于是"np=2 且 MTP 关"这件事在配置里是**一个不可拆分的事实**，而不是两条可能失配的配置。
2. **参数面板（补充路径）**：仍暴露 `n_parallel`，但写入前做**跨字段硬校验** ——
   当 `parallel > 1` 且该条目 `spec-type == draft-mtp` 时**直接拒绝保存**，并打印实测证据。

## 7. 客户端侧（agent 框架）同类教训

同一批工作里还定位到一个**通用**的上下文管理 bug，与本技能的主题相邻，值得记下：

- 客户端为每个模型声明 `contextWindow`。有人把**模型训练上限**（256K）填成了这个字段，
  而服务端实际只开 `-c 141K`。
- 自动压缩的触发点通常算作 `min(contextWindow * thresholdRatio, contextWindow - headroom)`。
  填 256K 时触发点 ≈ **188K ≫ 服务端 141K** ⇒ **永远不主动压缩**，一路涨到服务端报
  `CONTEXT_WINDOW_EXCEEDED`，才被迫做**一次 ≈141K 的全量摘要 prefill** —— 这正是把显存推到墙上的那一下。
- 修法：**`contextWindow` 必须等于服务端真实 `-c`**。改后触发点降到窗口的 ~48%，压缩请求本身的规模
  也跟着降到安全区（本例实测 65.7K token 的单发 prefill：prefill 695 t/s、显存与 45K 时**完全一致**）。

⇒ **通用规则：任何"上下文窗口"字段都必须与服务端实际 `-c` 对齐，填模型的理论上限只会让保护机制失效。**

## 8. 复现与验证

```bash
# 1) 先跑 np=1 拿真实余量（任何 np>1 测试的前提）
python scripts/np_probe.py --model-dir <model-dir> --ctx <ctx> --np 1 \
    --kv-k q4_0 --kv-v q4_0 --batch 256 --ub 256 --ngl 99 --tag <tag>-np1

# 2) 用上一步的余量作为闸门，逐档上探
python scripts/np_probe.py --model-dir <model-dir> --ctx <ctx> --np 2 \
    --kv-k q4_0 --kv-v q4_0 --batch 256 --ub 256 --ngl 99 \
    --prior-headroom <上一步 headroom_mib> --min-headroom 1024 --tag <tag>-np2
```

`scripts/np_probe.py` 每档独立加载一次服务，按 `c = 1..np` 发**互不相干**的并发请求，
并记录：每流/聚合吞吐、`n_ctx_slot`、`kv_unified`、显存余量、CUDA error / GGML_ASSERT 计数，
以及**请求前后的质量问答对是否完全一致**（用于证明"并发不损精度"）。

## 9. 安全红线（照做即可）

1. **np>1 前，np=1 的实测余量必须 ≥ 1,024 MiB**；不满足就先降 ctx / 降 KV 精度 / 关 MTP。
2. **np>1 与 MTP 只在余量充足时才能共存**；余量紧张时二者必须二选一。
3. **测速连测 3 次取后两次**（GPU 冷时钟陷阱）。
4. **参数改完必须重新生成**工件，不要手改生成物（尤其 GBK 的 `.bat`）。
