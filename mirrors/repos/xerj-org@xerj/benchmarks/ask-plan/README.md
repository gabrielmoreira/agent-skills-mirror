## The pairs

`data/gold/pairs.jsonl` — 230 lines, one pair per line, generated by
`scripts/derive_pairs.py` (python3 stdlib, deterministic: fixed template
order, fixed value lists, seeded phrasing choices; re-running on the same raw
bytes reproduces the file byte-for-byte, which `--check` asserts):

```json
{"id": "usgs-earthquakes-001",
 "dataset": "usgs-earthquakes",
 "index_hint": "ax-usgs-earthquakes",
 "prompt": "all events with magnitude 2.75 or greater",
 "gold": {"index": "ax-usgs-earthquakes",
          "doc_ids": ["aka2026rijzmt", "..."],
          "query_equivalent": {"range": {"mag": {"gte": 2.75}}}}}
```

- **Gold is derived from the source data only.** Each template filters the raw
  CSV rows in Python (`mag >= 2.75` over the committed snapshot) and the
  matching rows' `_id`s become `doc_ids`. **No engine is ever run to produce
  gold** — not at derivation time, not as a cross-check. `query_equivalent` is
  the predicate the prompt names, written as DSL (`term` / `range` /
  `bool.filter`, the shapes `engine/crates/xerj-query/src/parser.rs` parses);
  the harness *executes* it later as a fixture self-check, never as gold.
- **`_id`s are data-derived**, not row-order-derived: the USGS event `id`
  column, the exoplanet `pl_name`, `"<country>-<year>"` for gapminder. The
  loader (`scripts/ask_arm.py load`) bulk-indexes with the same `_id`s, so
  gold and index contents are tied to the same bytes.
- **Set sizes:** min 1, median 72.5, max 1,464 over the 230 pairs (cap 1500) —
  big enough that a 10-hit-default truncation scores badly, small enough that
  whole-set comparison at `size: 10000` is exact.
- A pair is kept only when its gold set is non-empty and ≤ 1500; if a raw
  refresh ever thins the set below 200 pairs, `derive_pairs.py` **refuses to
  write** rather than shipping a thinner gate.
- Prompts name values that exist in the data (that is what makes result-set
  F1 meaningful). Prompts that should *fail* — #1056's "unresolved phrases
  return 422 naming them" — live in `data/gold/negative-prompts.jsonl`, are
  NOT counted in the 230, and are not yet asserted by the harness (see Not
  covered).

## Scoring (the definition the future run will be held to)

For each pair: `POST /_ask {"index": <gold.index>, "prompt": <prompt>}` →
take the returned query DSL, execute it against `gold.index` at
`size: 10000`, compare the hit-`_id` set against `gold.doc_ids`:

```
precision = |got ∩ gold| / |got|        recall = |got ∩ gold| / |gold|
F1 = 2PR/(P+R);  both empty → 1.0;  one empty → 0.0
```

- HTTP 4xx/5xx from `POST /_ask`, or a returned query that fails to execute
  (HTTP 400 — the observable form of "fails `parse_request`"), or a 200 with
  no usable query: the pair scores F1 = 0 **and** increments
  `invalid_dsl_out`, which has its own zero-tolerance line.
- The gate metric is **macro-F1** (mean of per-pair F1) over all ≥ 200 pairs —
  the issue says "result-set F1 ≥ 0.9" without pinning the aggregation; this
  harness pins it as macro over pairs, reports per-dataset and micro numbers
  alongside in `summary.json`, and says here that it made that choice.
- Determinism: each pair is asked `DETERMINISM_RUNS` (default 3) times; all
  responses must be identical (#940's stable-tie-order lesson). The count of
  non-deterministic pairs is a gate field, not decoration.
- Raw per-pair responses land in `ask-raw.jsonl` unmodified; `summary.json`
  is derived from them. A run's numbers are recorded under
  `results/<date>-<label>/` and only enter this README after review — nothing
  self-updates.

## The agent-harness comparison (DESIGN, unrun)

`scripts/agent_arm.py` implements the case-study method the issue names —
the method of `docs/case-studies/reference-coding/CASE_STUDY.md`, whose
head-to-head (9,982 vs 26,477 output tokens, 16/16 vs 16/16 solved) is
**prior context for the method, not a result of this harness and not about
/_ask**:

- **8 tasks × 2 trials = 16 runs per arm**, tasks seeded-picked from
  `pairs.jsonl` across all three datasets.
- **`direct` arm:** the agent gets the index mapping and the task prompt,
  writes the `_search` body itself; the harness executes the emitted JSON
  verbatim.
- **`ask` arm:** same mapping and task, plus the knowledge that `POST /_ask`
  exists; the harness executes what the endpoint produced.
- **Solved** := the returned body executes AND result-set F1 ≥ 0.9 vs gold.
- **Tokens** are read from the `usage` field of real
  `claude -p --output-format json` runs — counted, never estimated. No
  `claude` CLI on PATH ⇒ the script refuses rather than approximates.
- **Gate:** median output tokens per solved task in the `ask` arm ≤ 50 % of
  the `direct` arm, at equal solve count.
- It will not run without `CONFIRM_AGENT_RUN=1`: 32 real model runs cost real
  money, and the refusal is the honest default.

## Run

```sh
cd benchmarks/ask-plan
../../engine/target/release/xerj --version   # build one, or set XERJ_BIN
./run.sh                                     # LABEL=skeleton by default
```

What it does today: verify inputs → boot a private throwaway node → load the
three `ax-*` indices → self-check every `query_equivalent` against gold →
probe `POST /_ask` → (endpoint absent) write
`results/<date>-<label>/status.json` with `measured: false` and exit 0.
Nothing else. With a build
that has `POST /_ask`, steps 4 onward produce `ask-raw.jsonl` +
`summary.json`; the agent arm is `scripts/agent_arm.py` behind
`CONFIRM_AGENT_RUN=1`.

## What is verified today, and what is not

Verified in this sandbox, 2026-09-29: the three downloads (HTTP 200, sha256
in provenance.json); the licence statements (fetched live, quoted verbatim in
each LICENCE); `derive_pairs.py --check` byte-identical regeneration (230
pairs); `verify_pairs.py` — every doc_id resolves to a raw row, every DSL
uses only `term`/`range`/`bool.filter` with bounds; and `run.sh` end-to-end
against a locally built `v1.0.0-rc.78` (run record committed at
`results/2026-09-29-skeleton/`): load counts 655 / 3,000 / 1,704 docs —
exactly the raw row counts — and the **fixture self-check passed on all 230
pairs**: every `query_equivalent` reproduces its gold doc-id set on the real
engine. `POST /_ask` answered 405 and the harness stopped with
`measured: false`, as designed.

NOT measured, plainly: the token arms (gate 3 — never run); index routing by
catalog description (needs the autoindex catalog, out of this harness's
scope for now). Latency is measured as WALL-CLOCK over loopback HTTP
(`scripts/latency_arm.py`, gate row 4): the issue's line says **CPU** on a
20-field index, and this harness cannot see in-process CPU time — loopback
wall-clock on an idle node is an upper bound on it, which is what the gate
row claims and nothing more. The fixture indices are small (655 / 3,000 /
1,704 docs); the measured p50 is a fact about THIS fixture, not a promise
about larger corpora.

When a measured run lands, it lands in `results/` with its raw files, and
this README's gate table gains a MEASURED row citing it — the table does not
move before that.
