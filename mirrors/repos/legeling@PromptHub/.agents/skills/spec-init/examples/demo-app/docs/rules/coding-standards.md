# 编码规范

## 职责边界

- 本文件负责：代码实现约束、设计先行约定、注释规范和禁止行为。
- 本文件不负责：测试分层细则、提交格式或变更生命周期；分别见 `testing-standards.md`、`commit-rules.md` 和 `change-management-rules.md`。

## 基本原则

- 先需求、再设计、再实现，禁止跳过文档直接大规模编码。
- 优先做最小正确改动，避免引入不必要的抽象。
- 不确定的信息写入文档的 `[待确认]`，不要在代码里靠猜测补齐。
- 对技术栈、架构、部署形态、权限模型等关键设计，不要为了省事选“最简单能跑的”，而要选对当前需求最合适、可解释、可维护的方案。

## 代码变更要求

- 新功能必须能回链到 `FR-*`、`DES-*`、`TEST-*`、`T-*`。
- 接口、数据结构或配置项变化时，必须同步更新 `docs/workflow/02-design/README.md`，并在需要时回写 `docs/knowledge/structure/README.md`。
- 关键技术权衡应记录到 `docs/adr/`。
- 当存在多种合理技术方案时，必须先在设计文档中列出利弊，并确认是否需要用户拍板。
- 大规模实现前必须先做一致性分析（analyze），确认没有孤立 ID、冲突文档或阻塞性 `[待确认]`。
- 实现完成后必须做文档收敛（converge），不能只改代码不更新当前状态文档、长期知识和变更记录。

## 设计先行约定

- 前端项目在开始大规模开发前，必须先在 `docs/workflow/02-design/README.md` 写清当前阶段交互设计，并把长期稳定规范沉淀到 `docs/knowledge/reference/README.md`。
- 后端项目在开始接口和数据库实现前，必须先在 `docs/workflow/02-design/README.md` 写清当前阶段接口与数据设计，并把长期稳定边界沉淀到 `docs/knowledge/structure/README.md`。
- 如果这些规范还不存在，不允许开发者按个人习惯默默决定；必须写入 `[待确认]` 或明确记录临时约定。

## 注释规范

- 代码必须包含有用注释，解释关键业务流程、结构边界和设计原因。
- 注释的目标是让后来人快速理解“这段代码是什么、为什么存在、如何串起业务流程”，而不是逐行翻译语法。
- 涉及需求承接、状态流转、权限判断、数据一致性、异常恢复、外部依赖、性能权衡的代码，必须在模块、函数或关键代码块附近写清楚背景。
- 公共 API、核心领域服务、复杂流程编排和跨模块边界必须有文档注释，说明输入输出、业务目的、关键约束和关联需求 / 设计 ID。
- 注释应优先说明“为什么这样做”和“这段逻辑在整体结构中的位置”，避免只写“设置变量”“调用函数”这类无意义注释。
- 如果代码实现与直觉不同，必须注释说明原因、取舍和风险。
- 修改代码时同步更新过期注释；过期注释视为错误文档。

## 禁止行为

- 用硬编码假数据掩盖真实问题
- 用注释掉出错代码的方式“修复”问题
- 用 `TODO` 占位代替关键逻辑
- 用默认值吞掉本应暴露的缺失字段或异常
- 写只复述代码语法、不能解释是什么或为什么的空注释
